# Наземные путешествия: страница, навигация и состояния

Date: 2026-10-13
Status: resolved

Основание — [исследование текущего UI](./page-flow-research.md) и последние
ответы владельца. Одна общая страница заменяет прежнее решение о двух
самостоятельных страницах. Домен путешествия остаётся типизированным rail/road.
Это принятый контракт будущего UI, не макет, реализация или визуальная приёмка.

## Страница и навигация — принято

Приватная `/ground-travel`: «Наземные путешествия» / «Ground travel».
Общий список поездов и роуд-трипов, фильтр «Все / Поезда / Авто».
Кнопка добавления открывает выбор «Поезд / Роуд-трип» и соответствующую форму.
Переключение вида в списке не преобразует существующую поездку и не смешивает
типы в одном путешествии. У каждой карточки различим вид транспорта.

Desktop: Обзор, Журнал, Наземные путешествия, Паспорт. Текущий desktop Add flight
сохраняет свои функции; у новой страницы собственный выбор поезд/роуд-трип.
Mobile: четыре направления «Обзор / Журнал / Наземные / Паспорт», с коротким
EN-именем «Ground» и полным доступным именем раздела. Нижняя кнопка «+»
заменяется четвёртым направлением, добавление находится внутри страниц.
На Journal сохраняется доступ ко всем четырём действующим способам добавления
перелёта через его кнопку; новая наземная форма не подменяет flight capture.
Профиль/настройки/очередь/рейтинг остаются доступны через существующие входы.

Это принятая поправка к Shell and navigation в DESIGN.md, ещё не построенная.
Остальные токены, responsive breakpoint, shared controls и правила движения
применяются как есть; дополнительных декоративных анимаций не требуется.

## Списки — принято

Обычный вид сначала показывает планы: будущие по ближайшей дате, затем планы
с прошедшей датой (новые даты раньше старых), затем без даты. Прошедшая дата
предлагает завершение, но не меняет статус. Сравнение использует одну todayISO
в текущем часовом поясе браузера владельца, с UTC fallback; сервер и клиент
одной загрузки используют тот же cutoff. Новый день пересчитывает группы,
но не статусы. Сегодняшний план остаётся в ближайших до следующего дня.
Далее история от новых к старым по дате начала; записи без даты — в её конце.
Равные даты сортируются стабильно по created_at DESC и ID ASC; undated — created_at DESC,
затем ID. Редактирование заметки не переставляет поездку по updated_at.

Отменённые доступны отдельным фильтром; при нём список содержит только отмену,
с тем же фильтром транспорта, датами начала DESC и неизвестными датами в конце.
Группировка и год используют дату начала; известный конец не заменяет её. Действия —
восстановить план или удалить. По умолчанию отмена не попадает в планы/историю.
Нет записей в текущем фильтре отличается от пустого всего раздела.

В обычном виде компактные фактические итоги разделены по транспорту: при «Все»
два блока, при выбранном виде — его блок. В cancelled-only view итоги скрыты,
чтобы не выдавать общую историю за статистику отменённых. Их метрики заданы
в places/storage contracts; неизвестное и неполное явно обозначаются.
Полная карта и подробности — внутри путешествия, не над общим списком.

## Адреса и возврат

`/ground-travel?mode=rail|road` фильтрует транспорт; без mode — все.
`status=cancelled` включает отменённые. Query-detail:
`/ground-travel?journey=<UUID>` открывает общую Sheet с типизированными деталями;
остальные фильтры сохраняются. Detail читается по владельцу/ID, независимо
от попадания карточки в текущий фильтр. Источники в Passport используют этот
адрес, а не прежние `/trains`/`/road-trips` предложения.

Новая запись: `/ground-travel/new?mode=rail|road`. Редактирование:
`/ground-travel/<UUID>/edit`; тип берётся из записи, не из query.
Формы и прямые ссылки под `(member)` проходят admission до приватных чтений;
чужая и отсутствующая запись не раскрывают данные другого владельца.
Существующий legacy `/journey → /overview` не меняется.

Фильтры заменяют history entry, открытие detail создаёт entry, смена выбранной
поездки заменяет его. Close/Back снимает свой detail entry; для прямого deep link
закрытие делает replace на текущий список, не уводит на случайный внешний сайт.
Возврат из new/edit сохраняет фильтры и контекст списка. Нет origin context —
возврат на `/ground-travel`; отмена формы сохраняет незаконченный ввод.
Клиент принимает только внутренний allowlisted return context, не произвольный URL.

## Ввод и действия

Сначала выбор «План / Совершённая поездка» и основа маршрута; известная старая
дата не завершает запись сама. Старая поездка сразу использует единую сверку.
Rail: список участков, город отправления/прибытия обязателен, станции/даты/
времена/характеристики необязательны. Добавление пересадки не требует заново
вводить известный город. Road: упорядоченные города, возврат к старту одним
действием; даты/ночёвки/заметки раскрываются при необходимости. Порядок меняется
кнопками и drag, без скрытого удаления повторной точки города.

OCR доступен в rail форме, пакет и общая проверка следуют rail-ocr contract.
Единая сверка показывает фактический маршрут, даты и явно подтверждённые страны;
карта лишь предлагает города/схему, не подтверждает границы.
Detail предлагает редактирование, завершение плана, отмену/восстановление плана,
возврат совершённой поездки в планы и удаление с существующим явным подтверждением.
Возврат в планы сообщает о снятии вклада этой поездки в Passport/итоги.
Удаление не обещает Undo; archived plan versions/корзина не появляются.

## Сохранение и восстановление

Незаконченный ввод изолирован по owner + schema version + new kind/edited ID.
Исходники OCR не сохраняются; восстанавливаются только полученные поля.
Завершённое сохранение очищает только подтверждённый снимок ввода. Если человек
успел изменить поля после отправки, поздний ответ не стирает эти изменения;
новые правки остаются несохранёнными. Двойная отправка использует тот же ключ
и submitted payload, а не новый create ID.

Неясный результат записи — отдельное состояние проверки квитанции. Отправленный
payload/ключ сохраняются, новые правки не подменяют их. Повтор оригинальной
операции следует storage contract; новый create ID не используется как обход.
При 409 показаны актуальные данные и сохранены собственные правки; повторное
применение выбирается явно. `saved + pending` означает сохранённую поездку:
итоги ждут нужную опубликованную ревизию, запись не отправляется заново.
Выход/смена владельца прерывает запросы и исключает восстановление чужих полей.

## Состояния и доступность

Loading, confirmed empty, filtered empty, partial, read error и ready различимы.
Неудачное чтение не изображает пустой журнал. Если детали недоступны, реально
полученный список остаётся; ошибку detail можно повторить отдельно. Городской
поиск различает loading/no result/error; запоздавший ответ не заменяет текущий
запрос. Ручное место доступно по принятому places contract.

RouteFocus переводит фокус на h1 при pathname navigation; фильтры этого не
делают. Sheet управляет modal-фокусом; close возвращает его к карточке, а если
она исчезла из фильтра — к доступному заголовку/списку. Добавление/перестановка
точки сохраняет логичный фокус; drag имеет кнопочную альтернативу.

Используются существующие Menu/Sheet/Combobox и текстовые кнопки. Длинные
названия/кольцевые маршруты остаются читаемыми; детали раскрывают полный маршрут.
RU/EN, 320px, 200% текста, 44px цели, видимый focus и reduced motion обязательны.
Полный корпус городов не загружается в Combobox; loading/error и асинхронный
поиск адаптируются на текущем seam. Наличие примитива не доказывает приёмку.

Проверки реализации: hard/soft admission, query/detail/back, owner isolation,
активный вложенный route, четыре направления и сохранённые flight capture
входы, пустой/недоступный/частичный список, отмена/восстановление, своя форма,
поздний ответ/неясное сохранение. Требуются Next build и полная navigation suite
по CODING_STANDARDS. Визуальная приёмка выполняется на построенном UI;
этот triage не является её результатом.

# Arc elements for boarding-pass Quick Add

Status: Recommendations from three GPT-6-Luna scouts at Max reasoning, using the manually invoked `$arc` skill on 2026-10-12. This is component research; no application code or dependencies changed.

Accepted behavior: [Boarding-pass Quick Add](../plans/2026-10-12-boarding-pass-quick-add.md). Visual and local API authority: [DESIGN.md](../../DESIGN.md) and installed source. The generic Arc defaults do not override either.

## Recommended composition

Compose the current mobile Sheet, equal source buttons, single-file selection, ticket review, unresolved questions and optional disclosure. All of these pieces already exist in Kuuki. The local barcode reader supplies extracted fields; these components do not implement recognition or persistence.

The caller selects `side`; anything other than `right` uses the local `BottomSheet`. Choose detents around the actual content and keyboard, rather than adding a second overlay stack.                    |

Use the current Button's `loading`/`loadingLabel` and visible `disabledReason` for action feedback where appropriate. Keep persistent errors and retry near the affected row. Recognition has no trustworthy percentage total; use truthful stages/status rather than an invented progress bar.

## Important integration details

**Unresolved dates.** Ticket requires a `date` string. The current mobile ReviewRow already supplies an empty string for an unknown date, and [`formatDateOnly`](../../apps/next/src/lib/format.ts) returns that unchanged. This avoids a fabricated year but produces a blank date. Quick Add needs a visible and accessible “year to confirm” or unresolved-date cue alongside the question. Do not manufacture a complete date to satisfy presentation. Ticket's article label currently names only the route.

**Draft presentation.** ReviewRow uses Ticket's `upcoming` styling with a review-specific status label. Keep the distinction between styling and canonical flight lifecycle. A same-day preflight capture remains an import draft row. Do not label it “Today”, “Landed” or “Logged” merely because its barcode decoded. Do not manufacture AI confidence percentages for locally decoded fields.

**Durable finish-later.** QuestionDeck's deferred-question set is component-local state, and its “not flown” answer dismisses a row. Neither operation implements durable deferral. Use the persisted import batch and existing queue for the accepted finish-later behavior. A “flown” answer selects a draft; final confirmation is still required.

**Existing authorities.** [`ReviewStep`](../../apps/next/src/client/import/review-step.tsx) accounts for selected, blocked, duplicate and unsaved rows. [`ImportClient`](../../apps/next/src/client/import/import-client.tsx) owns draft saving and final confirmation. Preserve version checks, pending/error handling and the save authority instead of creating a second save path.

**Capture handoff.** [`SourceStep`](../../apps/next/src/client/import/source-step.tsx) currently validates PDF/PNG/JPEG and size, then submits base64 plus a source label. Its API has `initialMode`, not an externally selected File. Native photo acquisition and handing a Quick Add selection into this boundary need an adaptation; the current component is not a drop-in camera controller. HEIC/orientation/PDF handling belongs in the decoder/media feasibility work.

**Shared entry.** [`AddActions`](../../apps/next/src/client/add-actions.tsx) serves the desktop menu as well as the mobile sheet. A change to its shared action route affects both callers.

## Current official Arc catalog

The catalog scout checked the [official index](https://uiarc.dev/llms.txt), [public catalog](https://uiarc.dev/r/catalog.json) and component markdown on 2026-10-12. Arc MCP search/get tools were not exposed, so official public documentation supplied the external evidence. These candidates were listed as free:

| Candidate                                                                | Verified upstream capability                                                                               | Decision                                                                                                                                                                                                  |
| ------------------------------------------------------------------------ | ---------------------------------------------------------------------------------------------------------- | --------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| [File dropzone](https://uiarc.dev/components/file-dropzone/markdown)     | `accept`, `multiple`, `onFilesChange`, `maxSize`, per-file `onUpload`; no documented camera `capture` prop | Use Kuuki's existing single-document adaptation. Generic per-file upload behavior is not the local controller's API.                                                                                      |
| [Bottom sheet](https://uiarc.dev/components/bottom-sheet/markdown)       | Controlled opening, detents and detent callbacks                                                           | Use the installed Sheet/BottomSheet adaptation, retaining local focus, viewport and footer behavior.                                                                                                      |
| [Expandable card](https://uiarc.dev/components/expandable-card/markdown) | Summary/details and expanded state                                                                         | Available and already adapted locally, but Disclosure is the simpler fit for inline pass details. Keep ExpandableCard for callers that actually need its card expansion or existing import dock behavior. |

Additional [Button](https://uiarc.dev/components/button/markdown), [Alert](https://uiarc.dev/components/alert/markdown), [Progress](https://uiarc.dev/components/progress/markdown) or [Radio group](https://uiarc.dev/components/radio-group/markdown) source would add little to the installed controls and existing year question. `ConfirmMorph` serves destructive confirmation and is not the flight-save control. A separate full file-upload block would duplicate the current controller.

No new Arc source, Pro functionality, provider, foundation stylesheet or fonts are needed for this recommended composition. Any later source acquisition must follow the tier/licence and attribution rules in the [Arc adoption inventory](2026-10-08-arc-source-inventory.md).

## Evidence limits and Arc review scope

Component fit, local prop contracts and the existing review/save boundaries are supported by installed source. Labels, native controls, sheet focus hooks, disclosure semantics and row readiness have source evidence; that does not prove the proposed composition is accessible when rendered.

Visual hierarchy, typography/copy, semantic token use, contrast, motion, touch geometry, overflow, both themes/accents and actual keyboard/screen-reader behavior were not audited in a running build. The current T3 concept is separate from these installed React components. Browser/device checks, decoder correctness and persistence integration were outside this component-selection task. No application lint/test/build result is claimed from read-only inspection.

Before implementation, resolve the date cue and stable `today` input, wire photo acquisition and local-field admission, then check the composed flow at phone widths and with the keyboard open. The accepted local-decoder pilot remains the evidence gate for recognition usefulness.

# Kuuki open-source map options

Date: 4 October 2026. Local baseline: `13034853df51874d20da95a3f4f3c2f7ea74f538`. Research only; no map dependency, application code, cloud resource or provider account changed.

User clarification: application code can use **mapcn + flightcn** directly. Installing mapcn supplies MapLibre as their rendering dependency; no separate handwritten MapLibre integration is implied. The selected direction and prototype gates are consolidated in the [decision record](../audits/2026-10-04-architecture-decisions.md).

## Recommendation

Prototype **MapLibre GL JS with mapcn for the expanded route map, passport and journey planner**, using flightcn's flight-history recipe as a focused interaction/geometry reference. Keep a small SVG dashboard preview and a non-WebGL fallback. Start with a tile-less country map using pinned public geometry served by Cloudflare Static Assets; detailed street tiles are not required by the existing features. Add **Protomaps/PMTiles on R2** only if the product needs a detailed basemap and measured traffic/latency justifies owning its delivery.

This recommendation separates three decisions: MapLibre renders the map, mapcn supplies React controls and composition, and a basemap supplies geographic detail. A visually polished UI does not require a third-party tile service. MapLibre runs in the browser; deploying Next on Workers does not require a server-side WebGL renderer or a GIS database.

mapcn is the strongest candidate for Kuuki's existing Tailwind/shadcn UI because its source provides theme-aware controls, selected routes, popups, polygon interactions and clustered points. It is a registry component copied into the app, so our team owns that code and must track upstream fixes. It uses MapLibre directly; adding react-map-gl alongside it would duplicate the React integration. This is an architectural judgment from source and docs, not a measured performance or visual comparison. [mapcn repository](https://github.com/AnmolSaini16/mapcn), [component API](https://www.mapcn.dev/docs/api-reference).

### Flight-specific candidate

[flightcn's playground](https://flightcn.yencheng.dev/playground) and [flight-history recipe](https://flightcn.yencheng.dev/recipes) are the closest examples to Kuuki. The root checked its current source: it uses Turf great-circle geometry and explicitly preserves MultiLineString dateline splits, rather than mapcn's decorative arc math. Its README claims type compatibility with MapLibre v5/v6, and its registry pulls in mapcn. However, its own demo dependency remains MapLibre `^5.19.0`; pin and test the copied code against v6/Next/OpenNext before adopting it. Preserve our existing airport/domain source instead of the registry's bundled 515-airport subset. Its source has a straight-line fallback when arc calculation fails, so geometry edge cases still need validation. `FlightRoutes` composes individual route components; a larger history should be compared with one batched GeoJSON source rather than assuming that component scales efficiently. Recipe source is an implementation reference; demo styling/performance was not inspected in a live browser. [Flight source](https://github.com/ridemountainpig/flightcn/blob/main/src/registry/flight.tsx), [registry dependencies](https://github.com/ridemountainpig/flightcn/blob/main/registry.json), [demo package](https://github.com/ridemountainpig/flightcn/blob/main/package.json).

## Version and implementation constraints

**Verify against MapLibre 6, not old snippets.** Current releases show **6.12.0, released 3 October 2026**; mapcn's current demo package declares `maplibre-gl ^6.3.0` and React 19.2.3. The demo's package version is not a stable mapcn npm-library release contract. Pin the renderer and the copied registry revision when prototyping. [MapLibre release](https://github.com/maplibre/maplibre-gl-js/releases/tag/v6.12.0), [mapcn package](https://github.com/AnmolSaini16/mapcn/blob/main/package.json).

MapLibre 6 is ESM-only and requires WebGL2. Handle unsupported/failed GPU initialization with the preview and the flight/country list. On Next/Turbopack, copy the installed worker **and its shared module** to the same versioned public directory at build time, then configure the matching worker URL. A worker emitted without its sibling can mount a map that never loads tiles. mapcn defaults to an unpkg worker; self-host those files through Static Assets instead. The existing main-app CSP is report-only and lacks worker permissions; validate the actual Next response policy during the proof, while keeping activation-page isolation. [v6 migration](https://maplibre.org/maplibre-gl-js/docs/guides/v5-to-v6-migration-guide/), [installation and Turbopack guidance](https://maplibre.org/maplibre-gl-js/docs/), [mapcn installation](https://www.mapcn.dev/docs/installation), [local headers](../../apps/web/public/_headers).

**Flight arcs must represent the intended geography.** mapcn's `MapArc` is a quadratic Bézier in longitude/latitude space. For geographic route views, build sampled great-circle LineString/MultiLineString features and render a batched line layer; use a wider invisible hit layer for touch selection. Audit the existing [geometry helper](../../apps/web/src/lib/geo.ts) for coincident/antipodal endpoints, numerical stability and wrapping before reusing it. These paths represent estimated great-circle connections, not recorded aircraft tracks. If a large-data benchmark requires deck.gl, `GreatCircleLayer` or `ArcLayer` with `greatCircle: true` is the relevant option, rather than decorative default arcs. [mapcn arc contract](https://www.mapcn.dev/docs/arcs), [deck.gl great-circle contract](https://deck.gl/docs/api-reference/geo-layers/great-circle-layer).

Use stable country IDs, fill/outline layers and feature state for hover/selection. Render airport circles/labels in layers when counts grow; reserve HTML markers/popups for selected items. Keep geometry stable across React renders, update only changed filters/paint/data, and avoid copying the full flight history into map props. Theme changes must restore our layers and selected state. The current mapcn source tears down/recreates children for style swaps and removes its map on unmount; those behaviors need a route-navigation and theme-switch proof, rather than a second custom lifecycle framework. [MapLibre hover example](https://maplibre.org/maplibre-gl-js/docs/examples/create-a-hover-effect/), [mapcn source](https://github.com/AnmolSaini16/mapcn/blob/main/src/registry/map.tsx).

## Basemap delivery on Cloudflare

For the current world/country use case, prefer `Map blank` plus a versioned low-detail GeoJSON asset. Build the ISO country IDs into the asset instead of maintaining another renderer-specific numeric-code table. Serve public geometry, styles and the worker with immutable versioned URLs. User routes remain authenticated application data; do not put private flight layers into a public archive or shared Next/edge cache.

If detailed geography becomes a requirement, compare **direct browser PMTiles range requests to an R2 custom domain** with **the Protomaps Worker ZXY tile adapter plus R2**. The first avoids a tile application server; the second supports tile-response caching. Test Range/206 support, CORS, ETag handling, cold/warm latency and read-operation volume. Preserve archive version identity by publishing a new URL on updates, and host required styles/glyphs/sprites too. R2's lack of egress charges does not eliminate request/storage cost or guarantee low cold-read latency. No PostGIS, Hyperdrive, Durable Object, Queue or dedicated GIS server is justified by the current map needs. [PMTiles storage contract](https://docs.protomaps.com/pmtiles/cloud-storage), [MapLibre protocol](https://docs.protomaps.com/pmtiles/maplibre), [CF adapter and cache](https://docs.protomaps.com/deploy/cloudflare).

mapcn's default CARTO basemap is an external service choice, not a property of MIT licensing. Choose a provider explicitly if we need tiles; verify its commercial terms and attribution separately from the renderer. OpenFreeMap is a credible hosted alternative with the stated no-SLA limitation. Our tile-less first option avoids that decision. Keep public basemap resources separate from private flight layers even if both use the same renderer.

## Next navigation, UX and acceptance evidence

Keep the authenticated shell, summary, accessible country/route list and preview available before map initialization. Load the browser-only map in a Next client island with a fixed-size placeholder, using visibility or explicit expansion to govern the heavy import. Instant Navigation shell prefetching should not eagerly initialize a GPU map or fetch every user's route dataset. The map must not hold up a page transition; preserve viewport in a suitable persistent layout or bounded UI state only when the user flow benefits.

Use a quiet low-detail map, restrained route colors, labels revealed by zoom/selection, a clear selected-route panel and a mobile bottom sheet. Add fit-to-trip/reset and explicit zoom controls; avoid scroll capture on small previews. Provide keyboard-accessible controls and a synchronized route/country list for canvas content, visible focus, reduced camera motion and loading/unavailable states. Library accessibility claims do not establish that Kuuki's map interaction is accessible.

The bounded proof should compare the expanded current map and mapcn using 50, 500 and 5,000 synthetic unique routes, plus representative deduplicated real-history distributions when consented fixtures exist. Measure first usable map, navigation responsiveness, full bytes including workers/tiles, pan/zoom frame time, filter response and memory after repeated navigation/theme switches. Include mobile/low-power hardware, WebGL2 disabled, failed assets, empty/single-airport trips, Pacific and polar routes, duplicate directions, and restored viewport. Retain the SVG preview unless measured UX benefits justify replacing it. No map implementation, device benchmark or hosted tile latency measurement was performed in this audit.

# Аудит полного импорта CSV из Flighty

10 ноября 2026 года. Проверена текущая рабочая копия Kuuki на базе `dd1074fb`,
включая существующие локальные изменения импорта. Это аудит реализации, а не
подтверждение поведения развёрнутой версии. Код приложения не изменялся.

**Вывод: перенос всей истории из оригинального CSV Flighty сейчас не поддержан.**
Общий AI-импорт не обеспечивает ни сохранение всех полей, ни полноту большой
истории. Соответствие последнему формату Flighty также не установлено: оригинальный
экспорт не предоставлен, а публичный CSV-контракт в просмотренных официальных
источниках не найден. [Отдельная проверка источников](2026-11-10-flighty-export-sources.md)
разделяет подтверждённые сведения и неизвестные свойства CSV.

## Как работает текущий импорт

1. Веб-интерфейс принимает PDF, PNG и JPEG до 10 MiB.
   [`ACCEPT` и `checkFile`](../../apps/next/src/client/import/source-step.tsx)
   используются и общей многофайловой сессией
   [`UnifiedSession`](../../apps/next/src/client/import/unified-session.ts).
   CSV с MIME `text/csv` отклоняется до чтения и отправки.
2. Текст можно вставить вручную. Локальный
   [`parseStructuredText`](../../functions/api/import/_text.ts) понимает списки
   `YYYY-MM-DD | JFK → LHR | BA178 | 19:00 → 07:00`.
   Строка заголовков CSV этот разбор не проходит: весь текст направляется
   в общий Gemini-экстрактор. Сервер принимает только типы `pdf`, `image`, `text`;
   отдельного `csv`-контракта нет.
3. [`normalizeFlights`](../../functions/api/import/_extract.ts) и
   [`draftFieldsOf`](../../functions/api/_services/importDrafts.ts) оставляют
   ограниченный набор полей. Черновики показываются для проверки; сохранение
   идёт через [`importConversion`](../../functions/api/_services/importConversion.ts)
   и общий [`flightCreate`](../../functions/api/_services/flightCreate.ts).
4. Многофайловый интерфейс создаёт отдельные задания, но не разбивает один большой
   CSV на пакеты. Ограничения действуют на каждый источник и в синхронном пути,
   и в [`ImportJob`](../../workers/import/ImportJob.ts).

## Подтверждённые проблемы

### P1. Оригинальный CSV нельзя импортировать файлом

Разрешённых MIME всего три; детерминированного CSV-парсера и отображения его
заголовков на поля Kuuki нет. Вставка содержимого переводит структурированные
данные в вероятностное распознавание. Это основной блокер самого сценария.

### P1. Контракт сохраняет лишь часть данных

Через extraction → draft → flight проходят восемь основных значений: дата,
аэропорты отправления/назначения, авиакомпания, номер рейса, ICAO-тип самолёта,
местные времена отправления/прибытия.

| Группа данных                                                  | Текущая реализация Kuuki                                                                                                       |
| -------------------------------------------------------------- | ------------------------------------------------------------------------------------------------------------------------------ |
| Дата, маршрут, авиакомпания, номер                             | Представлены; неизвестные справочные коды требуют исправления. Номер необязателен.                                             |
| Тип самолёта                                                   | Только `aircraft_icao`; отдельного отображения названия типа из CSV нет.                                                       |
| Время                                                          | Только два местных времени; исходная дата прилёта, смещение и выбор scheduled/actual либо gate/runway не сохраняются импортом. |
| Регистрация борта, место, класс, заметки, PNR, терминалы/гейты | В контракте extraction/draft/flight-create отсутствуют.                                                                        |
| Отмена, перенаправление, внешние идентификаторы                | Не представлены как сохраняемые атрибуты импортированной записи.                                                               |

Это инвентаризация возможностей Kuuki, **не утверждение**, что каждый перечисленный
атрибут присутствует в актуальном CSV Flighty. Набор реальных колонок ещё нужно
проверить по оригинальному экспорту. Неподдерживаемые значения не удерживаются
как остаточные данные: исходный документ намеренно не сохраняется.

### P1. Полная история упирается в ограничения общего импорта

- Вставляемый текст ограничен 100 000 символов (`MAX_TEXT_LENGTH`).
- AI-путь сохраняет максимум 100 черновиков на источник (`MAX_DRAFTS_MODEL`).
- Даже предварительное преобразование в локальный pipe-список даёт максимум
  500 черновиков (`MAX_DRAFTS_DETERMINISTIC`).
- Усечение отмечается состоянием `partial` и `ROWS_TRUNCATED`; это не бесшумная
  потеря, но автоматического продолжения оставшейся истории нет.

Существующие тесты подтверждают усечение 150 результатов модели до 100 и 600
локальных строк до 500. Разбиение подтверждения на запросы по 50 записей не
устраняет более раннее усечение при извлечении.

### P1. Воспроизведена неверная дата прилёта через линию перемены дат

[`computeFlightDuration`](../../functions/api/_services/flightDuration.ts)
рассматривает местную дату прилёта только как дату вылета либо следующий день.
Предыдущая дата не рассматривается; исходную дату прилёта импорт передать не может.

Синтетический пример: вылет HND **11.03.2026 00:30 JST**, прилёт HNL
**10.03.2026 12:30 HST**. Правильные UTC: `2026-03-10T15:30:00Z` →
`2026-03-10T22:30:00Z`, длительность 420 минут. Реальный `resolveFlightTimes`
возвращает прилёт `2026-03-11T22:30:00.000Z` и `durationMinutes: null`.
На сохранении длительность может заменяться медианой/оценкой; это не исправляет
неверный UTC прилёта.

Это дефект общего расчёта времени, воспроизводимый без Flighty. Он мешает точному
переносу, если экспорт содержит такие даты/времена. Исходник явно сохраняет
историческую совместимость с PostgreSQL: исправление должно учитывать эту
оговорку, а не менять старый алгоритм без анализа остальных потребителей.

## Фильтры: что есть и что ещё не доказано

- **Отмены, возвраты, неоплаченные и заменённые брони, чужой пассажир.**
  Для поддерживаемого pipe-списка есть явные правила исключения в `_text.ts`.
  Неопределённые статусы остаются для проверки. Для текста CSV действуют
  инструкции модели в [`EXTRACTION_PROMPT`](../../functions/api/import/_shared.ts).
  Детерминированной обработки колонки отмены CSV нет. Синтетическая передача
  `canceled: true` прямо в нормализатор не исключает строку: это показывает
  отсутствие второго барьера по такому атрибуту, но не доказывает ошибку модели
  на реальном экспорте.
- **Перенаправления.** Нет отдельного правила выбора исходного или фактического
  аэропорта из CSV. До проверки образца нельзя гарантировать верный маршрут и
  последующую статистику стран.
- **Дубли.** [`findDuplicateMatches`](../../functions/api/_services/duplicates.ts)
  сравнивает дату и маршрут по всей истории владельца; сохранение требует
  подтверждения повтора и защищено транзакцией/квитанцией. Это сильная защита
  повторного сохранения. Два разных рейса по одному маршруту в один день также
  будут предложены как повторы: это действующий контракт, не доказанный дефект.
  Внешний Flighty ID не сохраняется и не участвует в сопоставлении.
- **Ручные старые рейсы.** Номер необязателен и не теряется сама возможность
  сохранить дату/маршрут без него. Flighty официально допускает ручную запись с
  тремя обязательными значениями — дата и два аэропорта
  ([Flighty Help](https://flighty.com/help/importing-flights)). Их фактическое
  представление в CSV пока неизвестно.
- **Справочники и уверенность.** Пропуски года и неоднозначные аэропорты остаются
  для исправления; низкая уверенность влияет на начальный выбор. Оценка модели
  не является доказательством точности распознавания CSV.

## Проверки и воспроизведение

Приложение и постоянные тесты не менялись. Запущены существующие проверки:

```sh
pnpm exec vitest run --config functions/vitest.config.ts functions/test/import-text.test.ts functions/test/import-drafts.test.ts functions/test/import-conversion.test.ts functions/test/import-runtime.test.ts
pnpm --filter @kuuki/next exec vitest run src/client/import/source-step.test.tsx src/client/import/unified-session.test.ts
pnpm exec tsx .scratch/flighty-import-audit/probe.ts
```

- API: **147/147**, четыре файла.
- Клиент: **20/20**, два файла. jsdom вывел предупреждения разбора CSS;
  проверки прошли с кодом 0.
- Локальный исполняемый probe: код 0; подтвердил отказ `type: csv`, уход
  CSV-текста из локального парсера, потерю дополнительных атрибутов, сохранение
  кандидата без номера и описанную ошибку даты HND → HNL.

Логи, синтетический probe и открытые задачи находятся в
`.scratch/flighty-import-audit/` этой рабочей копии. Это локальные материалы;
probe не является оригинальным CSV Flighty. Реальных сетевых вызовов модели,
загрузки пользовательских данных, браузерной проверки и изменения production
не было. Успех этих тестов не доказывает поддержку Flighty: fixtures Flighty
и контрактных проверок его CSV в исследованном пути не найдено.

## Минимальный следующий шаг

Получить свежий оригинальный CSV Flighty и версию приложения. По образцу
зафиксировать реальные заголовки, пустые значения, статусы и семантику времени,
затем добавить детерминированный CSV-адаптер к существующему пути черновиков.
Обеспечить обработку всей истории пакетами с учётом исходных строк и явным
отчётом о неподдерживаемых колонках. Сохранение дополнительных полей требует
отдельного решения по модели хранения; добавление MIME само по себе задачу
не решает.

Задачи сохранены в `.scratch/flighty-import-audit/issues/01-csv-compatibility.md`
и `.scratch/flighty-import-audit/issues/02-arrival-date.md`.

# Источники для обогащения истории перелётов Kuuki

Проверено 7 октября 2026 года. Цель: модель самолёта и дополнительные сведения о состоявшемся перелёте без подписки на отслеживание в реальном времени. После исследования выполнен локальный эксперимент с уже используемым Gemini и изменена проверка предложений. Подписки не покупались, закрытые авиационные API не вызывались, деплоя не было.

## Вывод

Бесплатные справочники закрывают аэропорты и характеристики самолёта по известной регистрации. Главный пробел — связь **номер рейса + дата + маршрут → фактически использованный борт**. Среди проверенных источников готового бесплатного глобального поиска с подходящими правами на постоянное хранение не найдено. Отсутствие потребности в real-time не делает глубокую историю дешёвой: у поставщиков отдельно ограничены глубина архива и сохранение данных.

Для Kuuki разумно сначала улучшить исходные идентификаторы и справочники, использовать известную регистрацию и сохранять происхождение предложения. Для поддерживаемых внутренних рейсов США подходит BTS. Из платных кандидатов сначала проверять Flightera и AeroDataBox, но только вместе с условиями хранения. Покупать подписку до проверки покрытия нашего набора рейсов не стоит.

## Состояние Kuuki в начале исследования

- [Импорт](../../functions/api/import/_shared.ts) извлекает модель только когда она указана в документе. Электронные билеты, письма, изображения, PDF и текст поддерживаются уже сейчас. Расширение набора исходных документов не требует нового поставщика истории рейсов.
- [Обогащение](../../functions/api/enrich/aircraft.ts) использовало только Gemini + Google Search; AirLabs был удалён из цепочки. [Промпт](../../functions/api/enrich/_shared.ts) требовал датированных свидетельств. Порог 0.7 и наличие строки `evidence` допускали предложение, но не проверяли источник. Ссылки и цитаты из метаданных поиска обработчик не разбирал. Изменения после эксперимента описаны ниже.
- [Запись рейса](../../packages/shared/src/types.ts) хранит `aircraftIcao`, но не регистрацию, отдельного фактического оператора или происхождение значения модели. До интеграции нового источника нужно определить, какие свидетельства переживают принятие предложения пользователем.
- В [логе февраля](../../scripts/enrichment-log-2026-02-05.md) заполнены 174 из 259 моделей. **67.2% — доля заполненных записей, не измеренная точность**: независимого сопоставления с фактическими бортами в логе нет; тогда промпт ориентировался на текущее оборудование маршрута. Нынешний код уже требует исторических свидетельств.
- Расстояние, часовые пояса и оценка длительности уже вычисляются локально по [ADR 0002](../adr/0002-flight-metrics-provenance.md). Для них авиационный API не нужен. Фактически пройденное расстояние и время в воздухе — другие величины.

Две частые ловушки:

- [ADSBDB](https://github.com/mrjackwills/adsbdb) удобно возвращает модель по регистрации/ICAO24, но поиск callsign не принимает дату и не подтверждает борт рейса. MIT относится к коду; README отдельно запрещает копирование/публикацию/включение данных маршрутов в другие базы без разрешения владельца данных. Для aircraft-данных указан PlaneBase, но достаточные права на продуктовую выгрузку нужно уточнить. Не выбирать по одному обещанию «free API».
- [OpenFlights](https://openflights.org/data.php) — справочник под ODbL, не архив состоявшихся рейсов. Маршруты не обновлялись с июня 2014 года. Его equipment нельзя применять как подтверждение самолёта на дату поездки. [tar1090-db](https://github.com/wiedehopf/tar1090-db) полезен как формат выгрузки Mictronics; права источника нужно сохранять.

### Почему OpenSky не первый выбор

[REST API](https://openskynetwork.github.io/opensky-api/rest.html) возвращает наблюдаемые полёты с ICAO24/callsign и оценёнными аэропортами. Это не готовая таблица коммерческих номеров и кодшеров. `states` для обычного авторизованного пользователя ограничены прошедшим часом, экспериментальные `tracks` — 30 днями; эти пределы нельзя переносить на `/flights/*`. Полёты обрабатываются пакетно, есть отдельные ограничения интервала запроса и квоты. Документация не гарантирует полный архив по любому старому рейсу.

Аутентификация теперь только OAuth2 client credentials, Basic больше не принимается. [Условия OpenSky](https://opensky-network.org/about/terms-of-use), §3(vi), требуют письменной лицензии для операционного использования REST в продукте, в том числе некоммерческом. [Trino](https://openskynetwork.github.io/opensky-api/trino.html) предназначен для исследовательской работы с сырой историей. Это полезный исследовательский источник, но не беспрепятственный бесплатный backend Kuuki.

### Хранение важнее цены запроса

[AeroDataBox terms](https://aerodatabox.com/terms), обновлены 19 сентября 2026: ограничения распространяются и на извлечённые отдельные поля. Постоянная копия модели/регистрации — не автоматически разрешённый derived work. Standard caching — 7 дней, расширенное хранение определяется планом; Growth допускает хранение при активной подписке, более высокий план имеет ограниченное хранение после отмены. Для Kuuki нужно отдельно согласовать постоянные пользовательские записи, экспорт и публичный профиль, включая сохранение после завершения подписки.

[Flightera terms, Part B](https://www.flightera.net/en/terms) разрешают хранить данные при активной подписке и показывать пользователям записи их запросов. После завершения подписки использовать данные в продукте, поставляемом другим, нельзя. Есть запрет конкурирующих продуктов и самостоятельных выгрузок данных. Сценарий постоянного журнала, его CSV-экспорта и публичных профилей требует подтверждения поставщика. Подписка Plus — отдельный продукт и не даёт API-доступ.

[FR24 storage rules](https://fr24api.flightradar24.com/docs/storage-rules) требуют удалить накопленные данные через 30 дней после получения. [Terms](https://www.flightradar24.com/terms-of-service), §2.3, запрещают автоматический сбор сайта вне API. Подтверждение подсказки пользователем или ответ LLM не следует считать обходом лицензионных ограничений источника. Это практическая оценка совместимости условий с продуктом, а не утверждение о правовом статусе отдельных фактов.

## Что появилось в 2025–2026 годах

1. **17 апреля 2025 — FR24 Flight Summary Light/Full.** Light включает ICAO type, регистрацию, оператора, аэропорты и takeoff/landing UTC. Full добавляет длительность в воздухе, фактическое расстояние и полосы. Это подходящий по составу ответ без трека. По [документации endpoints](https://fr24api.flightradar24.com/docs/endpoints/overview), summary начинается с 1 июня 2022; дата 2016 на сайте относится к другим историческим endpoints. [Анонс](https://www.flightradar24.com/blog/b2b/flight-summary-flightradar24-api/).
2. **18 августа 2025 — Gemini URL Context вышел в GA.** Можно анализировать содержимое конкретной страницы/PDF, дополняя общий поиск. Для Kuuki это небольшой эксперимент на разрешённых датированных источниках; инструмент не открывает закрытые базы и не отменяет условия сайтов. [Анонс Google](https://developers.googleblog.com/en/url-context-tool-for-gemini-api-now-generally-available/), [документация](https://ai.google.dev/gemini-api/docs/url-context).
3. **2026 — AirLabs Historical Beta.** [Публикация 1 июня 2026](https://airlabs.co/historical-flight-data-api) и документация подтверждают направление, но не полноту архива и не наличие фактического борта.
4. **Август–сентябрь 2026 — Flightera Direct API.** Part B условий действует с 7 августа; опубликованы прямые планы с глубокой историей. Это свидетельство нового предложения, а не доказательство завершённого запуска self-serve или проверенной полноты aircraft-данных.
5. **8 сентября 2026 — AeroDataBox direct subscriptions и credits за ADS-B feeding.** Credits не истекают и работают без подписки через прямой gateway. Если приёмник уже есть, это может снизить расход; покупать и обслуживать приёмник только ради Kuuki пока не предлагается. Ограничения использования/хранения нужно проверять отдельно. [Анонс](https://aerodatabox.com/direct-subscriptions).
6. **7–19 сентября 2026 — AeroDataBox уточнил условия хранения и переиспользования.** [Объявление](https://aerodatabox.com/2026-09-terms-update) действует для новых подписчиков сразу; для существующих указана дата 7 ноября 2026. Это причина перепроверить старые рекомендации и тарифы.

## Что извлекать из документов и что подтверждать отдельно

[IATA BCBP guide](https://www.iata.org/contentassets/1dccc9ed041b4f3bbdcf8ee8682e75c4/2021_03_02-bcbp-implementation-guide-version-7-.pdf) описывает в штрихкоде аэропорты, operating carrier, номер, день года, место и cabin compartment. Тип самолёта и регистрация не входят в обязательный набор. Дата рейса не содержит полного года; условная дата выпуска содержит последнюю цифру года. Для старого документа это не основание угадывать десятилетие. Декодирование поможет идентификации рейса, но не само по себе модели самолёта.

Для расширения импорта полезнее сначала извлекать явно указанные сведения из itinerary/билета/письма/экспорта другого журнала. Указанное оборудование сохранять как **запланированное**, пока нет фактической записи. Фото регистрации борта или явное свидетельство пользователя позволяют перейти к справочнику, если связаны именно с этим перелётом. Место/схема салона не доказывают конкретную модификацию.

## Результат локального эксперимента

По согласованию проверяли качество источников, а не точность моделей: в тестовых данных нет независимо подтверждённых моделей или регистраций. Взяты 30 обычных перелётов 2015–2026 годов из существующей частной выборки импорта: 28 разных маршрутов, 28 записей с номером рейса. Модель — текущая `gemini-3.5-flash-lite`, по три перелёта в запросе. Выборка не представляет весь мир и не позволяет измерить точность.

| Прогон                                     | Ответы / ошибки, перелёты | Поисковые источники в метаданных | Предложенные модели | Медиана / максимум времени пакета |
| ------------------------------------------ | ------------------------- | -------------------------------- | ------------------- | --------------------------------- |
| JSON schema + Google Search                | 27 / 3                    | 0                                | 0                   | 5.41 / 19.64 с                    |
| Обычный JSON по инструкции + Google Search | 30 / 0                    | 0                                | 0                   | 3.83 / 5.82 с                     |

В первом прогоне учтены 15 858 токенов; расход одного ошибочного пакета неизвестен. Во втором — 17 373 токена. Это не стоимость в долларах: плата за поисковые запросы здесь не рассчитана. Оба прогона использовали один набор перелётов; запросы стохастические, поэтому это не контролируемое доказательство преимущества одного формата.

**Улучшение покрытия не подтверждено: финальный прогон дал источники для 0 из 30 перелётов.** Отсутствие `groundingChunks` не доказывает, что поиск не выполнялся или нужные страницы не существуют. Один диагностический запрос по известным публичным событиям вернул цитаты без JSON schema, но повтор не воспроизвёл результат. Отказ от schema не следует считать универсальным исправлением. Предложения без поискового происхождения теперь возвращаются как «неизвестно».

Локально [проверка ответа](../../functions/api/enrich/_lookup.ts) требует известный ICAO-тип, совпадение заявленных даты, маршрута и полного номера с перевозчиком, а также ссылку из поисковых метаданных. Цитаты привязываются к конкретной записи, включая UTF-8 и накопительные сегменты; произвольный URL из текста ответа не принимается как источник. Без номера рейса и перевозчика предложение отклоняется: на одном маршруте в день бывает несколько вылетов.

[Панель проверки](../../apps/next/src/client/import/aircraft-panel.tsx) показывает ссылки, заявленную дату рейса в источнике, оператора и регистрацию, если они есть. Фактический самолёт и оборудование из расписания различаются; расписание изначально не выбрано для принятия. Эти классификация и поля остаются утверждениями AI — наличие найденного URL не означает независимой проверки содержания страницы. Регистрация, оператор и происхождение показываются при проверке; принятие по-прежнему сохраняет только существующее поле `aircraftIcao`. Схема журнала не менялась.

Для воспроизведения есть [скрипт проверки источников](../../scripts/evaluate-aircraft.ts). Он требует явного `--real-provider`, читает `GEMINI_API_KEY` из окружения или `.dev.vars`, вызывает платный по использованию провайдер, но не пишет в журнал или D1. Вход и результаты допускаются только в игнорируемой `.scratch/import-eval/`; частная выборка не включена в репозиторий. Вход — JSON с `flights` из 1–50 записей с уникальными `id`, календарной `date`, IATA `origin`/`destination` и необязательными `airline_iata`, `flight_number`, `airline_name`.

```sh
pnpm exec tsx scripts/evaluate-aircraft.ts --real-provider \
  --input .scratch/import-eval/aircraft-input.json \
  --output .scratch/import-eval/aircraft-evaluation-new.json
```

Для следующей проверки нужен источник, связывающий конкретный перелёт с регистрацией: явно указанный борт в исходном документе, BTS в своём охвате или небольшой разрешённый архивный набор. Дальнейшие повторения общего поиска без изменения источников пока не оправданы полученным покрытием.

Локальная проверка изменений: `pnpm typecheck:api`, 857 API-тестов, 22 теста панели/проверки самолётов, линтер изменённых файлов Next, `pnpm next:build` и все 151 тест навигации прошли. Навигация запускалась на свободном порту через `KUUKI_NEXT_PORT=8808`; первоначальный запуск остановился из-за занятого 8800. Независимый обзор выявил риск сопоставить запись без номера рейса с другим вылетом на том же маршруте и дате; он исправлен и покрыт регрессией. Это локальная проверка кода, а не проверка точности модели или принятие релиза.

## Рекомендуемый следующий шаг

1. **Без новой подписки:** обновить справочные пробелы из разрешённых источников; сохранять указанные оператор/регистрацию и происхождение предложения; отделить planned от actual; не заменять ручное значение предположением модели. Вычисляемые метрики оставить в существующем resolver.
2. **Следующая проверка источника:** сначала получить датированные записи с известной регистрацией или моделью, затем проверять совпадение маршрута/оператора/даты и нормализацию типа. Проведённый эксперимент с Gemini дал 0/30 источников; оценивать точность без независимых меток нельзя. Использовать реальные цитаты/ссылки из ответа инструмента, а не только строку `evidence`; текущая [документация Google](https://ai.google.dev/gemini-api/docs/google-search) описывает метаданные цитирования. Конкретный формат зависит от API/SDK, используемого Kuuki.
3. **Если нужна высокая полнота старой истории:** запросить у Flightera/AeroDataBox условия для постоянного личного журнала и ограниченный тест нашего набора. Flightera интереснее для рейсов 2017–2024; AeroDataBox — для недавних. Платить за проверенные полезные совпадения, без постоянного опроса всех рейсов и без ненужных треков. Покрытие наших маршрутов пока не измерено.

Перед оплатой важны четыре конкретных ответа поставщика: можно ли бессрочно хранить принятые модель/регистрацию/времена; можно ли сохранять их после отмены подписки; разрешены ли пользовательский экспорт и публичный профиль; какие годы и aircraft-поля реально покрыты. AeroDataBox [предупреждает о best-effort покрытии по регионам](https://aerodatabox.com/data-coverage/); доля найденных рейсов не равна доле заполненных фактических регистраций.

## Границы проверки

Проверены публичные спецификации, тарифы и условия; закрытые авиационные endpoints не вызывались. Уже используемый Gemini вызывался для описанного локального эксперимента. Для OpenSky terms и BTS часть первичных страниц доступна через индексированные фрагменты официальных сайтов, прямое открытие возвращало ошибку. Наличие дат/полей в документации не доказывает качество ответов для Kuuki. Отчёт не обещает процент распознавания и не рекомендует автоматическое принятие неподтверждённой модели.

### Resolved ambiguities

- Import has three visible steps: Source, Review, Done. Recognition is the running substate between Source and Review. The brief's numbered “Stage 4” is Done, not a fourth stepper item.
- The map's buckets are fixed thresholds, 1, 2–3, 4–9, 10+, rather than statistical quantiles. Both the map and titled legend consume the same bucket function.
- “Nothing is stamped without you” has the documented seven-day automatic exception. Ship precise copy rather than an absolute privacy or control promise that contradicts D11.
- An exact replay of a successful confirmation returns the recorded result. A new operation on a logged or upcoming flight returns a state conflict. This satisfies idempotency and the rejection contract together.
- Existing completed flights stay logged. Migration never turns historical flights into a new awaiting queue or silently removes historical stamps.
- Sparse data hides a decorative chart, not a server failure. Loading, empty, filtered empty, error and partial results remain distinct throughout all hooks and screens.
- At 320px, three 104px stamps cannot fit with 16px page gutters. Use two columns below the width needed for three 104px cells and their gaps. At 390px use three columns; retain the 104px minimum.
- Russian and English parity means identical semantic key families. English normally has one/other while Russian has one/few/many/other; compare normalized plural families rather than demanding identical physical suffix sets. Add meaningful Russian forms for every counted family.

### C2. Lifecycle schema and transitions

Proposed additive migration: `db/migrations/0006_flight_lifecycle.sql`. Confirm the next available number at execution. Add constrained fields to flights:

| Field | Contract |
|---|---|
| `lifecycle_state` | `upcoming`, `awaiting`, `logged`; never `draft`. |
| `confirmation_source` | Nullable before logged; `save`, `user`, `automatic`, `legacy` when logged. `legacy` is migration provenance, not a claim of explicit confirmation. |
| `confirmed_at` | Canonical UTC ISO timestamp; unknown historical time may remain null with legacy provenance. |
| `awaiting_after` | UTC instant for the morning-after boundary, computed from departure date and captured member timezone. |
| `auto_confirm_after` | Seven calendar days after the eligibility boundary in that captured timezone. Late sync does not restart the clock. |
| `lifecycle_timezone` | Validated IANA timezone from the member's browser at create/date edit; UTC fallback for old clients. Store it per flight for reproducible cron decisions. |
| `arrival_transit` | Nullable before an explicit connection decision; boolean afterwards. False means visited/left the airport. C3 derives the effective prospective default while nullable; null does not imply country inclusion. |
| `is_upcoming` | Compatibility projection: 1 only for upcoming, 0 for awaiting/logged. New code reads lifecycle state. |

Use a reusable calendar-date helper with tests for DST and positive/negative offsets. Flight `date` remains a date-only departure label and is never converted with `new Date(date)` for presentation. Today counts as a same-day save and logs directly; a date later than today in the captured timezone creates upcoming. An existing upcoming flight becomes awaiting only when local departure date is past, at midnight at the start of the next calendar day. “Morning after” means that next-day boundary, not an arbitrary 09:00 alarm.

| Operation | Result |
|---|---|
| Past/today manual or draft save | Logged, source `save`; return newly pressed countries after publication. |
| Future save | Upcoming; no completed totals, visits or stamps. |
| Due upcoming sync | Awaiting; counts in completed totals and country counts, with pending-only stamp status where applicable. |
| Confirm awaiting | Logged, source `user`; apply submitted connection choices and return new stamps after publication. |
| Auto-confirm due awaiting | Logged, source `automatic`; apply the same validated connection defaults, publish, show no animation. |
| Edit awaiting into the future | Upcoming; remove completed evidence through repair; clear confirmation fields and recompute eligibility. |
| Edit awaiting with a past/today date | Remains awaiting; the arrival question is not answered by “Changed.” Recompute deadlines from the corrected flight date, never from edit time. |
| Edit logged into the future | Upcoming with cleared confirmation fields. Editing a logged past flight keeps its recorded confirmation provenance. |
| “Did not fly” | Client hides the card and defers the existing delete for a 6-second undo window. Closing before submission leaves the flight awaiting. |

Arrival eligibility uses the stored timezone captured from the member, rather than changing when the member travels or another device uses a different timezone. This is an explicit reproducibility choice. Countdown labels use the viewer's current locale/timezone. All clients send a validated timezone on create or date edit; this adds no account timezone setting.

### C3. Country evidence and connections

Keep `visits` as the airport aggregate so airport counts retain their meaning. Add a recomputable country projection, proposed `country_visit_evidence`, generated in the existing revision/publication batch from canonical sources. Store country/date/count/source summaries needed by passport; do not infer country membership from airport aggregates anymore.

- Awaiting and logged flights contribute completed flight/distance/time/airline/aircraft totals. Country totals use the same effective connection policy before and after confirmation; airport totals keep both endpoints.
- A country is pending only when it has awaiting contributions and no logged, legacy, claim or ground-visit evidence. Pending does not increase the pressed-stamp total; the total-country figure includes it with the explicit waiting caption.
- Claims and ground visits remain immediately pressed; legacy evidence remains authoritative until an explicit cleanup action. A confirmation's `newlyStampedCountries` compares pressed evidence before and after, so a pending country can become newly stamped without increasing `countries_count`.
- Airport visits retain both endpoints. A transit decision suppresses the incoming destination country and the matched outgoing origin country. Excluding only the incoming endpoint would silently restore the stamp on the next leg.
- Use the catalog's six-region collection model in Overview, Passport, profile counts and geographic progress. Keep existing historical badge awards. Inspect numeric continent-based eligibility before recomputing and document any changed rule in the lifecycle ADR.
- Do not silently change whether manual claims count toward flight-only leaderboard categories. Preserve the existing category meaning; expose passport collection count separately if it includes claims. Labels must distinguish the two where necessary.

Connection detection is a deterministic chain calculation, without a trips entity. Sort reliable UTC instants first with stable ID ties. Link legs only when arrival airport equals next departure airport, gap is nonnegative and at most 24 hours, and there is no competing equally plausible next leg. A maximal linked chain supplies its start and final country. Exclude endpoints in either of those countries from “third country” suggestions. With missing times, same/next calendar-day matches are candidates labelled as estimated. Ambiguous branches are review-only, not an automatic suppression.

For new awaiting flights, derive one effective arrival policy: explicit member choice first; otherwise an unambiguous qualifying connection defaults to transit; otherwise include the endpoint. Unique date-only same/next-day candidates may use that prospective default but remain visibly labelled estimated; ambiguous branches need explicit review and never trigger automatic suppression. Use this exact policy in queue DTOs, country projection, Overview/Passport and auto-confirm. A default transit country therefore never appears as a pending country merely because `arrival_transit` is null. «Выходил в город» explicitly includes it and can create a pending/pressed country according to lifecycle.

Confirmation validates the submitted candidate revision against current owned flights so a changed/removed connection cannot silently apply stale defaults. Auto-confirm records the effective decision it applied; a subsequent edit follows ordinary explicit country republishing. Legacy logged flights and past-dated direct saves retain their existing endpoint policy until cleanup/user choice. No prospective default retroactively classifies them. Both endpoints of a connection consume the incoming policy, including a matching outgoing leg not yet logged.

Separate candidate generation from writes. The one-time cleanup GET has no side effects. Its action marks selected incoming arrivals transit, republishes and reports actual removed country stamps. A country supported elsewhere remains pressed. Persist a per-account cleanup dismissal/completion marker as a small lifecycle migration field or record, so the banner does not repeat forever.

### C5. Import persistence, streaming and replay

Proposed migration `0007_import_drafts.sql`, following the lifecycle migration:

- `import_batches`: opaque ID, owner, sanitized source label/type, status `processing|review|partial|failed|cancelled|completed`, created/updated/expires timestamps, progress stage, monotonic sequence/revision, structured error code, optional retry timestamp. Expiry is 30 days from creation, visible in review.

Invalid references may remain here until corrected; they never enter flights prematurely.
- `import_conversion_receipts`: owner, draft ID, immutable conversion operation/key, request fingerprint and created flight ID/result. Keep receipts for at least 37 days and beyond any live batch retry window. A deleted converted flight leaves a tombstone receipt until expiry, so replay does not recreate it.
- New owner-scoped confirmation receipts and cleanup marker can live in `0006` or the next migration; the ordering above is conceptual. Use constraints and indexes for owner/state/expiry and per-batch ordinal uniqueness.

Never persist uploaded files, base64, pasted source text, full provider responses or `raw_text` in D1, Durable Object storage, queues, R2, logs or browser storage. Store only extraction fields/confidence and a verified optional bounded row snippet. All new tables participate in the explicit account-deletion cascade; do not rely solely on foreign-key cascade.

Proposed API:

| Endpoint | Contract |
|---|---|
| `POST /api/import/jobs` | Bounded existing parse input plus sanitized source label and submission operation ID. Authenticate/CSRF-check/rate-limit before dispatch. Return batch ID and acceptance only after server ownership is established. |
| `GET /api/import/batches/:id` | Read batch, rows, expiry, status and revision. Scope every query to authenticated owner. Supports refresh/remount. |
| `GET /api/import/batches/:id/events?after=N` | Same-origin authenticated SSE notifications; revision/row IDs only. D1 is authoritative. Reconnect by sequence, or request a fresh batch snapshot when a gap occurs. |

Extract shared bulk-create service code from the existing handler where necessary. Both ordinary `/flights/bulk` and draft confirmation call it. Do not make an internal HTTP round trip or create a second weaker validation path. Preserve existing per-item replay/partial results and deduplicate against the full owner dataset, not the first capped 200-flight page.

Runtime design choice:

1. Add proposed `workers/import/{index.ts,ImportJob.ts,tsconfig.json}` with an owner/batch-named Durable Object, accessed through the architecture-owned same-origin API adapter and service binding. T11 owns job behavior; the architecture owner integrates its Wrangler/binding configuration. The worker has no unauthenticated public import endpoint.
2. Job startup receives source input in memory, records metadata in D1, starts the bounded provider request, then acknowledges acceptance. A duplicate submission cannot start another provider call for the same active batch.
3. Use installed `generateContentStream` with the existing schema and normalization. A small bounded incremental JSON scanner recognizes complete objects in the `flights` array, including strings/escapes/nesting. It never publishes a partial object. Validate and persist each complete row before emitting its revision event. Reconcile ordinals against the completed final JSON envelope.
4. Keep in-flight work attached to the Durable Object rather than to an SSE subscriber. Its pending provider I/O continues after client disconnect. Request a compatibility date at least `2026-10-01` or the documented equivalent flag for this Worker through H5; the architecture owner controls runtime configuration.
5. Persist stages only when true: accepted, recognizing, validating, review-ready. No percentage based on unknown total, fake delay or synthetic “found” row. A stream that finishes with an invalid envelope retains valid rows as partial with a clear warning.
6. Cancel aborts provider work when supported and fences all later writes using batch generation/status. SSE disconnect only unsubscribes. Handle multiple tabs, slow consumers and repeated notifications without duplicate draft rows.
7. A deployment/runtime restart can lose unextracted input because document persistence is deliberately excluded. A bounded processing deadline and reconciliation mark stale jobs interrupted, retain extracted rows and request a reupload for missing results. Navigation alone must not stop the job. Do not promise automatic document recovery across server restarts.
8. Pin limits to existing 10 MiB files, 14 MiB JSON envelope, 100,000 source-text characters and provider timeout unless a measured streaming test justifies a change. Bound output bytes, draft count, event queues and concurrent jobs per owner; return a recoverable limit error rather than exhausting memory.

This transport change is justified by the user-selected scope. Ordinary HTTP Worker `waitUntil` has only a 30-second disconnect extension and is insufficient as the sole job guarantee. The proposed Durable Object design is an inference from the current platform contract and must pass the disconnect test in T11. [Workers context](https://developers.cloudflare.com/workers/runtime-apis/context/), [Durable Object keep-alive compatibility change](https://developers.cloudflare.com/changelog/post/2026-10-01-pending-io-keep-alive/), [Durable Object restart behavior](https://developers.cloudflare.com/durable-objects/concepts/durable-object-lifecycle/).

Structured output supports streaming partial JSON; complete row parsing and persistence are application responsibilities. The installed SDK's type definitions confirm the stream method, while current documentation provides the platform capability. Verify this combination on the configured model before integration. [Google structured output streaming](https://ai.google.dev/gemini-api/docs/generate-content/structured-output), [official JavaScript SDK](https://github.com/googleapis/js-genai).

Do not import issue [#39](https://github.com/indi256s/kuuki/issues/39)'s stale model, caching, two-pass extraction or unverified latency targets into this redesign. Coordinate overlapping work before implementation.

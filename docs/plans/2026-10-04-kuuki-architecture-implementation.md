# Kuuki architecture, performance and UX implementation plan

Goal: Migrate Kuuki incrementally to Next.js App Router on Cloudflare Workers/Static Assets, delivering the Redesign 2.0 experience with truthful data states, preserved accounts and writes, and demonstrated navigation/performance behavior.
Architecture: OpenNext hosts reusable prerendered/prefetched shells and streams request-time, access-checked summaries. D1, Better Auth, the existing domain/recovery functions, TanStack Query for interactive data, Zustand for UI/drafts, and shadcn/Radix remain. Application maps use mapcn + flightcn; MapLibre is their rendering dependency. Shared runtime application-data caching starts disabled.
Success: Existing identities, credentials, privacy and save recovery survive both forward migration and rollback; production-mode workerd proves the exact Next/OpenNext pair and Instant Navigations; retained journeys work in EN/RU and light/dark without false-empty states; before/after evidence demonstrates bounded payloads and lazy heavy assets without claiming unmeasured speedups.
Out of scope: This document grants no execution authority. No application changes, installation, deployment, cloud mutation, paid provider call, resource retirement, commit or push is authorized by the planning request. Database/provider replacement, detailed basemaps, persistent runtime caching and durable parsing are conditional follow-up work.
Constraints: Preserve unrelated shared-checkout work. Use existing Wrangler workflows; do not migrate to `cf` as part of this effort. Preserve atomic canonical-write/dirty-marker batches, per-item idempotency, revision-guarded publication and scheduled recovery. Keep authoritative visibility/session/CSRF checks outside caches. Use the fewest coherent changes; functional/layout checks are the default, and a full visual audit/atlas recapture is separate work unless requested.
Planning basis: The [decision handoff](../audits/2026-10-04-architecture-decisions.md) is authoritative; the [architecture audit](../audits/2026-10-04-architecture-and-services.md), [service research](../research/2026-10-04-services-audit.md), [map research](../research/2026-10-04-maps-options.md), and both [architecture](../audits/2026-10-04-opus-architecture-review.md) and [chart](../audits/2026-10-04-opus-charts-review.md) reviews supply qualified evidence. The independent [UX brief](2026-10-04-redesign-2.0-ux-ui.md), [journey atlas](../user-journeys/README.md), [PRODUCT.md](../../PRODUCT.md), [DESIGN.md](../../DESIGN.md) and [frontend guidance](../FRONTEND_GUIDELINES.md) constrain experience decisions.
Execution profile: primary=gpt-6.1-sol/xhigh (this planning thread only); workers=gpt-6-sol/medium; reviewers=independent-gpt-6-sol/medium; simple-bounded-read-only-lookups=gpt-6-luna/max; exact-profile-attestation=required
Authority evidence: User request of 2026-10-04 authorizes writing only `docs/plans/2026-10-04-kuuki-architecture-implementation.md`. Future execution needs its own authorization; preserve the future primary's current runtime profile unless the user changes it. ### Same-origin coexistence and eventual API port

Keep `apps/web` as the runnable Vite rollback app and add **proposed** `apps/next` (`@kuuki/next`) alongside it. Do not import `App.tsx`, browser-initialized i18n, auth stores or BrowserRouter into Server Components. Extract/reuse only modules actually needed, with explicit server/client boundaries.

W2's initial custom Worker entry dispatches `/api/*` to the generated Pages Functions Worker and other migrated requests to OpenNext. The inspected output of `build:api` exports a Fetch handler accepting request/env/execution context; prove the freshly generated output before relying on this composition. Use the public [custom Worker extension point](https://opennext.js.org/cloudflare/howtos/custom-worker), not patches to generated adapter internals. Missing API routes/methods must return JSON 404/405, never fall into Static Assets/SPA HTML. An explicit API route inventory and rejecting asset fallback protect that boundary. Preserve Request URL, Origin, Cookie, `Idempotency-Key`, request body/signal, execution-context `waitUntil`, statuses and every `Set-Cookie` header.

This avoids a cross-origin browser API, zone-route/DNS assumptions and a mandatory separate hosting migration. If the generated API handler cannot compose safely or exceeds measured limits, W2 is not accepted: choose an explicit same-origin API Worker service binding or port the affected handlers first, then repeat equivalence proof. Do not hide this behind an untested proxy. No cloud resources are created by this plan.

For interim capture, reserve a **proposed** same-origin `/legacy/` namespace. Produce a separate Vite compatibility build with matching asset base and BrowserRouter basename; merge its namespaced output into the Worker asset artifact without overwriting Next assets or the root-path rollback build. The Worker serves `/legacy/*` documents from that build's entry and its real assets by exact path; missing asset requests return 404, never entry HTML. `/api/*` remains at the origin root. Audit hard-coded links/auth redirects for the basename. Next reaches `/legacy/flights` (add/edit), `/legacy/import`, `/legacy/passport` (claims) and `/legacy/settings` (account/privacy writes) by full document navigation until equivalent W4 flows pass. Typed entry parameters select the intended form/owned record and an allowlisted same-origin return route; current modal-local state is not assumed to support deep links. Return uses full navigation so the new read model is fresh. This namespace is a compatibility bridge, not a second public navigation hierarchy.

The compatibility build registers no new root-scope service worker. Existing [Vite PWA configuration](../../apps/web/vite.config.ts) has root navigation fallback and broad JS/CSS runtime caching, so W2 also defines a targeted transition for the already-installed root worker and its owned caches. Preserve the old worker update URL during transition; prove an installed old worker cannot serve Vite HTML for Next documents/RSC/assets or cache personalized responses. Do not assume a fresh browser fixture proves upgrade behavior or clear unrelated origin storage.

Next initial reads call reusable D1 services directly with a fresh request-scoped identity; they do not self-fetch the public origin. Existing Pages endpoints call those same read functions. W4 ports mutation/import adapters behind the stable `/api/*` URLs to Request/Response handlers in Next, moving one family only after equivalence proof and disabling the old family in the dispatcher. Keep the compiled legacy handler available for remaining families. No duplicate handlers may both write; don't construct fictional Pages contexts inside RSC. The final API port may retain thin compatibility handlers in `functions/` for the rollback app until W5's rollback window ends.

### Initial data, revisions and freshness

Proposed shared read contract: `OverviewSummary = { schemaVersion, period, revision, publishedRevision, derivedState, generatedAt, totals, nextFlight, insights, topLists, months, countryIds }`. Limits are explicit: one hero flight, top-five lists and 12 monthly buckets; route geometry/full flight DTOs are excluded. Current names/endpoints remain usable by the Vite client until it migrates; introduce a versioned summary endpoint rather than silently replacing `completedFlights` in its existing response.

Read canonical/published state and all relevant derived rows in one consistent D1 batch/snapshot. When `revision > publishedRevision`, canonical flights may be newer than totals: expose that state and label the published snapshot; never claim a coherent ready revision from unrelated sequential reads. Aggregate period data server-side using current indexes/reference IDs; add an index/materialized projection only if query evidence warrants it. Country/continent definitions follow the explicit product rule, not a new client corpus.

Mutation acknowledgements keep current `derived_state`/`revision` fields and add published revision only additively. A receipt proves canonical acceptance; it does not prove derived publication. Pending/error polling is bounded and generation-guarded as in [derivedStateFeedback](../../apps/web/src/lib/derivedStateFeedback.ts), with a visible delayed state after polling ends and recovery on later entry. A newer published revision satisfies an earlier acknowledgement (`publishedRevision >= acknowledgedRevision`). Failure to publish never turns a committed save into “nothing saved.”

Initially, private/public application data are request-time; personalized HTML/RSC/API responses cannot enter public HTTP/CDN/service-worker caches. Prerender only reusable, non-personalized content and version reference assets by build. Check visibility before every new public response, including metadata, prefetch, search and comparisons. Already delivered browser content cannot be retracted; promise prevention of new disclosure rather than recall.

Conditional runtime caching must authenticate/check visibility **outside** the cached scope and use explicit user/profile, published revision, locale and normalized filters. R2 persistence, separate tag-D1 metadata for on-demand invalidation and a DO queue only for time-based revalidation require isolated bindings and cold/warm/expiry proof. Dropped invalidation must not bypass visibility. Scheduled publication uses fresh revision keys or durable authenticated invalidation delivery; maintenance cannot call `next/cache` directly. `router.refresh()` and server invalidation solve different layers. No invalidation outbox is required for request-time summaries.

## W1: Correct contracts and establish a useful baseline

Objective: The existing app can distinguish error/loading/empty/partial success, produces bounded reusable summaries, and preserves recovery while measurements become available.

Owned writes: [preview admission](../../scripts/check-preview-config.mjs); affected [flight](../../apps/web/src/lib/flights.ts), [profile](../../apps/web/src/lib/profiles.ts), [leaderboard](../../apps/web/src/lib/leaderboard.ts) data functions and their consumers; [DashboardPage](../../apps/web/src/routes/DashboardPage.tsx)/[useDashboardStats](../../apps/web/src/hooks/useDashboardStats.ts); [aircraft hook](../../apps/web/src/hooks/useAircraftEnrichment.ts), enrichment prompt/provider adapters; relevant `functions/api/me`, `functions/api/flights`, tests, maintenance and shared contracts. Proposed summary service `functions/api/_services/overview.ts`, versioned endpoint `functions/api/me/overview.ts`, bounded duplicate-candidate endpoint and aircraft-batch endpoint belong to W1.

Implementation:

1. Remove mandatory absent-KV checks; validate actual production/preview D1 identifiers, missing/invalid/equal IDs, maintenance-binding alignment and explicit environment origins. Preserve the separate live-isolation CI gate. Validate optional cache resources only if later declared. Do not change release readiness variables or enable deployment.
2. Propagate typed transport/server errors; return null only for the contract's real missing/not-found condition, and private-profile shell only for actual private visibility. Add explicit background-failure/last-valid-data presentation. Retry transient reads with a bound; no retry loop on auth, invalid input or provider quota. Keep pending derived data distinct from zero history and leaderboard ineligibility. Add root-level error coverage so boot/provider failures do not escape the route boundary; stop stale-chunk reload loops.
3. Implement the compact Overview read service/DTO above, consumed first by the existing page adapter. Batch independent reads; remove parallel duplicate total reads and full-history favorites work from the fast path. Keep detailed Vite filters functional during coexistence; their bounded server-query path does not force new Overview filters into 2.0. Map route payloads remain separate and deferred. Instrument request count, response bytes, D1 time/rows, summary duration and revision lag.
4. Replace aircraft fan-out with a ≤20-item owner-scoped batch. Validate each item, return accepted/error outcomes by flight ID, commit accepted canonical updates with one dirty marker, derive once, and reconcile every confirmed write even on mixed results. Reuse ordinary edit validation/derived handling; no broad country invalidation caused solely by an aircraft assumption. Historical prompt asks for evidence for the dated flight, labels uncertainty/suggestions, prefers unknown, and does not identify today's route equipment as fact. Set provider deadline below the endpoint/client deadline with finite cancellation/cleanup; distinguish timeout from known failure and avoid automatic paid retries.
5. Duplicate checks submit bounded extracted date/route candidate keys to the full owned history, reusing [single-check](../../functions/api/flights/check-duplicate.ts) semantics and edit exclusion. Do not download the first 1,000 flights or all history. Chunk/json-bind within D1 limits; do not infer “no duplicates” from a failed query. Preserve override and per-item create keys, which are a separate protection from duplicate warnings.

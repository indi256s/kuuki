# Технический аудит Kuuki

Дата: 3 октября 2026 года. Проверен commit `bc897858e7a5b5670a03ba461e3d5d356be100a0`, ветка `main`, и текущее состояние Cloudflare. Рабочее дерево до аудита содержало чужие untracked-файлы `CONTEXT.md`, `docs/agents/`, `docs/plans/phase8-prod-login-handoff.md`. Они сохранены.

## Вывод

Проект собирается, но переход на Cloudflare не завершён для пользователей. В production есть только один аккаунт, нет перелётов и справочников. Локально сохранился перенесённый набор из 26 пользователей и 343 перелётов. Для возвращения старых пользователей нужны перенос данных с сохранением идентификаторов и безопасное восстановление доступа. Старых пользователей удалять нельзя. AI-импорт дополнительно блокируют отсутствующий CSRF-заголовок и отключённая провайдером модель Gemini 2.0 Flash.

Переписывать приложение целиком оснований нет. React-приложение и API уже используют Cloudflare D1, cookie-сессии и собственные обработчики. Основная работа находится в завершении миграции, исправлении нескольких интеграций, согласовании истории поездок и проверках перед выпуском.

Это технический аудит с проверкой исходников, локальными проверками и чтением конфигурации и агрегатов production. Он не является исчерпывающим пентестом. Код приложения, пользователи, пароли и облачные настройки в ходе аудита не изменялись. В отчёт не включены адреса пользователей, хеши паролей и значения секретов.

## Проблемы по приоритету

Приоритеты означают порядок ремонта, а не CVSS: P0 блокирует возвращение пользователей, P1 нужно закрыть до полноценного запуска, P2 исправляется следующим этапом, P3 относится к уборке. У каждой проблемы указан уровень доказательства.

### A01. P0. Production не содержит перенесённых данных и справочников

**Подтверждено Cloudflare API.** В production 1 users, 0 flights, 0 airports_reference, 0 aircraft_reference, 0 badge_definitions. Локально находятся 26 users и 343 flights. Новый код работает с D1 и не читает старые аккаунты из Supabase.

Пустые справочники также мешают серверному вычислению расстояний, visits и badges. Frontend может показывать часть встроенных справочников, поэтому наличие автодополнения не доказывает готовность серверных данных. См. [серверные расчёты](../../functions/api/_services/stats.ts#L48), [API справочника](../../functions/api/reference/airports.ts#L8), [исторический handoff](../plans/phase8-prod-login-handoff.md).

**Исправление:** снять резервную копию текущей production БД, проверить актуальность старого экспорта, определить конфликты единственного нынешнего аккаунта с мигрируемыми, перенести исходные ID и связанные данные, загрузить справочники. Production schema уже существует, но `d1_migrations` пуст: нельзя применять `0001_init.sql` вслепую или пересоздавать базу с пользователем. Сначала сравнить схему и корректно установить migration baseline.

**Приёмка:** совпадение ожидаемых counts и ID, отсутствие FK-нарушений, контрольная сверка данных каждого пользователя. Существующий production аккаунт сохраняется или объединяется по явно согласованному правилу.

### A02. P1. Нет способа восстановить доступ старым пользователям

**Подтверждено исходниками и составом экспорта.** [Миграция](../../scripts/sb-to-d1.ts#L263) записывает `RESET_REQUIRED`; [verifyPassword](../../functions/api/_lib/crypto.ts#L76) такое значение отвергает. Старые парольные хеши не входят в имеющийся экспорт. Эндпоинтов восстановления или смены пароля и почтовой инфраструктуры в проекте нет.

Локально парольные хеши уже заменены [общим тестовым паролем](../../scripts/reset-passwords.ts#L14). Это объясняет `RESET_REQUIRED = 0` локально и не означает готовность production credentials. Нельзя переносить этот общий пароль как рабочий способ входа.

**Исправление:** добавить подтверждение владельца существующего аккаунта и установку персонального пароля. Предпочтительный вариант для небольшого существующего набора: одноразовая ссылка на подтверждённую почту, токен с коротким сроком и однократным использованием, отзыв старых сессий после смены пароля. Если прежний Supabase Auth всё ещё доступен, отдельно оценить временную проверку старого входа для выдачи D1 credentials. Доступность старого сервиса не установлена этим аудитом.

`AUTH_SECRET` привязан к каждому паролю. Версия `v1` записывается, но [проверка](../../functions/api/_lib/crypto.ts#L79) не выбирает secret по версии и не делает rehash-on-login. Не менять действующий secret без стратегии перевыпуска credentials.

**Приёмка:** существующий пользователь возвращается в прежний профиль со всеми перелётами; повторное применение recovery token отвергается; истёкший токен отвергается; чужой пользователь не получает доступ; общий пароль отсутствует.

### A03. P1. Preview подключён к production данным

**Подтверждено актуальной конфигурацией Cloudflare.** Preview и production имеют одинаковые DB и KV bindings; preview всех веток включён. Изменяющий запрос с preview приложения использует рабочую базу. Это риск целостности при проверке веток, даже если текущий маршрут правильно проверяет владельца записи.

**Исправление:** отдельные DB, KV и auth secrets для preview/staging, фиктивные или обезличенные данные. Явно выбрать единственный путь production deploy. Сейчас Pages Git integration и [.github/workflows/ci.yml](../../.github/workflows/ci.yml#L154) могут выпускать код независимо; Pages build не обязан ждать GitHub checks.

[Cloudflare поддерживает отдельные bindings для preview и production](https://developers.cloudflare.com/pages/functions/wrangler-configuration/). Не создавать новые проекты ради перехода на другой CLI: сначала исправить окружения существующего приложения.

**Приёмка:** IDs DB/KV различаются; запись на preview не появляется в production; выпуск идёт только через выбранные обязательные проверки.

### A04. P1. AI-импорт всегда получает CSRF 403 из текущего интерфейса

**Подтверждено исходниками и локальным probe.** [useImport](../../apps/web/src/hooks/useImport.ts#L117) отправляет raw `fetch` без `X-CSRF-Token`. [parse handler](../../functions/api/import/parse.ts#L258) требует этот заголовок и возвращает 403 до вызова Gemini. Cookie браузер отправляет, но одного cookie недостаточно.

**Исправление:** отправлять запрос через общий CSRF-aware [apiClient](../../apps/web/src/lib/apiClient.ts) либо использовать ту же логику заголовка. Не ослаблять серверную защиту.

**Приёмка:** реальный frontend запрос с фиктивным AI backend проходит; отсутствие и несовпадение CSRF token по-прежнему дают 403.

### A05. P1. Продлённая сессия теряет возможность изменения данных

**Подтверждено исходниками и probe cookie headers.** [setSessionCookies](../../functions/api/_lib/authCookies.ts#L18) выдаёт session и CSRF cookie на 30 дней. [Middleware](../../functions/_middleware.ts#L27) и явный [refresh endpoint](../../functions/api/auth/refresh.ts#L26) обновляют только session cookie. После 30 дней активный пользователь может оставаться авторизованным для чтения, но изменения и выход получают CSRF 403.

**Исправление:** согласованно продлевать срок CSRF cookie вместе с session, не заменять его случайно на каждой параллельной операции.

**Приёмка:** с управляемым временем после 31 дня активная сессия продолжает выполнять авторизованную запись и выход; неактивная сессия истекает.

### A06. P1. Middleware добавляет старую сессию после новой при повторном входе

**Подтверждено локальным вызовом middleware с фиктивным D1.** Для старой сессии, требующей ежедневного продления, [middleware](../../functions/_middleware.ts#L29) сначала получает response обработчика, затем добавляет старый session cookie. [signin](../../functions/api/auth/signin.ts#L48) к этому моменту уже установил новый. Проверенный порядок session cookie в ответе: `new, old`. UI сохраняет нового пользователя из JSON; cookie может оставить прежнего. Поведение конкретного браузера с двумя одноимёнными cookie отдельно не проверялось.

**Исправление:** не дописывать продление, если обработчик уже установил или очистил session cookie; отдельно проверить signin, signup, signout и refresh.

**Приёмка:** вход из аккаунта A в B после суток оставляет ровно один session cookie для B, и `/api/auth/me` возвращает B.

### A07. P1. Редактирование меняет семантику перенесённой истории visits

**Подтверждено исходниками и текущей локальной БД.** [PATCH/DELETE flight](../../functions/api/flights/[id].ts#L144) вызывает [rebuildVisitsForUser](../../functions/api/_services/stats.ts#L113), который удаляет visits пользователя и строит их заново из текущих flights. Исторический источник накапливал visits. Из текущих 171 сохранённых visits реконструируются только 156. У 8 пользователей есть 15 visits, которые исчезнут при такой пересборке независимо от конкретного редактируемого маршрута.

Комментарии в начале stats.ts обещают накопительную историю, а реализация пересборки намеренно уменьшает counts после удаления. Это противоречие требований, а не доказательство, что все старые агрегаты были правильными. [Июньское решение](../plans/phase5-to-phase7-handoff.md#L43) сохраняло live oracle именно из-за различий пересчёта.

**Исправление:** определить источник истины. Если исторические посещения должны сохраниться, дать им отдельное происхождение и пересчитывать только visits, полученные из существующих перелётов. Если нужен пересчёт по текущим перелётам, выполнить его как явную миграцию с резервной копией и проверкой ожидаемых изменений. Не замораживать старые ошибочные stats навсегда и не менять их незаметно при первом редактировании.

**Приёмка:** сохранение/редактирование/удаление одного перелёта меняет только согласованные посещения и stats; historical visits не исчезают побочным эффектом.

### A08. P2. Основная запись и производные данные фиксируются раздельно

**Подтверждено порядком операций; отказ D1 не инъецировался.** [Создание flight](../../functions/api/flights/index.ts#L114) фиксирует INSERT, затем последовательно обновляет visits, stats, badges и advanced stats. Ошибка позднего шага возвращает ошибку после сохранения перелёта; повтор может создать дубликат. Аналогично [unclaim country](../../functions/api/passport/claims/[cc]/index.ts#L38) удаляет ground_visits и country_claims двумя отдельными операциями.

**Исправление:** использовать атомарный `db.batch` для связанных SQL-записей там, где это возможно; для многошагового вычисления добавить идемпотентность и явное восстановление незавершённого пересчёта. Для unclaim объединить удаления в batch. D1 batch уже используется в других модулях; новый универсальный transaction framework не нужен.

**Приёмка:** при ошибке удаления claim сохраняются связанные наземные посещения с заметками; при поздней ошибке записи flight не остаются незавершённые производные данные; повтор запроса не создаёт второй flight.

### A09. P2. Смена маршрута сохраняет старое расстояние

**Подтверждено исходниками и локальным probe.** [PATCH](../../functions/api/flights/[id].ts#L92) оставляет прежний `distance_km`, если клиент его не передал; [fillDistanceAndDuration](../../functions/api/_services/stats.ts#L46) тогда не читает новые аэропорты. В probe JFK–LAX сменился на JFK–BOS, но осталось 4372 км вместо примерно 330 км по той же формуле.

Поведение унаследовано от старого trigger, который рассчитывал distance только при NULL. Это существующий дефект редактирования, а не доказанная ошибка самого переноса на D1.

**Исправление:** при смене origin/destination пересчитывать прежние distance/duration, если новые значения не переданы в PATCH. Явно переданное новое значение считать override этого запроса после валидации. Не пытаться определить происхождение старого числа по его величине: отдельного признака ручного ввода в схеме сейчас нет.

**Приёмка:** PATCH только destination меняет flight distance и total distance stats.

### A10. P2. Frontend не обновляет все зависимые данные после изменений

**Подтверждено исходниками.** [useCreateFlight и соседние mutations](../../apps/web/src/hooks/useFlights.ts#L95) обновляют списки и часть stats, но пропускают `dashboardStats`, `flightRoutes`, `passportCountries`, advanced stats и часть user stats. У запросов есть stale time, а refetch при фокусе окна выключен. На открытом экране данные могут оставаться старыми после успешного сохранения.

**Исправление:** общий небольшой список invalidation для связанных flight/geo/stats queries, с учётом userId. Применить его к create/update/delete/bulk/import/sync, не создавать отдельный слой событий.

**Приёмка:** после одного изменения обновляются видимые счётчики, карта, паспорт и advanced stats без перезагрузки.

### A11. P2. Ошибки выхода и экспорта показываются как успех

**Подтверждено исходниками; подавление ошибки выхода закреплено существующим тестом.** [signOut](../../apps/web/src/lib/auth.ts#L58) подавляет HTTP ошибку, store очищает пользователя, но серверная сессия может оставаться живой. [getAllFlights](../../apps/web/src/lib/flights.ts#L326) превращает ошибку загрузки в `[]`; [экспорт](../../apps/web/src/components/settings/DataExportSection.tsx#L37) создаёт пустой CSV, списывает лимит и показывает успех.

**Исправление:** передавать эти ошибки вызывающему коду, подтверждать выход после серверного ответа, не создавать CSV и не списывать лимит при неудачной загрузке. Различать реальный пустой набор и ошибку API.

**Приёмка:** при 500/403/сетевой ошибке пользователь видит ошибку; экспорт не создаёт файл; перезагрузка после успешного выхода не возвращает сессию.

### A12. P1. Рейтинги некому обновлять

**Подтверждено репозиторием и списком Workers текущего аккаунта.** [refreshLeaderboards](../../functions/api/_services/leaderboard.ts#L46) существует, но вызывается только migration script `derive.ts`. Scheduled Worker не реализован; отдельный Kuuki Worker в текущем аккаунте отсутствует. После переноса leaderboard_cache останется снимком, новые flights не изменят места.

**Исправление:** небольшой scheduled Worker с тем же production DB и отдельным staging DB, запускающий существующую функцию. Разделить deployment config и добавить наблюдаемое время последнего успешного обновления. Согласовать live opt-in фильтры `/api/me/rankings` и `/api/leaderboard/total-users` с главным leaderboard API.

**Приёмка:** после изменения stats следующий плановый запуск обновляет позиции; выключившийся из рейтинга пользователь не учитывается в публичных totals; ошибка обновления видна оператору.

### A13. P2. Зелёный CI не проверяет весь проект и не гарантирует выпуск

**Подтверждено workflow.** [Test job](../../.github/workflows/ci.yml#L90) имеет `continue-on-error`; deploy jobs зависят от lint/typecheck/build, но не от test. [Deploy-production](../../.github/workflows/ci.yml#L159) тоже допускает ошибку. Workspace команды не проверяют `functions/` и `scripts/`; backend tests в репозитории не найдены. Migration scripts typecheck сейчас падает на отсутствующем `@types/node`.

**Исправление:** сделать необходимые тесты и deploy errors видимыми обязательными результатами, добавить Functions typecheck и сборку Worker; объявить TypeScript и Node types там, откуда запускаются scripts. Добавить целевые проверки auth, ownership, CRUD consistency и восстановления доступа. Согласовать Node version в CI, локальной среде и README.

[Auto-revert](../../.github/workflows/auto-revert.yml#L33) пытается откатывать commit прямо в main при любой основной CI ошибке. Для failed merge commit команда без `-m` не подходит; глубина истории 2 дополнительно ограничивает откаты. Production deploy failures при текущих настройках до него вообще не доходят. Отделить возврат версии сайта от автоматической правки Git-истории.

**Приёмка:** заведомо упавший backend typecheck/test блокирует deploy; failed deploy даёт failed release; rollback проверен отдельно на staging.

### A14. P2. Lockfile требует обновления и проверки применимости advisories

**Подтверждено текущим npm audit.** Получено 182 advisory records: 2 critical, 80 high, 87 moderate, 13 low по классификации registry. Среди пакетов Vitest 4.0.18, protobufjs 7.5.4, React Router 7.13.0, Vite 6.4.1 и множество транзитивных dev dependencies.

Эти цифры нельзя считать severity приложения. Например, [Vitest advisory](https://github.com/vitest-dev/vitest/security/advisories/GHSA-5xrq-8626-4rwp) касается UI/API server и специальных условий, а здесь запускался `vitest run`. [React Router RCE advisory](https://github.com/remix-run/react-router/security/advisories/GHSA-49rj-9fvp-4h2h) исключает Declarative Mode с BrowserRouter, который использует Kuuki. [protobufjs advisory](https://github.com/protobufjs/protobuf.js/security/advisories/GHSA-xq3m-2v4x-88gg) требует загрузки недоверенных schema/descriptor; maintainer классифицирует его как High, хотя npm audit пометил Critical.

В проверенной Functions esbuild metadata нет файлов модулей protobufjs, Hono, Express, MCP SDK или undici; включена web-сборка Google GenAI. Это снижает применимость перечисленных серверных advisories к этому bundle, но не заменяет разбор всех остальных.

**Исправление:** обновить зависимости небольшими совместимыми группами, начиная с реально используемых runtime packages и инструментов разработки; проверить changelog и lockfile; повторить сборку, тесты и audit. Не применять слепой `audit fix --force` и не создавать набор overrides без проверки совместимости. Минимальные версии из трёх рассмотренных advisories исправляют только соответствующие проблемы, а не весь накопившийся набор.

### A15. P2. Сервер слабо проверяет входные данные перелёта

**Подтверждено исходниками.** [POST flights](../../functions/api/flights/index.ts#L85) проверяет только непустые date/origin/destination; PATCH ещё слабее. Неизвестные коды или некорректная дата проходят дальше к SQL и производным расчётам. Frontend validation не защищает API от прямого запроса.

**Исправление:** валидировать формат и существование даты, нормализовать IATA, проверить аэропорты и поддерживаемые aircraft codes. Общие типы уже существуют; можно добавить небольшой schema validator на границе API. Перед нормализацией двух сохранённых A380 rows проверить ожидаемые изменения статистики.

**Приёмка:** невалидные запросы дают 400 до записи; валидный новый и migrated flight проходят; date не меняет completed/upcoming по ошибочному parsing.

### A16. P1. Импорт вызывает уже отключённую модель

**Подтверждено исходниками и актуальной документацией Google.** [Очистка текста](../../functions/api/import/parse.ts#L27) и [извлечение полей](../../functions/api/import/parse.ts#L133) используют `gemini-2.0-flash`. По [Google deprecations](https://ai.google.dev/gemini-api/docs/deprecations) и [release notes](https://ai.google.dev/gemini-api/docs/changelog) эту модель отключили 1 июня 2026 года. Исправление CSRF само по себе не восстановит импорт. Платный запрос к Google в аудите не выполнялся.

Enrichment отдельно использует `gemini-3-flash-preview`, поэтому нельзя распространять вывод об отключении 2.0 на все AI-вызовы. Его preview-статус всё равно требует явного выбора поддерживаемой production-модели.

**Исправление:** выбрать действующую модель по [исследованию OCR](../research/2026-10-03-ticket-ocr-models.md), вынести model ID в конфигурацию, сохранить JSON schema и серверную проверку полей. Проверить совместимость существующего SDK, image/PDF token costs и limits. Качество не выводится из номера поколения модели; нужен небольшой набор билетов с известными ответами.

**Приёмка:** текст, фото и PDF на действующей модели дают валидные проверенные поля; provider model-not-found отображается как ошибка импорта, а не пустой успешный результат.

## Дополнительные замечания и уборка

- `/dev/reset` включён в [production router](../../apps/web/src/App.tsx#L163), его chunk попал в production build. Страница удаляет все перелёты текущего пользователя после ввода `DELETE`. Endpoint защищён auth, ownership и CSRF, поэтому это не удаление чужих данных. Убрать dev-инструмент из production либо оформить его как явно поддерживаемую функцию настроек с понятным восстановлением.
- Founding User выдаётся всем новым аккаунтам при signup в [users.ts](../../functions/api/_lib/users.ts#L100) и при наличии `beta_invite` в [evaluateBadges](../../functions/api/_services/stats.ts#L306). Это наследованное поведение; определить, должен ли статус оставаться только у исторической группы, и зафиксировать eligibility.
- `rateLimit` использует KV read-modify-write, поэтому не даёт строгой защиты при параллельных запросах. Комментарий про fixed window неточен: TTL задаётся заново каждым `put`. Для реального ограничения попыток входа определить требуемый лимит и использовать подходящий Cloudflare механизм; не считать текущий counter строгой квотой.
- В enrichment размер JSON проверяется по Content-Length. Проверять фактически прочитанные bytes, включая запросы без этого заголовка, до платного AI-вызова.
- CSP в `_headers` имеет режим Report-Only и старый `airlabs.co` в img-src. Проверить фактические origins, настроить получение CSP reports и только после этого включать enforcement. Применение этих заголовков к конкретным Functions responses в production отдельно не проверялось.
- README и TECH_STACK продолжают описывать Supabase backend, setup credentials и команды, которые не соответствуют текущему приложению. `scripts/enrich-existing-flights.ts` использует Supabase SDK, отсутствующий в manifests. Архивировать этот скрипт или переписать на D1 только при реальной необходимости; старые migrations сохранить как историю до завершения переноса.
- Старые `VITE_SUPABASE_*` переменные остаются в production. После проверки переноса удалить неиспользуемые bindings и отдельно проверить доступность старого Supabase/RLS. Значения этих переменных и текущие права старого сервиса не проверялись.
- Исторические документы и untracked handoffs отражают разные этапы. Нужен один актуальный runbook восстановления и выпуска вместо указаний из разных июньских сессий.

## Порядок работ

1. **Подготовить сохранность данных.** Сохранить текущую production БД и имеющийся экспорт; установить актуальный источник; сравнить схемы и конфликты accounts; сформулировать семантику исторических visits. Не удалять пользователей или production DB.
2. **Исправить код до переноса.** Закрыть CSRF import, заменить отключённую AI-модель, исправить session-cookie ошибки, подавление signout/export ошибок, distance/cache bugs и dev reset. Добавить небольшие проверки реальных сценариев, включая два фиктивных пользователя и истечение cookie.
3. **Вернуть доступ прежним пользователям.** Реализовать recovery/login enablement с подтверждением владельца и персональными credentials, сохраняя старый user_id. Не копировать общий локальный пароль и не менять pepper вслепую.
4. **Разделить окружения и выпуск.** Отдельные DB/KV/secrets; один путь deploy; обязательные Functions/typecheck/tests; исправить воспроизводимость migration scripts; обновить зависимости.
5. **Проверить перенос на staging.** Counts, FK closure, прежние user IDs, credential reset, два изолированных пользователя, редактирование одного flight, passport, stats, export и cron. Проверить rollback на резервной копии.
6. **Выполнить production cutover после отдельной авторизации.** Свежий экспорт при необходимости, сохранение текущего аккаунта, baseline migrations, seed, данные, credentials, cron, проверка на реальном Cloudflare runtime. После подтверждения убрать старые Supabase интеграции.

Работы 1–5 можно конкретизировать без production изменений. Production перенос, отправка recovery сообщений и deploy требуют явного разрешения на соответствующие действия. В этом аудите эти действия не выполнялись.

## Покрытие и ограничения

Проверены структура monorepo и зависимости, текущие настройки Cloudflare и CI, auth API и frontend integration, основные маршруты flights/profiles/passport/import/enrich/stats/badges/leaderboard, схема D1, migration scripts и исторические handoffs. Три независимых разбора auth/backend/frontend сверены главным агентом с исходниками и доступными проверками.

Не выполнялись входы от имени реальных пользователей, изменения production, платные вызовы Gemini, браузерный E2E и визуальная проверка, нагрузочный тест, проверка текущего Supabase и почтовой доставки, полная ревизия всех 182 advisories. Проходящие unit tests и сборки не устанавливают работоспособность этих непроверенных сценариев. Июньские staging E2E не считаются актуальным доказательством нынешних окружений.

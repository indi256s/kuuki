# ADR 0009: Server code decisions

- **Status:** Accepted, 21 November 2026.
- **Source:** decisions that lived as code comments until the comment ban (`scripts/comments.mjs`); each entry names the symbol it governs.

## Context

A lint rule now bans comments in the codebase. The server code (`functions/`, `workers/`, `db/scripts/`) carried comments that were not restatements of the code but the only record of why a statement is shaped the way it is: platform limits, security trade-offs, replay and fencing rules, and parity quirks inherited from the Supabase port. Those reasons cannot be expressed in the code itself, so they are recorded here, grouped by subsystem and keyed by symbol, and ADRs 0001 to 0008 remain the authority wherever they already cover a decision.

## Decision

### Authentication, sessions and CSRF

- **`requireCsrf`** ([auth.ts](../../functions/api/_lib/auth.ts)) — auth moved from bearer tokens (CSRF-immune) to an httpOnly cookie, which reintroduced CSRF risk. The defence is layered: cross-site `Origin` is rejected on mutations, and a double-submit token (a non-httpOnly `kuuki_csrf` cookie that JS echoes in the `X-CSRF-Token` header) is required, because an attacker page cannot read the cookie to forge the header.
- **`requireSameOrigin`** ([auth.ts](../../functions/api/_lib/auth.ts)) — pre-auth endpoints (signup, signin) use the same-origin check alone because no CSRF cookie exists before login. A missing `Origin` is allowed: a non-browser client such as curl carries no ambient cookie, so there is no CSRF risk.
- **`requireStrictSameOrigin`** ([auth.ts](../../functions/api/_lib/auth.ts)) — activation requires an explicit browser `Origin` and an exact scheme/host/port match.
- **`onRequest`** ([_middleware.ts](../../functions/_middleware.ts)) — recovery and OAuth routes own the authentication transition, and session-replacement routes own their cookie writes, so the middleware never refreshes or renews an old identity on them.
- **`createAuth`** ([betterAuth.ts](../../functions/api/_lib/betterAuth.ts)) — Google is trusted to verify only Gmail/Googlemail addresses or Workspace accounts (`hd` set), not third-party mailboxes. Google sign-in proves ownership of an unclaimed migrated journal; accounts with an existing password or provider identity keep the local verification gate. User, profile and credential are provisioned in one D1 batch so signup is atomic. Sign-in requests only the stable provider identity, not reusable Google API credentials. Rate limiting goes through Kuuki's atomic D1-backed per-IP counters. The session is read together with its user in one joined query, not two D1 round trips on every authenticated request.
- **`onRequest`** ([auth/[[path]].ts](../../functions/api/auth/[[path]].ts)) — Better Auth client endpoints are routed through Kuuki's own signin/signup/signout handlers so provisioning keeps the atomic D1 batch. A late response that renews a replaced Better Auth cookie must not restore the old identity, so the previous session is checked before the renewal is honoured.
- **`onRequestPost`** ([auth/refresh.ts](../../functions/api/auth/refresh.ts)) — refresh only extends a still-valid session and cannot revive an expired one. The client's "on 401, refresh once, retry" must therefore treat a 401 here as a hard logout, or it loops forever.
- **`onRequestPost`** ([auth/signin.ts](../../functions/api/auth/signin.ts)) — an unknown account runs `dummyVerify` so its timing matches a wrong password. Better Auth's own 401 body differs from the unknown-email one and would reveal that the account exists, so Kuuki's body is returned for both.
- **`onRequestPost`** ([auth/continue.ts](../../functions/api/auth/continue.ts)) — `POST /api/auth/continue` is the one-form card's first step (email + password). A verified password issues a session with the sign-in body, an unknown email answers `{ next: 'create' }`, anything else is 401. Every call verifies a password (Better Auth for a known account, `dummyVerify` for an unknown one) so timing does not reveal existence. The account-existence leak (security finding 8, low) is accepted: `create` versus 401 reveals registration, sign-up already does through 409 `EMAIL_TAKEN`, and email-verify-first was rejected because it forces an app switch. It is bounded per IP: every call spends the `signin:` bucket and every `create` answer also spends `signup:` (10 per hour). Once `signup:` is spent, every unverified outcome (unknown email, wrong password, `RESET_REQUIRED`) gets the same 429; a verified password still signs in. The check is a non-consuming peek, so only `create` answers spend the bucket. The route returns its own 401 body because Better Auth's differs and `RESET_REQUIRED` accounts have no credential row.
- **`onRequestPost`** ([auth/signup.ts](../../functions/api/auth/signup.ts)) — the distinct 409 `EMAIL_TAKEN` is an accepted account-enumeration trade-off (security finding 8, low). The privacy-preserving fix (accept-then-verify by email) needs transactional email infrastructure the app lacks; the leak is per-IP rate-limited, low-value here, and sign-in is separately hardened (`dummyVerify` plus generic `INVALID_CREDENTIALS`). Secrets and configuration are validated through `createAuth` before any account row is written.
- **`onRequestDelete`** ([auth/account.ts](../../functions/api/auth/account.ts)) — account deletion re-authenticates on the server with the current password, because the client dialog is not trusted (security finding: delete re-auth was client-side only). Password checks are limited to five per account per hour so a stolen session cannot become a password oracle. All owned rows are deleted explicitly in one batch (FK cascade is not guaranteed); deleting the sessions rows revokes every session. The durable D1 delete fence commits first and only then are live import jobs aborted, since aborting providers cannot restore deleted rows.
- **`hashPassword`** ([crypto.ts](../../functions/api/_lib/crypto.ts)) — passwords are PBKDF2-HMAC-SHA256 over an HMAC-SHA256-peppered password (`AUTH_SECRET` as the key), so a DB dump without `AUTH_SECRET` cannot be brute-forced. The stored format is self-describing, `pbkdf2$<pepperVersion>$sha256$<iterations>$<salt>$<hash>`, so parameters can evolve. The pepper version (`v1`) is reserved so that `AUTH_SECRET` can later rotate without bricking logins (verify old versions with the old secret, then rehash). Neither rotation nor rehash-on-login exists yet: `verifyPassword` accepts only `v1` with the current secret, so changing `AUTH_SECRET` today fails every stored password.
- **`PBKDF2_ITERATIONS`** ([crypto.ts](../../functions/api/_lib/crypto.ts)) — must stay at or below 100,000. Workers' `crypto.subtle` throws `NotSupportedError` above that, while Node (`wrangler pages dev`, Vitest) allows more: 210k passed every local gate and returned 500 on the deployed runtime. `verifyPassword` reads the iteration count from each stored hash, so legacy hashes had to be re-derived at 100k or less for signin to work on Workers.
- **`pepper`** ([crypto.ts](../../functions/api/_lib/crypto.ts)) — fails closed on a missing `AUTH_SECRET`; HMAC with the literal string "undefined" would silently collapse the pepper for every user.
- **`dummyVerify`** ([crypto.ts](../../functions/api/_lib/crypto.ts)) — burns roughly the same time as a real verify for unknown emails, to prevent account enumeration through response time on sign-in.
- **`corsHeaders`** ([cors.ts](../../functions/api/_lib/cors.ts)) — import, enrich and search were public with `Access-Control-Allow-Origin: *`, which is illegal once credentials are sent. The configured `PAGES_ORIGIN` is reflected with credentials allowed and `X-CSRF-Token` among the allowed headers (the double-submit check). The request `Origin` is echoed only when it equals `PAGES_ORIGIN`; otherwise the configured origin is advertised so a mismatch is visible rather than silently `*`. On a same-origin deployment CORS is mostly moot; tightening is defence in depth and a prerequisite for sending the session cookie.
- **`parsePassword`** ([users.ts](../../functions/api/_lib/users.ts)) — a new password needs 8 or more characters, a current one only needs to be present; both are capped at 1024 to bound hashing cost.
- **`accountPhase`, `unclaimedSql`, `activeSql`** ([users.ts](../../functions/api/_lib/users.ts)) — the `RESET_REQUIRED` sentinel is a fixed literal, never user input, so the SQL fragments over `password_hash` are safe to inline.
- **`gateActivationHost`** ([hostGate.ts](../../functions/api/_lib/hostGate.ts)) — the sign-in return redirect (`/?mode=signin`) resolves to the card's password-saved notice. `mode=signin` stays so a legacy rollback still opens sign-in, and the empty fragment stops the browser carrying a token fragment across.
- **`gateRequest`** ([workerBoundary.ts](../../functions/api/_lib/workerBoundary.ts)) — a synchronous gate shared by Worker and Pages, run before assets, API or sessions. The activation host is constrained to its three assets plus its completion endpoint, and a maintenance hold still blocks that API before it reaches D1.
- **`MAINTENANCE_MODE`** ([env.d.ts](../../functions/env.d.ts)) — `'true'` blocks API access before any session or database work.
- **`isUserAnalyticsAdmin`** ([userAnalyticsAccess.ts](../../functions/api/_lib/userAnalyticsAccess.ts)) — exactly one configured account owns analytics; malformed or absent configuration denies access.

### Activation and password recovery

- **`activationEmailKey`** ([activation.ts](../../functions/api/_lib/activation.ts)) — the rate-limit key is an HMAC of the normalized email, so the email itself is never stored in the rate-limit table.
- **`requestActivation`** ([activation.ts](../../functions/api/_lib/activation.ts)) — only unclaimed accounts receive a link, and callers always return the same public result for unknown, active and delivery-failed accounts, so account existence cannot be enumerated. Links target extensionless URLs because Pages redirects `.html` assets to the extensionless URL.
- **`completeActivation`** ([activation.ts](../../functions/api/_lib/activation.ts)) — the claim, credential update and token revocation are one D1 transaction.
- **`configuredActivationOrigin`** ([activationSender.ts](../../functions/api/_lib/activationSender.ts)) — activation uses a dedicated static host kept separate from the main application's origin.
- **`configuredMailSender`** ([activationSender.ts](../../functions/api/_lib/activationSender.ts)) — native Cloudflare sends cannot be cancelled, so an issued link is invalidated only after the send is acknowledged. Fetches use `redirect` `manual` or `follow` only (workerd supports nothing else), and `!response.ok` rejects redirects. Provider bodies and transport errors can contain addresses, links or credentials, so they are never logged; only the event, purpose and a fixed failure code are.
- **`configuredRecoveryOrigin`** ([passwordRecovery.ts](../../functions/api/_lib/passwordRecovery.ts)) — recovery links go only to the main app origin; activation has its own isolated host.
- **`completePasswordRecovery`** ([passwordRecovery.ts](../../functions/api/_lib/passwordRecovery.ts)) — the D1 batch is atomic, and every mutation is additionally guarded against a lost claim.
- **`onRequestPost`** ([auth/activation/request.ts](../../functions/api/auth/activation/request.ts)) — configuration is checked before any lookup so all account states fail identically. Lookup and delivery run in `context.waitUntil`, outside the account-dependent response path; Pages keeps the task alive after the generic response has returned, and failures are logged without detail.
- **`onRequestPost`** ([auth/password-reset/request.ts](../../functions/api/auth/password-reset/request.ts)) — sender configuration is checked before account lookup so the public result stays generic.
- **`onRequestPost`** ([auth/link/request.ts](../../functions/api/auth/link/request.ts)) — the single "get back in" link always returns the generic `{ ok: true }`; the lookup that picks the activation or reset email runs in the background. Every configuration check runs before any lookup so the 503 never depends on account state, and each helper re-checks account state so a stale choice cannot send the wrong link.

### Privacy and public views

- **`toPublicProfile`** ([profiles.ts](../../functions/api/_lib/profiles.ts)) — public responses use a strict column allowlist; `gemini_api_key`, `home_airport`, `locale` and other private fields must never leave through public endpoints.
- **`toPublicStats`** ([stats.ts](../../functions/api/_lib/stats.ts)) — a public profile and its owner preview show totals only (ADR 0007), never the member id or `updated_at`, which would reveal when the member was last active.
- **`toLeaderboardEntry`** ([leaderboard.ts](../../functions/api/_lib/leaderboard.ts)) — `user_id` stays on cached entries so the client can highlight the current user. The cache holds only public, opted-in users (see `refreshLeaderboards` for the sky and ground gates), so it is not a privacy leak. `metadata` is JSON stored as TEXT and is flattened onto the entry.
- **`toOwnFlight`** ([flights.ts](../../functions/api/_lib/flights.ts)) — a strict allowlist: it drops `user_id` (always the requester) and `aircraft_lookup_attempts` (a D1-only enrichment counter never present in the Supabase types the frontend was generated from), and returns `is_upcoming` as a boolean rather than SQLite's 0/1.
- **`runHandler`** ([http.ts](../../functions/api/_lib/http.ts)) — database and provider error messages can contain user input or payload fragments, so a 500 never echoes them.
- **`onRequestGet`** ([profiles/[id].ts](../../functions/api/profiles/[id].ts)) — private profiles return 404 to other users so their existence is not leaked; only `is_public` profiles expose the public view.
- **`onRequestGet`** ([profiles/search.ts](../../functions/api/profiles/search.ts)) — search returns only public profiles, only through the public DTO allowlist, needs `q` of at least 2 characters, and escapes LIKE metacharacters so a literal substring is matched.
- **`readPublicProfile`** ([publicProfiles.ts](../../functions/api/_services/publicProfiles.ts)) — visibility is checked on every read, before any derived data is fetched. Profile stamps exclude hidden countries and carry codes only (no dates, counts, sources, claims or ground visits). Scope `flights` shows flight countries (the `countries_count` set) whose airports are in the public route set, so the profile names no country the public Overview globe does not already show; scope `all` shows every pressed country, never pending ones. If the owner changed `passport_publication` during the read, the narrowest projection is used, so a narrowed scope never returns the wider set it replaced.
- **`readPublicOverview`** ([publicOverview.ts](../../functions/api/_services/publicOverview.ts)) — visibility and section consent are rechecked after the private read, as `publicProfiles` does, to close a visibility race.
- **`READ_GATE`** ([publicLeaderboard.ts](../../functions/api/_services/publicLeaderboard.ts)) — consent is rechecked live on cached rows so a member who leaves between rebuilds disappears at once. Sky rows keep the five-flight gate; ground rows need all countries published (ADR 0007 refinement) and three completed journeys, so deleting one hides the member before the next rebuild.
- **`VISIBLE_BOARD`** ([publicLeaderboard.ts](../../functions/api/_services/publicLeaderboard.ts)) — ranks the live eligible set before pagination or selecting one member, so places and percentiles reflect the participants visitors can currently see while cached values stay as published. The viewer's own rows are read without the live gate so a pending viewer still sees the last published place.
- **`onRequestGet`** ([me/overview/share.png.ts](../../functions/api/me/overview/share.png.ts)) — the share-card accent is the owner's stored `theme_color`; no request parameter can supply a colour.
- **`resolveShareAccent`** ([overviewShareCard.ts](../../functions/api/_services/overviewShareCard.ts)) — stored `theme_color` may still hold pre-v1 accent names (new writes store canonical names only); `recognizeAccentKey` normalizes them and unknown or missing values fall back to `shu`. The static share-card fixture stays DOM-free (a plain SVG string); the application dial owns radial rendering.
- **`onRequestPatch`** ([profiles/me.ts](../../functions/api/profiles/me.ts)) — `avatar_url` is accepted only as `null` (clear): avatar characters replaced photo URLs, and a remote URL would make every viewer fetch a host the member chose. `null` still clears for earlier clients. Only canonical accent names are stored in `theme_color`; retired names are mapped by readers, never written. `username_derived` is a request flag, never stored: the client derived `username` from the name, so collisions get a silent numeric suffix. A lazily derived username is written with `COALESCE(username, ?)` so it never replaces an address another request saved since the read. `show_on_leaderboards` changes are picked up by the cron rebuild, so the PATCH must not refresh leaderboards inline. Username uniqueness is case-insensitive.

### D1 batches, limits and replay

- **`assertRows`** ([d1.ts](../../functions/api/_lib/d1.ts)) — fails loudly when D1 reports an unsuccessful or partial read instead of rendering empty rows.
- **`nowIso`, `normalizeIso`** ([time.ts](../../functions/api/_lib/time.ts)) — every timestamp written to D1, new rows and imported Supabase rows alike, uses the canonical `Date.prototype.toISOString()` form (`YYYY-MM-DDTHH:MM:SS.sssZ`: UTC, millisecond precision, `T` and `Z`). SQLite stores text, and mixing in Postgres' `2026-06-20 10:00:00+00` silently breaks lexicographic ordering, `ORDER BY claimed_at`, sliding sessions and `expires_at > ?` comparisons.
- **`rateLimit`, `rateLimitExhausted`** ([ratelimit.ts](../../functions/api/_lib/ratelimit.ts)) — fixed-window counters are one SQLite UPSERT, so parallel requests cannot lose increments. All callers share `auth_rate_limits`, so each key starts with its route prefix (`signin:`, `signup:`, `import-parse:`, `import-enrich:`, ...). `rateLimitExhausted` is a read-only check that consumes nothing.
- **`deleteUserCascade`** ([users.ts](../../functions/api/_lib/users.ts)) — deletes every owned row, then the profile and user rows, in one `db.batch()`, children before parents: D1's FK `ON DELETE CASCADE` is not guaranteed on every path (see the schema header), and a failure must roll back instead of leaving a half-deleted account. ADR 0001 section 6: drafts, receipts and evidence go first, then the flights they point at; ADR 0008: Flighty history rows (private source cells), then their runs. Live import jobs are captured in the same transaction as their deletion fence, including racing submissions.
- **`createUserWithProfile`** ([users.ts](../../functions/api/_lib/users.ts)) — ports Supabase `handle_new_user`: creates the auth user and profile in one batch, with no username and no `user_stats` row (that is created lazily by derived-state repair). Founding badges already earned by historical users are untouched; new signups receive none.
- **`MAX_FILTER_VALUES`** ([flightQuery.ts](../../functions/api/_lib/flightQuery.ts)) — multi-value filters are capped at 25 so an `IN` clause cannot exceed D1's ~100 bound-variable limit (uncapped arrays were a self-DoS). Overview binds the filtered selection once in a CTE so three 25-code filters stay under the limit instead of doubling their placeholders.
- **`WRITE_SLICE`** ([historyImport.ts](../../functions/api/_services/historyImport.ts)) — bulk `UPDATE ... FROM json_each` statements are cut to 400 rows to stay under D1's bound-parameter size.
- **`buildSeedSql`** ([generate-seed.ts](../../db/scripts/generate-seed.ts)) — seed INSERTs are chunked at `floor(100 / numCols)` rows because of D1's 100 placeholder/value limit.
- **`genAircraft`** ([generate-seed.ts](../../db/scripts/generate-seed.ts)) — the seed dedups aircraft on `icao`, keeping the first row and dropping the second (the duplicate `E135` drops `RJ140`, keeping `RJ135`), to mirror `packages/data` row for row.
- **`validate`** ([generate-seed.ts](../../db/scripts/generate-seed.ts)) — a hard assertion that no flight references `E135`: both source `E135` rows share the icao and the kept row is `RJ135`, so no flight using `E135` proves the dedup cannot orphan anything. The wider survey of flight `aircraft_icao` values absent from the reference set is informational, not a seed failure: those are pre-existing live data-quality issues for the flights import, not for the reference seed, which must mirror `packages/data`.
- **`readJson`** ([http.ts](../../functions/api/_lib/http.ts)) — the 128 KB default (`DEFAULT_MAX_JSON_BYTES`) covers the largest ordinary body (a 10,000-id bulk delete is about 110 KB); larger callers pass `maxBytes`. Bytes are counted from the stream itself because `Content-Length` can be absent or false, and a body over the limit throws a 413 `HttpError`. Empty or invalid JSON returns `null`.
- **`decodedBase64Size`** ([import/_body.ts](../../functions/api/import/_body.ts)) — the validating regex stays flat: repeating quartet groups can exhaust the stack on a valid 10 MiB file. Padding is allowed only in the final quartet.
- **`bulkDeleteRequest`** ([flights/bulk-delete.ts](../../functions/api/flights/bulk-delete.ts)) — ids are chunked into batched DELETEs because D1 caps bound variables per statement.
- **`onRequestPost`** ([flights/bulk.ts](../../functions/api/flights/bulk.ts)) — the body limit is 64 KB: a full legitimate item is under 1 KB, so `FLIGHT_BULK_CREATE_MAX` items fit with room to spare. The same reasoning gives 64 KB for batch confirm ([import/batches/[id]/confirm.ts](../../functions/api/import/batches/[id]/confirm.ts)), where an item is about 150 bytes.

### Receipts, fencing and idempotency

- **`freezeResult`** ([receipts.ts](../../functions/api/_services/receipts.ts)) — an operation's outcome is recorded once, by whoever gets there first; every caller returns what was recorded.
- **`confirmFlights`** ([confirmation.ts](../../functions/api/_services/confirmation.ts)) — ADR 0001 section 5 (C4). Confirmation is receipt-first: a known operation id is answered from its receipt before anything else is validated, so a replay depends neither on the flights still existing nor on a fresh candidate token. One D1 batch (one transaction) holds (1) the receipt insert (`complete 0`, expected N; a duplicate operation id aborts the batch), (2) the guarded flight `UPDATE` (awaiting only, revision guard), (3) `UPDATE receipt SET applied_count = changes(), complete = 1`, whose `CHECK (complete = 0 OR applied = expected)` aborts the batch when any flight was lost to another writer, and (4) the dirty mark. `changes()` counts only the direct UPDATE, never trigger writes, unlike D1's `meta.changes`. The publication repair runs after commit; when it fails the response says `derivedState: 'pending'` and the receipt keeps no outcome, and the next replay repairs, freezes the outcome once and returns it without applying anything twice.
- **`confirmFlights` before-set** ([confirmation.ts](../../functions/api/_services/confirmation.ts)) — the "before" set needs a published, current projection and is repaired first when it is not. If that repair fails the confirmation still proceeds and `newlyStampedCountries` is reported as unknown, not guessed.
- **`planConfirmation`** ([confirmation.ts](../../functions/api/_services/confirmation.ts)) — one request reports one kind of problem, by precedence: unknown or foreign flight (404, indistinguishable), flights not awaiting (409 `STATE_CONFLICT` with a cause per flight), a connection changed since the member looked (409 `CANDIDATES_CHANGED`), then an arrival decision the connection cannot support (400).
- **`onRequestPost`** ([flights/confirm.ts](../../functions/api/flights/confirm.ts)) — all or nothing; replaying an `operationId` returns the recorded outcome, and reusing it with different decisions is 409.
- **`applyGroundCommand`** ([groundJourneys.ts](../../functions/api/_services/groundJourneys.ts)) — receipt-first, one D1 batch each: session and CSRF, then static command shape and digest (no resource reads), then the owner's receipt for the operation key, and only for a new command the current state. The batch is (1) receipt insert (`complete 0`, `applied 0`, fresh nonce; a duplicate key aborts), (2) parent compare-and-set (insert, update or tombstone), (3) `UPDATE receipt SET applied = changes()` right after the CAS and never carried further, (4) child DELETE/INSERT guarded by "receipt of this nonce is applied and open" plus parent live, (5) the dirty increment guarded the same way, (6) `complete = 1`, whose `CHECK (complete = 0 OR applied = 1)` aborts the whole batch when the CAS matched nothing. A lost CAS, even on a journey without children, commits nothing: no receipt, no dirty revision. Child statements check their own receipt guard and the parent, never `changes()`. A duplicate key, a lost CAS or a colliding child id rolls the batch back whole and the command re-reads; a publication failure is not a save failure (the receipt is committed and readiness is reported honestly). A tombstone or any existing journey id, another owner's included, is never reused; manual places must be the owner's and child ids must not belong to another journey (primary keys are global).
- **`createFlightStatements`** ([flightCreate.ts](../../functions/api/_services/flightCreate.ts)) — ADR 0001 section 6. `POST /api/flights`, `POST /api/flights/bulk` and draft conversion share one path: one validation (`parseFlightBodies`), one ledger/receipt scheme, no internal HTTP round trip. A plain create is ledger insert, conditional flight insert, ledger link; a conversion adds a guard on the first statement and two statements after the link (draft flip and conversion receipt), so every statement is gated on this batch's own previous write and the chain is all-or-nothing per item. `timezone` is request context (ADR 0001 section 1): it picks lifecycle state and deadlines but stays outside `FlightInput`, so it never enters the idempotency digest. With a guard, stale, converted or unacknowledged drafts write nothing (ADR 0001 section 6 step 4); a history guard does the same for a reviewed Flighty row in an open run of the same generation and carries its trusted timing (ADR 0008, built only after the server re-maps the row, never from a request body).
- **`conversionStatements`** ([flightCreate.ts](../../functions/api/_services/flightCreate.ts)) — the draft flip stays gated on the version and `changes() = 1` from the link; a ledger `UPDATE` does not change `last_insert_rowid()`, so it still names the flight this batch inserted. The conversion receipt takes its flight id only from the draft this batch converted, and its no-target `ON CONFLICT` covers both the key and the draft uniqueness (neither conflict is reachable after the guards).
- **`bulkCreate`** ([flightCreate.ts](../../functions/api/_services/flightCreate.ts)) — up to `FLIGHT_BULK_CREATE_MAX` flights, each under its own idempotency key and validated independently; accepted flights and receipts commit in one D1 batch with one dirty mark, then derived state is repaired once (`derived` is null when nothing was accepted). For a conversion item `created` means this batch inserted the flight and converted the draft; any other outcome must be classified by the caller from conversion receipts, because `replayed` only says the key had a ledger row. The dirty mark is unconditional: `changes()` only sees the last item, and a pure replay just repairs again.
- **`confirmBatch`** ([importConversion.ts](../../functions/api/_services/importConversion.ts)) — ADR 0001 section 6 (C5), `POST /api/import/batches/:id/confirm`. Receipt-first, then shared `bulkCreate` with one conversion chain per item: (1) a conversion receipt by key and by draft answers a replay before any batch check, so it survives batch expiry and deletion (receipts are tombstones kept 37 days); (2) a ledger row without a conversion receipt for the key means the key was used by something else; (3) otherwise the batch must exist and be unexpired (with replays in the same request the failure is per item so they are still delivered); (4) ledger insert (guarded on the draft), flight insert, ledger link, draft flip and receipt run in one D1 batch, with the batch completion in the same transaction so a conversion never commits without it (a receipt-only replay would never get another chance to complete the batch); (5) every attempted item is classified from what the database now holds, never from the batch's own results. A moved version or a row past review writes nothing, and step 5 tells "just converted elsewhere" from "stale".
- **`completionStatement`** ([importConversion.ts](../../functions/api/_services/importConversion.ts)) — advances the batch sequence and completes the batch once no `review` row is left, but only when one of the keys now has a receipt in this batch. Step 1 already answered every key that had one, so that receipt was written by this transaction (or by a concurrent request with the same key, which at worst advances the sequence once more). It runs after the item chains in the same batch. A Quick Add row dated today or earlier needs the member's own "I flew it"; a future date converts as upcoming.
- **`persistDraftRows`** ([importDrafts.ts](../../functions/api/_services/importDrafts.ts)) — ADR 0001 section 6 "Deletion fence". The drafts and the batch finalization are one D1 batch where every statement is `... WHERE EXISTS (batch still processing, same generation)`, so after cancel (generation + 1), discard, the maintenance sweep or account deletion a late write matches nothing and a half-written batch cannot exist. `BatchFence.generation` is the writer's ownership token that all four end.
- **`persistDraftVerification`** ([importDrafts.ts](../../functions/api/_services/importDrafts.ts)) — only untouched drafts accept a checker result, because a member patch always increments the version; checker output never overwrites member edits.
- **`createProcessingBatch`** ([importDrafts.ts](../../functions/api/_services/importDrafts.ts)) — inserts a `processing` batch unless the owner is at a limit, in one statement, so two concurrent requests cannot both pass the open-batch limit. A replayed submission operation id inserts nothing.
- **`mergeFields`** ([importDrafts.ts](../../functions/api/_services/importDrafts.ts)) — syntax is the flight validator's (`validateFlightInput`), so a draft holds only what a flight could hold shape-wise, but reference existence is not checked: an unknown airport stays a correctable draft and is refused at conversion, never bypassed. `null` or `''` clears an optional field.
- **`patchDraft`** ([importDrafts.ts](../../functions/api/_services/importDrafts.ts)) — the flown confirmation is the member's answer, not a correction, so it never marks a draft `edited`, and it can only be set through the draft patch `flownConfirmed`, never through `fields`, so a member cannot bypass the Quick Add confirmation. A new date voids a prior "I flew it" unless the same patch answers again. The batch sequence/status update rides in the same D1 batch as the draft update, gated on `changes() = 1` (`BATCH_STATUS_AFTER_DRAFTS`), so batch state never diverges from its drafts. A stale version or a converted row is 409 `DRAFT_VERSION_CONFLICT` with the current draft, so another tab's edit is never overwritten ([import/drafts/[id].ts](../../functions/api/import/drafts/[id].ts)).
- **`BATCH_STATUS_AFTER_DRAFTS`** ([importDrafts.ts](../../functions/api/_services/importDrafts.ts)) — recomputes batch status in SQL: no `review` row left completes it; a row coming back (an un-dismiss) reopens it, as `partial` when the reading recorded an error (only partial reads keep an `error_code`); `processing`, `failed` and `cancelled` keep their status.
- **`discardBatch`** ([importDrafts.ts](../../functions/api/_services/importDrafts.ts)) — deletes the drafts, then the batch, explicitly in one D1 batch; it never relies on the FK cascade (`0001_init.sql`).
- **`cancelBatch`, `interruptBatch`** ([importDrafts.ts](../../functions/api/_services/importDrafts.ts)) — cancel is a durable D1 fence even when the live Durable Object worker cannot be reached. Restart and deadline recovery retain review work and never attempt to recover the source.
- **`interruptBatchSql`** ([importBatchInterrupt.ts](../../functions/api/_services/importBatchInterrupt.ts)) — the one definition of interrupting an import batch. A batch whose job died keeps the rows it persisted (`partial`) or fails (`failed`); the generation bump fences any late write from the dead job and the stored deadline is cleared so the sweep never picks it up again. Mode `one` binds (now, batchId, userId, generation) and fences one batch; mode `overdue` binds (now, now) and takes every processing batch whose stored deadline has passed.
- **`abortImportJob`** ([importRuntime.ts](../../functions/api/_services/importRuntime.ts)) — swallows service errors because the D1 fence has already committed; a service outage cannot undo cancellation or discard. The `IMPORT_JOBS` binding is addressable only from the authenticated API, and source content travels in memory only.
- **`onRequestPost`** ([flights/aircraft-batch.ts](../../functions/api/flights/aircraft-batch.ts)) — up to 20 aircraft suggestions for owned flights, as a replay-safe absolute set. Each item gets its own result, `accepted` (with the resulting flight) or `error` (`http_status`, `code`, `message`); valid items are written in one atomic D1 batch together with the dirty marker, then derived state is published once. Missing-only is the default; `replaceAll: true` permits overwriting an existing aircraft. The request sets an absolute value and never increments anything, so replaying it, for example after a lost response, returns `accepted` with the same flight state and leaves flight rows unchanged; invalid items (`NOT_FOUND`, `UNKNOWN_AIRCRAFT`, ...) fail the same way on every replay. Derived state is marked dirty and republished on every call that writes, so a replay yields the same totals at a later revision and nothing is counted twice. There is no server receipt or idempotency key: the client treats a lost answer as `uncertain` and resends the same items.
- **`onRequestPost`** ([flights/schedule-batch.ts](../../functions/api/flights/schedule-batch.ts)) — each guarded update and its conditional dirty marker commit in the same atomic batch.
- **`onRequestPost`** ([passport/ground-visits/index.ts](../../functions/api/passport/ground-visits/index.ts)) — create is `ON CONFLICT DO NOTHING`, and its dirty mark is conditional: a replayed or refused id inserts nothing, so it must not dirty derived state either. A visit id belonging to another owner, or already used for another country, is answered 409 and never revealed or reused.
- **`parseVisitId`** ([groundVisits.ts](../../functions/api/_lib/groundVisits.ts)) — the visit id is chosen by the browser so a retried create can be recognised: absent, or a lowercase UUID like every stored id.
- **`onRequestPatch`** ([passport/ground-visits/[id].ts](../../functions/api/passport/ground-visits/[id].ts)) — compare-and-set on the row as read, so a concurrent edit is not overwritten by fields this body left out.
- **`onRequestDelete`** ([passport/claims/[cc]/index.ts](../../functions/api/passport/claims/[cc]/index.ts)) — ground visits can exist without a claim, so unclaim deletes them and the claim as separate statements, each with its own only-if-changed dirty mark, because `changes()` sees only the preceding statement.
- **`onRequestPut`, `onRequestDelete`** ([passport/hidden/[cc]/index.ts](../../functions/api/passport/hidden/[cc]/index.ts)) — hiding a country is presentation only: both calls are idempotent and dirty no derived state, because nothing derived reads `passport_hidden_countries`. Only a pressed country can be hidden (pending-only and absent countries have no stamp to hide), enforced by inserting from `country_visit_evidence`.
- **`onRequestPut`** ([me/overview/prefs.ts](../../functions/api/me/overview/prefs.ts)) — validation stays strict, but the validated body is parsed tolerantly to retain facet insertion order. Background saves omit consent, so the write is compare-and-set to preserve a concurrent consent withdrawal.
- **`createManualPlace`** ([groundPlaces.ts](../../functions/api/_services/groundPlaces.ts)) — idempotent by client id: the same owner replaying the same payload gets the stored place; a different payload, or an id held by anyone else, is a conflict that discloses nothing about the other row. The endpoint ([ground-places/manual.ts](../../functions/api/ground-places/manual.ts)) answers 201 on creation, 200 for the same owner and payload, and 409 otherwise, so the two conflicts are indistinguishable.

### Derived state

- **`dirtyUserStatement`** ([derivedState.ts](../../functions/api/_services/derivedState.ts)) — must be in the same D1 batch as every canonical user mutation; the original published revision stays visible until a complete repair publishes. The mark is upsert-then-guard so an account with no derived-state row still reaches every revision-guarded write.
- **`repairUserDerivedState`** ([derivedState.ts](../../functions/api/_services/derivedState.ts)) — calculates only from canonical rows, then publishes every derived table in one D1 batch. A newer canonical mutation makes the first guard violate a `CHECK`, rolling the batch back; the `-1` branch violates it so no later result can publish after a newer revision, and an UPDATE that matches zero rows must not let the remaining derived writes through. A newer mutation owns the failure marker, so a stale attempt never attaches its error to it. No user identifier is logged on repair failure; OPERATIONS.md has the query that finds the affected rows.
- **`isDerivedReady`** ([derivedState.ts](../../functions/api/_services/derivedState.ts)) — readiness needs the evidence stamp too: an older build can publish a revision without the country-evidence projection (ADR 0001 section 4).
- **`mergeVisits`** ([derivedState.ts](../../functions/api/_services/derivedState.ts)) — keeps the first contributing legacy country per airport, so the contributing order is explicit. Archived counters may overlap flight history, so the merge keeps the larger observed count, never adds both and never infers extra trips from their difference. The all-time archived-countries read in Overview ([overview.ts](../../functions/api/_services/overview.ts)) matches it: an unsuppressed logged airport supplies its reference country, otherwise the first contributing legacy country in rowid order, with counts max-merged across all contributing rows before country validity is checked. Passport per-airport visit counts max-merge flight endpoints with the archived counter the same way ([passport.ts](../../functions/api/_services/passport.ts)).
- **`computeStatsForVisits`** ([stats.ts](../../functions/api/_services/stats.ts)) — ADR 0001 section 4: stats are calculated against the proposed visits (airports) and the proposed country-evidence countries, never old visits. Airports keep both endpoints of a transit stop; `countries_count` and `continents_count` come from the one country calculation. The continent rule is `continentOf7`, versioned `badge-continents-v1`.
- **`computedBadgeStatements`** ([stats.ts](../../functions/api/_services/stats.ts)) — award-only: existing awards are never revoked, so a changed input never revokes an earned badge.
- **`computedStatsStatement`** ([stats.ts](../../functions/api/_services/stats.ts)) — ported from the live PL/pgSQL (`db/_extracted/LOGIC_SPEC.md`) with parity kept deliberately: recompute does not set `most_visited_*`, `world_completion_pct` or `time_zones_count`. Do not "fix".
- **`continentOf7`, `regionOf`** ([continents.ts](../../functions/api/_lib/continents.ts)) — ported verbatim from the live PL/pgSQL CASE expressions and intentionally different, for parity. `continentOf7` (used by `recalculate_user_stats`) has seven buckets with North and South America separate and unmapped as `OTHER`; `regionOf` (used by `compute_continent_breakdown` and `compute_region_breakdown`) collapses both into `americas` and maps unmapped to `other`. Do not unify them.
- **`REGION_POLICY`** ([regions.ts](../../functions/api/_lib/regions.ts)) — ADR 0001 section 4 "Region models". Overview, Passport and geographic progress group countries by the catalog's six regions, computed at read time from the published country evidence and never persisted, so a policy bump needs no dirty mark. The other two models stay where they are and are versioned by what they feed: `continentOf7` for `continents_count` and continent badges (`badge-continents-v1`, award-only), and `regionOf` for the persisted `user_advanced_stats` breakdowns. Overview continents use the six-region model (`regionPolicyVersion`), not `continentOf7` ([overview.ts](../../functions/api/_services/overview.ts)).
- **`toBadgeDefinition`** ([badges.ts](../../functions/api/_lib/badges.ts)) — `badge_definitions.criteria` is JSON stored as TEXT and is parsed before the badge DTOs return it.
- **`flightCountriesOf`** ([countryEvidence.ts](../../functions/api/_services/countryEvidence.ts)) — ADR 0001 section 4. This is the one country-evidence calculation: Passport, Overview, `user_stats`, advanced stats and the queue DTOs read what it publishes (or call `effectiveArrivalPolicies`), and nothing recomputes a country set from airport aggregates or live endpoints.
- **`effectiveArrivalPolicies`** ([countryEvidence.ts](../../functions/api/_services/countryEvidence.ts)) — the policy of every completed (awaiting or logged) flight: (1) an explicit decision wins, where transit consumes the destination and the stored leg's origin and only while that leg still departs the same airport (the live chain never moves a stored decision); (2) otherwise an awaiting flight with an unambiguous third-country connection defaults to transit; (3) otherwise (logged legacy/save, route changed, no connection) the endpoint is included. Airport evidence is never suppressed, only the country: the destination of a transit arrival and the matched leg's origin.
- **`connectionChains`** ([connections.ts](../../functions/api/_services/connections.ts)) — ADR 0001 section 4. There is no trips entity: a link is derived from two legs, a chain is a maximal path of unambiguous links, and ambiguity is review-only and never suppresses a country. A link A to B exists only when B is A's single candidate and A is B's single candidate in the winning tier (precise outranks estimated); anything else with a candidate is ambiguous, and an untimed same-date pair that cannot be ordered (a cycle) is ambiguous too. Flight `date` is a date-only label, never passed to `new Date()`, only compared and shifted with the calendar helper; instants (`departure_utc`, `arrival_utc`) are canonical ISO strings. `flights.date` has no DB `CHECK`, so a label that is not `YYYY-MM-DD` cannot be shifted and that leg is treated as undated: it never forms or extends a chain, though its endpoints still count as ordinary evidence.
- **`queue`** ([queue.ts](../../functions/api/_services/queue.ts)) — ADR 0001 section 5 (C4). The awaiting queue derives candidates and defaults from `connectionChains` and `effectiveArrivalPolicies` over one evidence snapshot, the same calculation the repair publishes, so queue, Passport and Overview cannot disagree about a default. Ambiguous-connection candidate ids are review-only and never suppress a country. `candidateTokenOf` hashes only this flight's route and connection decision, the matched leg's route and the resulting default, so another flight changing never invalidates it while a change to this connection does.
- **`readPressedBefore`** ([newlyStamped.ts](../../functions/api/_services/newlyStamped.ts)) — ADR 0001 section 5. Newly stamped = (pressed after publication minus pressed before) intersected with the countries the operation's own flights contribute; the intersection keeps a concurrent claim or another writer's flight from being credited to the operation. The before-set is the published projection, trusted only while publication is current; an account with no derived-state row gets one first (as confirmation does) so a first save is known. The result is null whenever it cannot be told: unknown before-set, publication still pending, or nothing fresh (a replay). Only logged, non-suppressed endpoints press a country; awaiting ones are pending and upcoming ones contribute nothing.
- **`passportRead`** ([passport.ts](../../functions/api/_services/passport.ts)) — ADR 0001 section 4. List and detail derive from one pure policy (`countryContributions`) so Passport, Overview and `user_stats` cannot disagree about which countries a flight supports. `pressedCountryCount` includes claims and ground visits and ignores hiding; `pendingCountryCount` counts awaiting-only countries; hidden countries (presentation only, nothing derived reads them) leave `countries`, `pendingCountryCount`, `regions` and `visibleCountryCount` but stay in `pressedCountryCount`; `flightCountryCount` equals `user_stats.countries_count` (flights and legacy evidence, no claims or ground visits), which is what the leaderboard `countries` category ranks. Overview passes `applyHidden: false` because hiding is a Passport presentation choice. One owner-scoped batch supplies every collection and the revision metadata, shared by `GET /api/passport/countries` and the Next server read. A stored hidden preference counts only while its country is pressed: when the last support goes, or the country falls back to pending, it is neither a hidden stamp nor kept out of the pending block.
- **`countryStays`** ([passport.ts](../../functions/api/_services/passport.ts)) — merges consecutive duplicate flight copies, including a copy enriched with times; an intervening leg preserves a real second entry on the same day even when its times are unknown. An airport with unresolved country is no evidence that the traveller left the last known country, so stays skip it.
- **`completedScope`** ([periodScope.ts](../../functions/api/_services/periodScope.ts)) — the one definition of what the Overview and the opened map count: completed (awaiting or logged) flights of one owner in one period, and the C3 countries they reach after the published transit suppressions (ADR 0001 section 4). The Overview summary and `GET /api/flights/route-projection` both build their statements here, so figures and map disagree only when the published revision changed between two reads. `MAX_COUNTRY_CODES` bounds reference country reads, which fail rather than truncate if the imported set outgrows it. `countryEndpoints` keeps the flight id per endpoint so published suppressions can be anti-joined (`UNSUPPRESSED`). `countryVisitsStatement` reads the published projection for unfiltered all-time (flight and legacy countries, no claims or ground visits) and otherwise canonical endpoints minus the published suppressions, so a suppressed transit hub never counts.
- **`onRequestGet`** ([flights/route-projection.ts](../../functions/api/flights/route-projection.ts)) — the private, compact projection for the opened map (C6) shares the Overview's completed-period predicate, country policy and publication stamps, so map and summary agree or visibly differ by revision. Geometry comes from D1's authoritative airport reference and is bounded; `MAX_PROJECTED_ROUTES` is 5,000 distinct pairs, the largest payload the opened map was measured at (docs/research local performance).
- **`readOverviewData`** ([overviewData.ts](../../functions/api/_services/overviewData.ts)) — one batch, one snapshot: ground journeys are read in the same batch so they come from the revision the ETag names. `ownerJourneysRead` ([groundJourneyRead.ts](../../functions/api/_services/groundJourneyRead.ts)) exposes the owner journey read as statements plus assembly for the same reason.
- **`newCountriesIn`** ([overviewShape.ts](../../functions/api/_services/overviewShape.ts)) — countries whose earliest non-transit evidence across all time falls in the period. `evidence` is every published flight-or-legacy country with its all-time first visit; intersecting with the period's own countries stops a legacy country with no flight in the period (legacy evidence has no per-year attribution) from counting as new. In Overview, `firstVisits` uses that all-time evidence and the year only selects which countries are first visits.
- **`journalFirsts`** ([firsts.ts](../../functions/api/_services/firsts.ts)) — spec D2. Journal firsts reuse the Passport contribution policy, so a transit-suppressed endpoint never earns one, and non-flight evidence that may predate a flight blocks it: a claim records when it was entered, not when the visit happened, so it counts as undated and blocks every flight; a ground visit is dated to the first day of `visit_year`; contributing legacy visit evidence (`legacyEvidenceStatement`) uses its own country over the airport's. Upcoming flights never earn (they still matter as outgoing transit legs), awaiting flights earn with `pending`, and a flight earns a country only when no earlier flight contributes it and no non-flight evidence for it is dated on or before the flight's date or undated. Malformed rows are skipped, never thrown on. An undatable flight still supports its countries in the Passport, so a dated flight cannot claim that country first.
- **`findDuplicateMatches`** ([duplicates.ts](../../functions/api/_services/duplicates.ts)) — ADR 0001 section 6. One `json_each` tuple query over the member's whole history, independent of list paging: a candidate (date, origin, destination) matches the lowest-id owned flight with the same tuple, optionally excluding one flight (the one being edited, or the flight a draft already became). `duplicate-candidates` ([flights/duplicate-candidates.ts](../../functions/api/flights/duplicate-candidates.ts)) queries bounded candidate keys across the entire owned history for the same reason.
- **`userAnalytics`** ([userAnalytics.ts](../../functions/api/_services/userAnalytics.ts)) — counts records retained by current accounts, not a historical event ledger; travel dates, automatic confirmations and session refreshes do not measure someone adding journal content.

### Flight lifecycle and reads

- **`lifecycleForCreate`, `lifecycleForEdit`** ([lifecycle.ts](../../functions/api/_services/lifecycle.ts)) — ADR 0001 section 2. Create, bulk create and edit call the pure rules; the owner sync and the cron share `applyDueTransitions`. Lifecycle-aware writes always set the lifecycle columns and the `is_upcoming` projection together, so the section 1 adapter triggers never fire for them. Date and route edits move lifecycle and the projection in the same UPDATE ([flights/[id].ts](../../functions/api/flights/[id].ts)).
- **`takeRequestTimezone`** ([lifecycle.ts](../../functions/api/_services/lifecycle.ts)) — the member's browser timezone travels as a top-level `timezone` request field next to the flight fields, never part of `FlightInput` or its idempotency digest. Absent is null (old clients); present but not a valid IANA zone is 400 `INVALID_TIMEZONE`.
- **`deadlinesFor`** ([lifecycle.ts](../../functions/api/_services/lifecycle.ts)) — awaiting starts the morning after the flight and auto-confirm seven local days later, in the flight's time zone (ADR 0001 section 1 calendar rule). A corrected upcoming flight never skips the awaiting queue, and an edit never auto-confirms inline.
- **`applyDueTransitions`** ([lifecycle.ts](../../functions/api/_services/lifecycle.ts)) — ADR 0001 section 2: upcoming becomes awaiting once the stored `awaiting_after` has passed, awaiting becomes logged (`automatic`) once `auto_confirm_after` has passed, and a flight past both makes both moves in one pass, so a missed cron or a late first session never restarts the clock. Deadlines are never recomputed. Each direction is capped at `limit` flights, oldest stored deadline first, so the stored deadline is the cursor and a backlog drains over successive passes without moving anyone's eligibility. Auto-confirm writes the effective arrival policy from one snapshot and is guarded by the derived-state revision that snapshot was read under; the revision is read before the flights, so any later mutation bumps it and fails the guard, and the next pass retries. The dirty mark is unconditional whenever due rows were read, because `changes()` would only see the last UPDATE; a lost race costs one extra repair. Counts come from `RETURNING` because D1 `meta.changes` also counts trigger writes (A1 note).
- **`onRequestPost`** ([flights/sync-upcoming.ts](../../functions/api/flights/sync-upcoming.ts)) — ADR 0001 section 2 (R1): applies the owner's due transitions and then publishes derived state; awaiting flights count as completed. It returns `{ synced, awaited, autoConfirmed, more, derived_state?, revision? }`; `synced` counts distinct flights whose state changed (a flight making both moves counts once) and `more` asks for another bounded pass. It is the Next member shell's only path for both transitions while the cron is held (the `ActivityBridge` trigger). Any unpublished state is repaired inline (this pass's dirty mark, an earlier failed repair, and a stale evidence stamp left by a publication below the rollback floor, ADR 0001 section 10), so a member's first session reconciles even while the cron is held.
- **`onRequestGet`** ([me/awaiting.ts](../../functions/api/me/awaiting.ts)) — ADR 0001 section 5: strictly read-only. It never moves a flight, repairs derived state or writes a row, so opening the queue cannot change what it shows.
- **`reviewTransit`** ([transitReview.ts](../../functions/api/_services/transitReview.ts)) — ADR 0001 sections 4 and 5. A logged `legacy` or `save` flight with no arrival decision keeps its destination country (rule 3): nothing reclassifies history on its own. When the same calculation that gives awaiting flights a transit default finds an unambiguous third-country connection, the member may opt in; applying stores `arrival_transit = 1` plus the leg and changes nothing else (lifecycle, provenance and `confirmed_at` are left alone). GET is a pure read; POST follows the receipt-first protocol of `confirmation.ts` (shared pieces in `receipts.ts`): apply is all or nothing and dismiss records the marker only. `reviewTokenOf` is per flight, like the queue token. Removal is computed by applying every candidate in memory and comparing pressed countries, so a country another flight, a claim, a ground visit or archived evidence still supports is not removed, and `removedCountries` credits only countries these flights' decisions could have suppressed, so a claim or flight deleted meanwhile is not counted.
- **`updateFlight`** ([flights/[id].ts](../../functions/api/flights/[id].ts)) — every query is scoped `id = ? AND user_id = ?` because D1 has no row-level security; mutations require CSRF. PATCH and DELETE re-run the same service chain as create so stats, badges and advanced stats stay in sync. The route adapter clears transit on every route change, so `arrival_transit` and its leg are restored after the guarded route write in the same transaction. Explicit source instants (`utc_explicit`) hold only while date, route, clock times and zones are unchanged (ADR 0008); a guarded update that changes no rows rejects changes to any rewritten snapshot field with 409, while a concurrent deletion stays a 404. Deleting a flight tombstones its imported history rows in the same batch (ADR 0008), as does bulk delete.
- **`buildFlightWhere`** ([flightQuery.ts](../../functions/api/_lib/flightQuery.ts)) — shared by `GET /api/flights` and `GET /api/flights/ids` so they stay in lockstep. Sort field and direction are allowlisted (`SORT_FIELDS`) because the column name is interpolated into SQL; every value is bound. `isUpcoming=false` keeps its meaning of completed, i.e. awaiting or logged (ADR 0001 section 1). City and alias search words are resolved to IATA codes in JS with Unicode folding, because SQLite `lower()` folds only ASCII (Russian, native script, diacritics), and each word is bound with its codes as one JSON array matched against origin and destination.
- **`orderByClause`** ([flightQuery.ts](../../functions/api/_lib/flightQuery.ts)) — built from an already-validated `SortConfig` with a stable id tiebreak. The default sort (date descending) leads with `lifecycle_state = 'upcoming'` rows, nearest first, so the Journal's Upcoming group is globally nearest-first across pages; every non-default sort is a plain column order. An explicit date-descending request is indistinguishable from the default and gets the same upcoming-first order.
- **`onRequestGet`** ([flights/journal.ts](../../functions/api/flights/journal.ts)) — `owner=<id>` binds the read to the account the page was rendered for. After a cross-tab account switch the cookie names someone else, the read is refused before any private data is loaded, and so it never lands in the old page's cache.
- **`computeFlightDuration`** ([flightDuration.ts](../../functions/api/_services/flightDuration.ts)) — ADR 0002. Ported from the live PL/pgSQL (`supabase/migrations/20260212120000_fix_timezone_aware_duration.sql`, a one-time UPDATE: there is no deployed trigger re-running this logic, verified against live `pg_proc` on 2026-06-20). Postgres `AT TIME ZONE` parity quirks are kept (do not "fix"): `departure_utc` is set unconditionally from the same-day departure, and a missing time or tz leaves everything unchanged. One deliberate departure: the arrival is the candidate date from -1 to +2 days (date-line eastbound to westbound trans-Pacific) whose duration falls in (0, 1440] minutes, taking the smallest duration; with no candidate the arrival is unknown (null) and the existing duration is kept. This replaces the legacy arrival CASE, which stamped inverted or day-shifted arrivals across the date line, and is justified by the server being the authority now that the legacy backfill is done. `decideDuration` clamps to 1200 later.
- **`localWallClockToUtc`** ([flightDuration.ts](../../functions/api/_services/flightDuration.ts)) — replicates Postgres `(timestamp without time zone) AT TIME ZONE tz`. Intl only goes UTC to local, so the wall-clock parts are treated as UTC, Intl gives the local time of that instant, and the difference is the zone's offset; a second pass fixes DST-transition days where the offset at the guessed instant differs from the corrected one (matching Postgres' deterministic resolution of normal times).
- **`explicitDuration`** ([flightMetrics.ts](../../functions/api/_services/flightMetrics.ts)) — ADR 0008: server-validated instants replace wall-clock inference only when both parse and give a positive duration within the clamp; anything else falls back to inference. They are never taken from a request body.

### Leaderboards

- **`refreshLeaderboards`** ([leaderboard.ts](../../functions/api/_services/leaderboard.ts)) — ported from the live PL/pgSQL `refresh_leaderboards()` (`db/_extracted/LOGIC_SPEC.md`). It runs from cron every 5 minutes, not per write, as a full rebuild of `leaderboard_cache`; the cache is always cleared in the same batch as the inserts, even when nobody is eligible. Parity quirks (do not "fix"): the `cities` category ranks `airports_count`, not a city count; sky eligibility keeps `total_flights >= 5` and `show_on_leaderboards = 1`; percentile is `ROUND((1 - rank/total) * 100, 1)` in float division with a `total > 0` guard. Deliberate deviations (leaderboard redesign, 2026-10-15; `.scratch/leaderboard-redesign/spec.md`): eligibility also requires `is_public = 1`, as every public read does, so hidden members leave no rank gaps; competition ranking (1, 1, 3) so equal values share a rank instead of `ROW_NUMBER()` by signup date, with percentile following the shared rank; three ground categories (ADR 0005, ADR 0007 refinement) for members who publish all countries (`passport_publication = 'all'`) with at least 3 completed rail and road journeys together; two periods, `all` and the current UTC calendar year (`YYYY`), with thresholds judged on all-time totals in both so nobody drops out of the year board for flying little; a zero value is not ranked, except in all-time sky categories (parity: everyone eligible ranks there); lane vehicles ride in `metadata` (2026-10-16): sky rows carry the most-flown aircraft type, ground Countries rows the mode the member covered more distance by.
- **`refreshLeaderboards` inserts** ([leaderboard.ts](../../functions/api/_services/leaderboard.ts)) — chunked by the per-row bind count because D1 caps one statement at 100 bound variables.
- **`groundTotals`** ([leaderboard.ts](../../functions/api/_services/leaderboard.ts)) — completed journeys per member, optionally only those starting in `year` (an integer string, safe to inline). Deleted journeys have no status, so `completed` excludes them.
- **`topAircraft`** ([leaderboard.ts](../../functions/api/_services/leaderboard.ts)) — each member's most-flown aircraft type among awaiting and logged flights, optionally in one year (bound). Ties go to the type flown most recently, then the code, so a rebuild is stable. Sky rows preserve the actual aircraft type for their period; artwork fallback belongs to the client.
- **`groundKm`** ([leaderboard.ts](../../functions/api/_services/leaderboard.ts)) — more rail kilometres run the locomotive; anything else, including no known distance, drives the car.
- **`refreshLeaderboards` year values** ([leaderboard.ts](../../functions/api/_services/leaderboard.ts)) — computed from that year's flights. Countries are airport countries only, since the year has no legacy evidence or connection/transit rules, so it can differ from the all-time number.
- **`PUBLISHED_DERIVED_STATE`** ([leaderboard.ts](../../functions/api/_lib/leaderboard.ts)) — the eligibility gate shared by every leaderboard read and rebuild: a user whose derived state is stale (`revision != published_revision`) is hidden until repair publishes it; users with no `user_derived_state` row are eligible. Use it as `${derivedStateJoin('lc')} ... WHERE ... AND ${PUBLISHED_DERIVED_STATE}`; the join always aliases the table as `ds`. `SKY_MIN_FLIGHTS` (5) and `GROUND_MIN_JOURNEYS` (3) are the participation thresholds, and the calendar-year period of a rebuild at `now` is the UTC year.

### Flight enrichment and import extraction

- **`ANTHROPIC_ENRICH_DEADLINE_MS`** ([enrich/_anthropic.ts](../../functions/api/enrich/_anthropic.ts)) — 35 s, so both Anthropic Messages calls finish before the existing 40 s web client deadline. Only tool-attested cited excerpts cross from the search step into the extraction request. Multi-fetch document ordering is not guaranteed by the API contract, so each literal excerpt is bound to exactly one returned document URL by text match, never by title. `quoteSupports` stops the extractor copying the requested identity into an unrelated cited excerpt, and the literal supporting excerpt is kept as evidence, not the extractor's invented prose.
- **`normalizeAircraftEvidence`** ([enrich/_evidence.ts](../../functions/api/enrich/_evidence.ts)) — a source-backed suggestion still requires review; it does not authorize a journal write.
- **`ENRICHMENT_DEADLINE_MS`** ([enrich/_lookup.ts](../../functions/api/enrich/_lookup.ts)) — 20 s, below the 40 s web client deadline including response validation. A retrieved URL is provenance, not independent verification of the page's claims. Gemini search supports may be cumulative prefixes, so a citation is attributed only to the row whose unique evidence it ends in, not to every earlier record in that prefix.
- **`lookupAircraft`** ([enrich/_lookup.ts](../../functions/api/enrich/_lookup.ts)) — JSON mode is omitted with `googleSearch` because live checks returned no grounding citations with it.
- **`safeUrl`** ([enrich/_shared.ts](../../functions/api/enrich/_shared.ts)) — provider and client URLs become links only as credential-free http(s) URLs.
- **`buildBatchPrompt`** ([enrich/_shared.ts](../../functions/api/enrich/_shared.ts)) — searches for evidence about the dated flight, not current route equipment, which is not evidence for a past flight.
- **`onRequestPost`** ([enrich/aircraft.ts](../../functions/api/enrich/aircraft.ts)) — the endpoint is state-changing and burns paid Gemini quota, so it requires same-origin plus the double-submit token and an authenticated user, and is rate-limited per user (30 per hour) to prevent quota and cost abuse (security finding: AI quota/cost abuse).
- **`FLIGHT_RESPONSE_SCHEMA`, `extractFlights`** ([import/_extract.ts](../../functions/api/import/_extract.ts)) — ADR 0001 section 6, controller ruling R3: provider extraction is shared by the synchronous parse endpoint and the persisted job writer with one prompt, schema, model and set of limits; nothing here persists anything and callers decide what to keep (the job writer drops `raw_text`). The schema orders flights before `raw_text` so streamed rows arrive before the note, and the note stays short so a long source cannot hit the output cap. Pasted-text extraction is capped at `MAX_TEXT_LENGTH` (100,000 characters) to control Gemini cost; the text branch was previously uncapped.
- **`MAX_IMPORT_BODY_BYTES`** ([import/_extract.ts](../../functions/api/import/_extract.ts)) — 14 MiB: a 10 MiB file becomes at most 13,981,016 base64 bytes and the rest is the JSON envelope. The stream limit applies even without `Content-Length`.
- **`validMonthDay`** ([import/_extract.ts](../../functions/api/import/_extract.ts)) — accepts `02-29`: the year is unknown for a month-day-only date.
- **`normalizeFlight`** ([import/_extract.ts](../../functions/api/import/_extract.ts)) — a missing airline gets the `ZZ` placeholder (flagged `airline_was_placeholder`) instead of rejecting the flight. A model-supplied year without explicit source evidence is never a save-ready fact: the draft stays for review with a blank date and a visible provenance flag.
- **`PROVIDER_TIMEOUT_MS`** ([import/_provider.ts](../../functions/api/import/_provider.ts)) — 90 s, because the import UI has a 120 s deadline and validation and response delivery need the rest. `providerFailure` maps provider errors to stable user-visible failures without leaking provider payloads or document text.
- **`PROCESSING_WINDOW_MS`** ([importDrafts.ts](../../functions/api/_services/importDrafts.ts)) — the 90 s provider deadline plus validation and the write (120 s in total); past it the maintenance sweep treats the job as dead.
- **`review_required`, `verification`** ([import/_shared.ts](../../functions/api/import/_shared.ts)) — `review_required` marks conflicting or uncertain source evidence and means never preselect. `verification` is a server-owned source check and is never accepted from extraction output.
- **`EXTRACTION_PROMPT`, `EXTRACTION_TASK`** ([import/_shared.ts](../../functions/api/import/_shared.ts)) — rules first, then the document, then the task, because Gemini 3 long-context guidance puts the request after long context. The response schema fixes the JSON shape, so the prompt explains values, not structure. `RAIL_PROMPT` follows the same order with `RAIL_TASK` ([railTicketOcr.ts](../../functions/api/_services/railTicketOcr.ts)).
- **`parseStructuredText`** ([import/_text.ts](../../functions/api/import/_text.ts)) — only a fully recognised `KUUKI FLIGHTS` pipe-list bypasses the model; any unknown prose falls back intact. A leading `KUUKI FLIGHTS v<N>` line (any N) and a wrapping Markdown code fence are ignored. The parser excludes this booking's status, never an uncertain refund or a cancelled other leg. Only status or evidence doubt blocks preselection of a row; catalog and year gaps show in `field_confidence` and the empty fields. A locally parsed list holds up to 500 drafts per batch because it is exact, while model extraction is limited to 100 because it is not.
- **`verifyFlights`** ([import/_verify.ts](../../functions/api/import/_verify.ts)) — conservative admission policy, below the provider context ceiling, and evidence is never truncated.
- **`draftFieldsOf`** ([importDrafts.ts](../../functions/api/_services/importDrafts.ts)) — import drafts never store uploaded bytes, base64, pasted text, provider responses or `raw_text`; a draft holds only the extracted flight fields and bounded confidence numbers, and strings are bounded so `fields_json` stays far below its `CHECK`.
- **`submitImport`** ([importJob.ts](../../functions/api/_services/importJob.ts)) — ADR 0001 section 6, controller ruling R3. The synchronous writer makes one provider call in the request, then persists the batch and all drafts in one fenced D1 batch, idempotent on the submission operation id. Nothing about the source is persisted: the content lives in this call's memory only, `raw_text` is dropped and the provider response never leaves `extractFlights`. Local legs are persisted synchronously with no provider call and no job, so they need neither a credential nor `IMPORT_JOBS`. A refused job handshake is not an outage when the batch has moved on (the original job may have finished or been cancelled between the read and the handshake): D1 is the authority, and only a batch still waiting for its first start counts as a failed dispatch. An insert can become visible before its first dispatcher has established ownership, so the handshake is repeated safely: the Durable Object serializes starts and calls the provider once.
- **`onRequestPost`** ([import/jobs.ts](../../functions/api/import/jobs.ts)) — ADR 0001 section 6 (C5). CSRF, auth and the per-user `import-parse:` rate limit gate a provider extraction; the result is a server-owned batch of review drafts. It is idempotent on `submissionOperationId`: a replay returns the stored batch and never calls the provider again. `type: 'boarding_pass'` admits legs the browser decoded itself: validated here and persisted as unverified review drafts through the same batch writer, with no provider call or import job, no date yet (the member picks the year), no confidence, and never preselected.
- **`onRequestGet`, `onRequestDelete`** ([import/batches/[id].ts](../../functions/api/import/batches/[id].ts)) — GET is the batch snapshot (status, stage, revision, expiry, every draft with its duplicate match and validation issue); D1 is authoritative, so it is also the refresh/remount read. DELETE is an explicit discard; closing the page is not a discard.
- **`onRequestPost`** ([import/batches/[id]/confirm.ts](../../functions/api/import/batches/[id]/confirm.ts)) — receipt-first and per item: each item answers `created`, `replayed` or an error in place, so a retry after a lost response or partial failure creates only what is still missing. Flights come from the shared bulk-create path, so reference validation is the ordinary one (statement chain in `importConversion`).
- **`extractRailTickets`** ([railTicketOcr.ts](../../functions/api/_services/railTicketOcr.ts)) — only the structured, bounded fields ever leave the module: passenger names, booking and ticket numbers, payment data, barcode payloads and source text are neither requested nor projected. `normalizeRailResponse` drops unknown keys by construction, including sensitive text the model returned despite the prompt, and throws on a malformed envelope. `detectRailFileMime` decodes only the first 24 base64 characters (18 bytes) and refuses unknown content rather than defaulting to an image type. Logging records outcome and size buckets only, never content.
- **`onRequestPost`** ([ground-journeys/ocr.ts](../../functions/api/ground-journeys/ocr.ts)) — one base64 file per request, `{ content }`. The declared type is ignored and the file signature decides. Nothing is stored; each accepted file spends one shared provider call. The rate limit is counted only after admission, so files refused for type or size spend no provider call, and it is the `import-parse` quota itself, not a parallel one, so rail OCR cannot bypass it.

### Flighty history import

ADR 0008 is the authority for the Flighty model; the entries below record only the reasons the code carried.

- **`admitChunk`, `createRun`, `discardRun`, `eraseRunSource`** ([historyImport.ts](../../functions/api/_services/historyImport.ts)) — every write is owner-scoped and fenced on the run's status and generation, so a late chunk after a discard, an erasure or an expiry inserts nothing. Cell values are never logged or put into error messages. Opening a run is idempotent: the same operation id and manifest answer the run already opened, however the earlier call ended. A replay of an admitted chunk inserts nothing and answers the same run, and when it completes a run that an interrupted seal left `receiving`, the replay finishes the seal; racing seals are harmless because each write is fenced on `receiving`.
- **`runStatusStatement`** ([historyImport.ts](../../functions/api/_services/historyImport.ts)) — the run's status follows its open rows and every change bumps the revision that group answers fence on. The fence is the run's generation plus its status (`receiving` for a seal, else `review` or `completed`), optionally the revision the owner saw, and optionally that the preceding statement of the batch changed a row.
- **`sealRun`** ([historyImport.ts](../../functions/api/_services/historyImport.ts)) — compares a complete run with the owner's journal and earlier imports, then opens it for review in one D1 batch: every row update and the status flip are fenced on the run still `receiving` at this generation, so a concurrent seal or a discard leaves nothing half-classified. Only records an export actually accepted count toward matching: a `link` receipt (a repeat) never adds an occurrence, so re-importing a file cannot multiply what an earlier file said once. A record whose only trace is a `link` receipt to a flight the owner deleted is still a deleted record: the receipt adds no occurrence, but its tombstone keeps the identity so it is never offered as new.
- **`readRunPage`** ([historyImport.ts](../../functions/api/_services/historyImport.ts)) — filters are read with own keys only, so an inherited name such as `constructor` is an unknown filter, not a prototype member. `GET /api/import/history/:id` ([import/history/[id].ts](../../functions/api/import/history/[id].ts)) returns summary and one keyset page (`state`, `group`, `cursor`, `limit` up to 50); with `representation=archive` it returns every record and its private source cells as a JSON download. DELETE discards what is not confirmed; created flights stay.
- **`discardRun`, `eraseRunSource`** ([historyImport.ts](../../functions/api/_services/historyImport.ts)) — discard removes a run with nothing committed; otherwise its unconfirmed rows become `ignored`/`discarded` and lose their cells, the run closes and its generation fences late writes. Erasure removes every stored cell (PNR and notes included) while flights and minimal tombstones stay; erased cells never come back, and unconfirmed records leave review ([import/history/[id]/source.ts](../../functions/api/import/history/[id]/source.ts)).
- **`confirmRows`, `answerGroup`, `patchRow`** ([historyImportDecisions.ts](../../functions/api/_services/historyImportDecisions.ts)) — every write re-maps the row on the server from its verbatim cells and the answers, and is fenced on the row version and the run generation (group answers also on the run revision the owner saw). Confirmation creates flights only through the shared `bulkCreate` chain with a history guard; links and preserved records update only their own rows, and they commit before, and independently of, the creates. `isClockHeader` accepts only known clock columns: any other offset key is meaningless and unbounded input.
- **`answerGroup`** ([historyImportDecisions.ts](../../functions/api/_services/historyImportDecisions.ts)) — applies one answer to every open row of a group at the run revision the owner saw. All rows change in one D1 batch or none do; a decision made elsewhere in the meantime is a revision conflict, never a partial application. A match group settles only rows whose mapping is clean, and `link` needs exactly one found flight ([import/history/[id]/groups.ts](../../functions/api/import/history/[id]/groups.ts)).
- **`confirmRows` replay** ([historyImportDecisions.ts](../../functions/api/_services/historyImportDecisions.ts)) — receipt first: an answered key replays whatever happened since, even after a discard or erasure. A row whose mapping no longer yields `ready` (catalog change or a rule fix) goes back to review. When a link guard refuses because its target flight was deleted after the review, the row would stay `ready` with a finding that links to nothing, so it goes back to review as a deleted record the owner must re-confirm. Confirm takes at most 50 items per request, receipt-first per item ([import/history/[id]/confirm.ts](../../functions/api/import/history/[id]/confirm.ts)).
- **`evaluateRow`** ([historyImportEvaluate.ts](../../functions/api/_services/historyImportEvaluate.ts)) — the one rule for a row's state: the server maps the verbatim cells with the owner's answers, then applies the match finding. Admission, answers, group answers and confirmation all call it, so a row can never be `ready` on one path and not on another. `NAMES_CONFLICT` findings name a reviewed conflict, so answering `new` waives the SQL same-date-and-route guard for them only. An exact repeat of an earlier confirmed record (`previous_import`) is already accounted for and becomes a ready link whatever the mapping still asks.
- **`tombstoneHistoryRowsStatement`** ([historyImportRetention.ts](../../functions/api/_services/historyImportRetention.ts)) — ADR 0008 "Private source data and deletion". Retention and deletion statements are meant for the caller's own D1 batch, so private cells disappear in the same transaction as the flight, run or account they belong to. Before `DELETE FROM flights` in the same batch, rows linked to those flights lose their cells and link and become `removed`; digest, Flighty ID and match key remain as the tombstone that stops a silent re-creation.
- **`expireHistoryRunsStatements`** ([historyImportRetention.ts](../../functions/api/_services/historyImportRetention.ts)) — maintenance: 30 days after a run opened, its unconfirmed rows become `ignored`/`expired`, ignored rows lose their cells and the run closes. Committed rows keep their cells; no row disappears, so totals still add up.
- **`catalogFlightyRefs`** ([flightyRefs.ts](../../functions/api/_services/flightyRefs.ts)) — ADR 0008. One catalog definition for the API and the offline evaluator. Airports come from the offline catalog with their IANA zone; the zone of an airport without one is derived from its coordinates, as flight metrics do. Final airport existence is still checked against D1 when a flight is written.
- **`FlightScanner`** ([workers/import/scanner.ts](../../workers/import/scanner.ts)) — the output-size refusal stays authoritative over a parse error from an oversized malformed tail.

### Ground travel

- **`parseGroundCommand`** ([groundJourneys.ts](../../functions/api/_services/groundJourneys.ts)) — SQLite `length()` counts characters, so validation counts code points, not UTF-16 units (8 emoji are 16 units but 8 characters; 4 emoji used to pass the length test). Leg dates are date-only because times sit in the place's own zone, which may be unknown; ISO dates compare as text. Operation keys are ASCII only so JS length and the receipt table's SQL `length()` `CHECK` count the same thing.
- **`GROUND_BODY_MAX_BYTES`** ([groundJourneys.ts](../../functions/api/_services/groundJourneys.ts)) — 5 MiB (5,242,880 bytes), derived from the largest documented request at 4 UTF-8 bytes per character: place snapshot about 4,000 bytes, road point about 44,200 (note 10,000 x 4 + snapshot + ids), rail leg about 11,000, journey about 42,800, and 100 road points make 4,462,800 bytes, leaving about 17% headroom. The 128 KB JSON default is far below it. D1 caps one bound string at 2 MB, so child rows go in several INSERTs; 20 x 44,200 bytes stays under 1 MB.
- **`placeNameKey`, `placePrefix`** ([groundPlaces.ts](../../functions/api/_services/groundPlaces.ts)) — contract in `.scratch/ground-travel/places-contract.md`. The key helpers must import nothing at runtime except the shared folding, because `scripts/generate-geonames-places.ts` builds the catalog keys with them. Catalog rows and queries must use the same function (case- and diacritic-folded by `foldSearchText`, punctuation and hyphens turned into single spaces, so "Coeur d'Alene" becomes "coeur d alene"). The longest key is capped so one request cannot build an unbounded range; `MAX_CODE_POINT` makes every real key starting with the query sort below `query + MAX_CODE_POINT`. Catalog reads over-fetch by 5 because aliases of one place collapse afterwards.
- **`searchGroundPlaces`** ([groundPlaces.ts](../../functions/api/_services/groundPlaces.ts)) — up to `GROUND_LIMITS.searchResults` places: the owner's manual places and catalog matches, exact-name first (manual before catalog), then prefix matches (manual, then by population). One catalog bucket is read per keystroke, and an empty or unloaded catalog yields manual matches only. A query under `GROUND_LIMITS.searchMinChars` (3, the catalog bucket width) folded characters returns nothing, manual matches included, so one gate keeps the picker's "keep typing" state consistent. Up to three characters a bucket holds every match in population order, so the scan stops after the limit; longer keys narrow the bucket to a handful of rows, so the key range is sought instead, reading only the matches (worst measured about 2.3k keys for "sant") where the bucket walk could read all about 7.6k.
- **`onRequestGet`** ([ground-journeys/export.ts](../../functions/api/ground-journeys/export.ts)) — the owner's versioned JSON export of rail and road journeys and manual places. Live journeys only (plans and cancellations included); receipts, tombstones, internal user ids and the shared city catalog never leave the database. No reverse import is promised. All tables are read in one D1 batch so they share one snapshot, and a malformed legacy snapshot exports as null rather than failing the file.

### Workers and Durable Objects

- **`ImportJob`** ([workers/import/ImportJob.ts](../../workers/import/ImportJob.ts)) — one server-owned request per batch. Durable storage contains only the fence, never source or provider output. A duplicate start never makes a second provider call, including after a restart, because the stored fence is compared first. No exception payload is logged, only a fixed error code, since database errors may contain extracted values. Every provider await is raced against an abort promise so a provider that ignores the `AbortSignal` still cannot outlive the timeout. `rejectedOrdinals` remembers rows refused while streaming because the final pass revisits them. A deterministic parse has every row up front, so contiguous runs are written in one fenced batch each, and up to `MAX_DRAFTS_DETERMINISTIC` rows cost a few D1 batches; it never passes through the provider scanner, whose output cap a long paste would exceed after truncation. Source ordinals survive rejected rows, and existing drafts (including member edits) are never overwritten. One bounded replay chunk keeps the 128-event history independent of the 16-chunk live queue. A final write may have run while the initial D1 read was pending, before registration. The heartbeat reconciles subscribers outside termination even while the provider is idle, and comment frames make disconnects flush.
- **`fetch`** ([workers/import/index.ts](../../workers/import/index.ts)) — the import Worker has no public surface (fetch returns 404); the authenticated API uses the namespace binding exclusively.
- **`DUE_USERS_PER_DIRECTION`** ([workers/maintenance/index.ts](../../workers/maintenance/index.ts)) — users served per direction and cycle (ADR 0001 section 8); each user is further capped per call inside `applyDueTransitions`. `REPAIR_USERS` must exceed what a full cycle can dirty (two user lists plus earlier leftovers) so the repair loop can publish them all.
- **`scheduled`** ([workers/maintenance/index.ts](../../workers/maintenance/index.ts)) — step 1: the maintenance guard runs before any DB access, including the status probe, so `MAINTENANCE_MODE` truly freezes the cycle. Steps 2 and 3 (ADR 0001 sections 2 and 8): users are chosen by their oldest due stored deadline, the cursor, so a backlog or missed day catches up over successive cycles without moving anyone's eligibility, and a flight past both deadlines makes both moves in one pass; each user is one capped batch, and one account's failure never blocks the others but fails the cycle. Step 5: a leaderboard refresh failure must not skip cleanup (ADR 0008 staging expiry, sessions, receipts); it fails the cycle in step 7. Cleanup: import drafts are deleted at their batch's expiry and the batch row a week later, conversion receipts age from their own creation, Flighty staging closes 30 days after a run opened while committed rows and tombstones stay (ADR 0008), ground-travel receipts expire at their stored instant while tombstones stay for the account's lifetime, and a batch whose job died is interrupted through the one shared `interruptBatchSql` definition. Step 7: remaining dirty users, stale stamps or due transitions make the cycle a retryable failure.

### Test harness decisions

- **`OLD_CREATE_LEDGER`** ([lifecycle-fixture.ts](../../functions/test/lifecycle-fixture.ts)) — the pre-lifecycle writer statements are copied verbatim from `abe1d80`, the build below the rollback floor, so the migration tests exercise exactly what a rolled-back build would run; do not modernize them. D1 `meta.changes` is a `total_changes()` delta (ADR 0001 section 1) that includes the lifecycle adapter's nested write; old readers tolerate it because they only test `> 0`, log it, or read the trigger-free ledger statement. A build below the floor publishes the revision without the evidence stamp, so the owner reads `updating` while public readers keep serving the last published profile.
- **`MAPPING_HASH_BY_VERSION`** ([regions.test.ts](../../functions/test/regions.test.ts)) — moving a country between regions changes what Overview and Passport report for existing accounts, so it is a policy change: bump `REGION_POLICY.version` (and `id`) together with this pin, never the pin alone.
- **`createApiDatabase`** ([harness.ts](../../functions/test/harness.ts)) — one Miniflare per test file holds four D1 bindings; booting workerd and replaying every migration per test cost about 350 ms apiece, so a binding is migrated once and wiped back to that state when handed out again. It deletes `airports_reference` after migrating because API fixtures supply their own airport corpus and reference-data migrations belong to the dedicated migration tests, not thousands of restored rows per test. D1 always enforces `ON DELETE CASCADE`, so row counts cannot prove the explicit deletes in account deletion; the test records the batch statements to verify children-before-parents order in one atomic batch. `instrumentDb` ([db-hooks.ts](../../functions/test/db-hooks.ts)) tracks SQL by wrapping statement RPC stubs and unwrapping inside `batch`, because workerd hands out stubs.
- **`clock`** ([import-fixture.ts](../../functions/test/import-fixture.ts)) — fakes only `Date`; D1 and the workerd runtime need real timers, and faking them all would hang the API tests.
- **`runtime`** ([import-runtime-fixture.ts](../../functions/test/import-runtime-fixture.ts)) — Miniflare is loaded through wrangler's require because only wrangler's installed runtime supports the required keep-alive date and the root Miniflare is older. - **`airport catalog expansion`** ([airport-catalog-migration.test.ts](../../functions/test/airport-catalog-migration.test.ts)) — D1's hosted statement size limit (100,000 bytes) also applies inside a batch, so migration statements are asserted below it.
- **`mockMail`** ([link-request.test.ts](../../functions/test/link-request.test.ts)) — acknowledges only the recipient each send asked for, as the real provider does: the sender rejects any receipt naming someone else and then deletes the activation token.

## Consequences

- Each rule above is load-bearing for a platform limit, a security property or a replay guarantee. Changing a listed behaviour means updating this ADR in the same change, and the entry's symbol is the place to look.
- Where an entry cites an ADR (0001 to 0008), that ADR remains the authority for the lifecycle, evidence, import and publication models; this ADR only records the reasons that lived in the code.
- A new code comment is a lint error. A new non-obvious server decision belongs in this ADR, or in a new ADR when it is a design choice of its own.

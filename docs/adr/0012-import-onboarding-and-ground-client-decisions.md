# ADR 0012: Import, onboarding and ground travel client decisions

- **Status:** Accepted, 21 November 2026.
- **Source:** decisions that lived as code comments until the comment ban (`scripts/comments.mjs`); each entry names the symbol it governs.

## Context

The browser side of import (documents, boarding passes, barcodes, the Flighty CSV history import), onboarding and ground travel carries many rules that the code cannot express: why a request is sent one at a time, why a key is reused, why a value is kept out of browser storage. They were written as comments next to the code. Comments are now banned by lint, so each rule that a reader could not rebuild from the code is recorded here under the symbol it governs. Rules already recorded in [ADR 0001](0001-flight-lifecycle-and-import-drafts.md), [ADR 0005](0005-ground-travel-journey-boundaries.md) and [ADR 0008](0008-flighty-history-import.md) are linked, not repeated.

## Decision

### Boarding-pass and barcode privacy

- **`parseBcbp`** ([bcbp.ts](../../apps/next/src/client/import/bcbp.ts)) — projects an IATA BCBP barcode (Resolution 792) onto airports, carrier, flight number and Julian day only. Passenger name, PNR, seat, sequence, status and the conditional and security sections are read past by offset and never copied out, so nothing else can leave the module. `null` means the text is not a usable boarding pass and the caller falls back to uploading the source. The layout constants encode the format: a 23-character header (`HEADER_LENGTH`), then 37-character leg blocks (`BLOCK_LENGTH`): PNR 7, from 3, to 3, carrier 3, flight 5, day 3, compartment 1, seat 4, sequence 5, status 1, then the conditional-section size in two hex digits.
- **`readBoardingPass`** ([barcode-reader.ts](../../apps/next/src/client/import/barcode-reader.ts)) — decodes entirely in the browser in a dedicated worker. The decoder (zxing-wasm, self-hosted wasm) and pdf.js load only once a file is chosen. Decoded text goes straight into the BCBP projection and is never logged, stored or returned, so only allowlisted legs leave the module. `decodeBoardingPass` ([barcode-decode.ts](../../apps/next/src/client/import/barcode-decode.ts)) keeps the raw text inside the worker for the same reason.
- **`PDF_MAX_IMAGE_PIXELS`** ([barcode-reader.ts](../../apps/next/src/client/import/barcode-reader.ts)) — pdf.js skips embedded images above the limit and shrinks those above the canvas area, so a phone photo wrapped in a PDF decodes inside the same memory bound as a page render.
- **`takePixels`** ([barcode-reader.ts](../../apps/next/src/client/import/barcode-reader.ts)) — zeroes the canvas size after reading pixels, because mobile browsers count canvases against a tight total memory budget.
- **`BoardingPassSource`** and **`submitSource`** ([import-api.ts](../../apps/next/src/client/import/import-api.ts)) — a barcode source carries only flight fields read on this device: no file bytes, no decoded text. Source bytes and pasted text live only in the request body and never touch browser storage.
- **`fileToBase64`** ([source-step.tsx](../../apps/next/src/client/import/source-step.tsx)) — builds the base64 in memory for the request body only; it must never be written to browser storage (privacy boundary).
- **`passFile`** ([import-client.tsx](../../apps/next/src/client/import/import-client.tsx)) — Quick Add keeps the chosen pass file in memory only, never stored, while its reading is partial, so the member can still send it for online recognition. Any other submission, and leaving the flow, drops it.
- **Quick Add source step** ([quick-add-source.tsx](../../apps/next/src/client/import/quick-add-source.tsx)) — a readable pass goes to the server as flight fields only. Anything else is offered as an upload for online recognition, and only after the member has been told the document will leave the device. The file lives in component state and is never stored.
- **`passUploadFence`** ([import-client.tsx](../../apps/next/src/client/import/import-client.tsx)) — names the one pending pass read. Leaving the flow clears it, so a read that lands afterwards is dropped.
- **Retry after a reload** ([import-client.tsx](../../apps/next/src/client/import/import-client.tsx)) — the document is never stored, so after a reload a retry asks for it again instead of replaying the stored failure.
- **`historyArchiveHref`** ([history-api.ts](../../apps/next/src/client/import/history-api.ts)) — the owner's archive is a same-origin download; the browser keeps it and the page never stores it.

### Confirm and replay safety

Lifecycle and draft rules: [ADR 0001](0001-flight-lifecycle-and-import-drafts.md) §6 and §9.

- **Confirm chunking** ([confirm-runner.ts](../../apps/next/src/client/import/confirm-runner.ts)) — reviewed drafts are confirmed in chunks of at most 50 items (the server cap). A chunk is sent only after the previous one answered, never fanned out. Every item has a deterministic key `import:<draftId>:<version>`, so a lost response is replayed by the server instead of creating a second flight, and no receipt is kept in browser storage.
- **Uncertain rows** ([confirm-runner.ts](../../apps/next/src/client/import/confirm-runner.ts)) — `uncertain` means the request was sent but no answer arrived: the row may or may not be saved, and resending the same key is safe. A transport failure or a 5xx may have committed, so those rows are uncertain; a 4xx was refused before any write. An item missing from a well-formed answer is unknown, never assumed saved.
- **`classifyRowFailure`** ([import-errors.ts](../../apps/next/src/client/import/import-errors.ts)) — only transient causes are retried, with the same key. The classification is pure and its copy lives in `copy.ts`, so a server message string is never shown and "Failed to fetch" never reaches the member.
- **`withSaved`** ([review-model.ts](../../apps/next/src/client/import/review-model.ts)) — a confirm answer is authoritative even when the read after it fails, so rows it saved show as saved until a newer snapshot agrees. `import-client.tsx` lays the same saves over the snapshot.
- **Submission operation id** ([import-client.tsx](../../apps/next/src/client/import/import-client.tsx)) — once a submission produced a stored batch with a known outcome, replaying its id only replays that outcome (ADR 0001 §6), so the next attempt with the same source gets a new id. While the outcome is unknown (request lost, batch still running) the id is reused so no second recognition starts. `SourceStep` ([source-step.tsx](../../apps/next/src/client/import/source-step.tsx)) keeps the id while the source is unchanged for the same reason: a retry never calls the recognition service twice.
- **`Busy`** ([import-client.tsx](../../apps/next/src/client/import/import-client.tsx)) — carries the reset epoch, so a late answer after a reset neither writes state nor frees a newer operation.
- **`resetEdits`** ([import-client.tsx](../../apps/next/src/client/import/import-client.tsx)) — edits belong to one batch: a reset disposes the old saver (in-flight answers are dropped) and starts a new one.
- **`onSelectAll`** ([import-client.tsx](../../apps/next/src/client/import/import-client.tsx)) — saves one draft at a time, because each edit is version-checked and the requests are never fanned out together.
- **Leaving the review** ([import-client.tsx](../../apps/next/src/client/import/import-client.tsx)) — Import, Retry original save and Done retry are held back while a correction is typed or unsent, because leaving would unmount the form and lose it. The review shows the reason beside the control.
- **Derived-state refresh** ([import-client.tsx](../../apps/next/src/client/import/import-client.tsx)) — a `ready` answer refreshes through the feedback. Any other answer calls `router.refresh()` at once, which drops a Passport prefetched before the write, so Open Passport shows the new revision and waits for its publication itself.
- **`DraftSaver`** ([draft-saver.ts](../../apps/next/src/client/import/draft-saver.ts)) — unsent review text never leaves memory. A failed PATCH keeps the change in the saver and the form keeps showing it; the member can retry, re-apply after a conflict or discard. Edits to one draft are serialised so each request carries the version the previous one returned. `dispose` drops parked and queued edits and silences in-flight requests, so nothing leaks into the next import once the batch is discarded, cancelled or replaced.
- **`unsentNow`** ([import-client.tsx](../../apps/next/src/client/import/import-client.tsx)) — synced at commit, before any awaited save step resumes, so those steps read the current unsent state while render stays pure.
- **Zone on confirm** ([import-api.ts](../../apps/next/src/client/import/import-api.ts)) — `confirmItems` sends the member's IANA zone on every confirm, as the other flight writes do, and retries once without it when the zone is rejected. `confirmHistoryRows` ([history-api.ts](../../apps/next/src/client/import/history-api.ts)) does the same.
- **`fetchPressedCountries`** ([import-api.ts](../../apps/next/src/client/import/import-api.ts)) — returns `null` when the passport cannot be read, so nothing is claimed as a new stamp.
- **`flightIdentity`** ([manual-save.ts](../../apps/next/src/client/import/manual-save.ts)) — deliberately conservative (date, origin, destination only): derived metadata and optional details cannot release an unresolved same-flight hold.
- **Manual-flight create operation** ([manual-save.ts](../../apps/next/src/client/import/manual-save.ts)) — reuses the shared create helper and its receipt (one stored key and payload per operation id, `flightCreateOperations`); no second receipt store exists. An operation stays unsettled, with receipt, operation id and pinned payload, until the outcome is known: a 2xx (written or replayed), a definitive validation refusal on an operation with no earlier attempt, or the member's explicit "I checked the journal". Everything else (401/403, 408, 409/410 idempotency answers, 413, 429, 5xx, network loss, or any refusal after an earlier attempt) may have followed a committed write, so the receipt stays and the unchanged row replays under the same key. A changed payload under that receipt is refused locally (`UnconfirmedFlightOperationError`).
- **`classifyManualFailure`** ([manual-save.ts](../../apps/next/src/client/import/manual-save.ts)) — `firstAttempt` is true only when no receipt existed before this send. Only then is a validation refusal proof that nothing was written; after an earlier attempt of unknown outcome the operation stays unsettled.
- **`saveManualRows`** ([manual-save.ts](../../apps/next/src/client/import/manual-save.ts)) — a new row must not mint a second key for a flight whose earlier save is unresolved, whatever wrote that receipt: the same date and route are held back, pointing at that save, until it is settled. Only a first-attempt validation refusal frees the receipt and rotates the operation id, so the corrected row is a fresh operation instead of a clash; every other failure keeps both.
- **`unconfirmedSaves`** ([manual-save.ts](../../apps/next/src/client/import/manual-save.ts)) — lists every unresolved create receipt of this owner in this browser, whatever wrote it: a manual row of any import (plain UUID ids from earlier versions, `manual:<scope>:` ids), the add-flight form, or the legacy import's `<run>:<row>` ids. Each is shown once with the payload its receipt pinned. Retrying replays that payload under its own key, so listing a receipt another screen also owns can never mint a second key. `receipts` in [import-client.tsx](../../apps/next/src/client/import/import-client.tsx) shows them on every step until settled; a row of the page that owns one shows its own recovery instead.
- **`retryUnconfirmedSave`** ([manual-save.ts](../../apps/next/src/client/import/manual-save.ts)) — "Retry original save" resends the pinned payload under its own key. Nothing is rotated or dropped unless the answer is a 2xx; any other answer leaves the receipt for another retry or the journal check. A missing or replaced receipt reports settlement elsewhere and never becomes a new operation. Failures are classified with `firstAttempt = false`, because the receipt predates the send.
- **`ManualRow` edits** ([review-step.tsx](../../apps/next/src/client/import/review-step.tsx)) — edits that touch only optional fields keep a date/route hold tied to its original receipt until recovery settles it.
- **`UnifiedSession.save`** ([unified-session.ts](../../apps/next/src/client/import/unified-session.ts)) — one explicit member save authorizes past-flight confirmation, then reuses the idempotent per-batch confirm receipts. The receipt version after the patch is pinned for every retry of an unknown confirm outcome.
- **`UnifiedSession` submission** ([unified-session.ts](../../apps/next/src/client/import/unified-session.ts)) — barcode fields are persisted before the full source is sent, so resume never depends on the file staying in memory. Source bytes are memory-only; failed inputs are kept for retry only while the page stays open. Retry never replaces retained partial drafts or receipts: it adds a new run and the server's duplicate guard applies.
- **`UnifiedSession.pump`** ([unified-session.ts](../../apps/next/src/client/import/unified-session.ts)) — runs one processing batch at a time, because the existing admission contract permits one processing batch per owner.
- **Dismissal** ([unified-session.ts](../../apps/next/src/client/import/unified-session.ts)) — the suppressed draft id is recorded before the dismissal request is sent, so an interrupted response cannot expose a system-made Restore action.
- **`UnifiedImport` presentation** ([unified-import.tsx](../../apps/next/src/client/import/unified-import.tsx)) — rows shown with `flown_confirmed` forced true are presentation only: the final save carries the owner's confirmation and the display suppresses just the repeated question. Paste is ignored while the history screen is open, because a paste there would restart the Flighty upload under way or start a document read the owner cannot see.

### Import batch run, watcher and dock

- **`batch-run`** ([batch-run.ts](../../apps/next/src/client/import/batch-run.ts)) — free of React so the import runs provider keeps a run alive across routes and a hook reads it with `useSyncExternalStore`. The snapshot is the only authority; nothing is written to browser storage. `useImportBatch` ([use-import-batch.ts](../../apps/next/src/client/import/use-import-batch.ts)) follows the same rule: inside the member shell's import runs the run belongs to the shell, so leaving the page keeps it being read; outside it (the welcome card, tests) the run belongs to the hook and unmounting stops it.
- **`Stopped` and cancel** ([batch-run.ts](../../apps/next/src/client/import/batch-run.ts)) — rows kept although recognition stopped early appear under an explicit "partial" heading. A cancel keeps the rows found before it (ADR 0001 §9), so a cancelled batch with drafts becomes a ready `stopped` review rather than a `cancelled` phase; an interruption carries what the server reported.
- **`watchBatch`** ([batch-watcher.ts](../../apps/next/src/client/import/batch-watcher.ts)) — D1 (the snapshot) is authoritative; server-sent events only say "read again". It is free of React and the transport so resume, gaps and reconnects are unit-tested. A terminal end status stops reconnecting for good: if the snapshot read it triggered failed, only that read is retried with a bounded backoff, and the stream is never reopened for a status other than `processing`.
- **Import announcer** ([announcer.ts](../../apps/next/src/client/import/announcer.ts)) — speaks every stage change at once, found-count changes at most once per interval, and the last held count when the interval ends. It is pure and clock-injected.
- **`ImportRunsProvider`** ([import-runs.tsx](../../apps/next/src/client/import/import-runs.tsx)) — mounted by the member shell only when the job worker is bound, and keyed by the owner so signing out drops every run. It seeds from `/api/me/awaiting` and asks it to reload when a run finishes, so the header count agrees with the dock. Runs stay alive across member routes so reading continues elsewhere; only reading happens in the background, review and saving stay on `/import` (decision 1), and nothing is written to browser storage. A page that shows a run "views" it and the dock leaves viewed runs to the page; opening a finished run's review is what clears it from the dock.
- **Silent runs and `seen`** ([import-runs.tsx](../../apps/next/src/client/import/import-runs.tsx)) — runs that end with nothing to look at (a cancel that kept no rows, an expired batch, a finished batch with no rows left in review) leave the dock without a word. `seen` remembers every batch the tab has held, so a stale awaiting read never brings back a run that ended or was dismissed.
- **`seed`** ([import-runs.tsx](../../apps/next/src/client/import/import-runs.tsx)) — follows only batches the server is still reading; batches already in review belong to the header queue, not the dock.
- **Import dock** ([import-dock.tsx](../../apps/next/src/client/import/import-dock.tsx)) — floats in the shell's toast corner and only follows reading; ready runs call the member back to `/import`. It announces stage and state transitions, never every found count. Its live region stays mounted in one place so screen readers have it before the first transition.
- **`keyOf`** ([import-dock.tsx](../../apps/next/src/client/import/import-dock.tsx)) — run keys come from a WeakMap, because a run has no batch id until the server accepts its upload. **`itemCache`** memoises one dock item per immutable run state and locale, so a change to one run never rebuilds the others' review counts.
- **Lazy dock** ([import-dock-lazy.tsx](../../apps/next/src/client/import/import-dock-lazy.tsx)) — loaded dynamically after the page with `ssr: false`: it renders into the toast slot, which exists only after hydration, and loading it late keeps its review rules, airport tables and sheet motion out of every route's first load.
- **Import wire types** ([import-types.ts](../../apps/next/src/client/import/import-types.ts)) — a client copy of `functions/api/_services/importDrafts.ts` and `importConversion.ts` (ADR 0001 §6/§9), so the Next bundle never imports Worker code.
- **`FailurePanel`** ([failure-panel.tsx](../../apps/next/src/client/import/failure-panel.tsx)) — a stated cause with its own actions. It replaces the review and is never rendered beside empty-review copy.
- **`FileDropzone`** ([file-dropzone.tsx](../../apps/next/src/client/import/file-dropzone.tsx)) — manually adapted from the MIT-licensed Arc FileDropzone (`../ui/ARC-LICENSE.txt`). Keep that attribution and its selection, thumbnail, removal, sheet-stack, drag-depth and clipboard lifecycle; Kuuki owns validation and submission; `motion/react` is omitted. By default it picks one document; `multiple` hands every picked or dropped file to the caller, which renders its own per-file rows.
- **Import copy** ([copy.ts](../../apps/next/src/client/import/copy.ts)) — every string is written in English and Russian together (Russian addresses the member as «вы»), counts use real plural forms, and server messages are never shown. `PROMPT_EXAMPLE` is one string so the copy prompt and the server parser grammar (`functions/api/import/_text.ts`) are tested against the same text (`prompt-contract.test.ts`). The prompt asks for the reply format the server extraction reads most reliably (`functions/api/import/_shared.ts`): a written year, IATA codes, one segment per line, no private booking details. `emailHelpBody` names assistants, not their mail and calendar features, because assistants rename those features often.
- **Passport link in the done step** ([done-step.tsx](../../apps/next/src/client/import/done-step.tsx)) — may prefetch fully: stamps appear only after the write refreshed the router, and every later write refreshes it again.

### Review questions and aircraft review

- **Review questions** ([questions.ts](../../apps/next/src/client/import/questions.ts)) — what holds review rows back, grouped so one answer settles every row with the same cause. Questions are derived from the drafts on every render and never stored. An answer is an ordinary draft change, so a reload, another tab or an expired batch behaves as it does for row edits. Kuuki never answers for the member: suggestions are buttons, never defaults.
- **`suggestedYears`** ([questions.ts](../../apps/next/src/client/import/questions.ts)) — offers the latest year in which every given day has happened by today plus 2 days (a boarding pass issued the day before), and the year before it. Both are buttons; neither is preselected.
- **`buildQuestions`** ([questions.ts](../../apps/next/src/client/import/questions.ts)) — asks the flown question for duplicate rows too: their "Save anyway" stays blocked until the flight is confirmed, and only the member can acknowledge the duplicate itself.
- **`readyAfter`** ([questions.ts](../../apps/next/src/client/import/questions.ts)) — source verification is informational and never holds a row back from selection (amends ADR 0001).
- **`formatMonthDay`** ([question-deck.tsx](../../apps/next/src/client/import/question-deck.tsx)) — formats a printed day without its year in a fixed leap year, so 29 February survives.
- **Aircraft review** ([aircraft-review.ts](../../apps/next/src/client/import/aircraft-review.ts), [aircraft-panel.tsx](../../apps/next/src/client/import/aircraft-panel.tsx)) — suggestions come from `/api/enrich/aircraft`; accepting goes through `/api/flights/aircraft-batch`, 20 flights at a time and never in parallel. Only suggestions at or above 0.7 are offered. Suggestions from older responses omit `basis` and start selected. Select-all doubles as deselect-all. Every flight keeps its own outcome: saved, failed, or `uncertain` when the answer was lost (the aircraft may or may not have been written). `onSaved` fires after any confirmed write, including a partial one, so every freshness owner refreshes.
- **Aircraft announcements** ([aircraft-panel.tsx](../../apps/next/src/client/import/aircraft-panel.tsx), [aircraft-announcement.tsx](../../apps/next/src/client/import/aircraft-announcement.tsx), [aircraft-review.ts](../../apps/next/src/client/import/aircraft-review.ts)) — counts for the finished submission are cleared when the next one starts, so an identical result is announced again. Both live regions stay mounted so each submission can update the right one. `summarizeAircraftRun` returns one sentence; nothing saved is a problem and goes to an assertive region, anything saved goes to a polite one.

### History import session

Storage, run tables and mapping: [ADR 0008](0008-flighty-history-import.md).

- **`HistorySession`** ([history-session.ts](../../apps/next/src/client/import/history-session.ts)) — the file is parsed in the browser and sent in digest-checked chunks; from then on the server run is the only authority and a refresh restores from it. Browser storage holds only the run id, the operation id and the manifest digest, never cells or the file. `forOwner` keys `sessionStorage` per owner as `kuuki-history-import:<ownerId>`.
- **`putHistoryChunk`** ([history-api.ts](../../apps/next/src/client/import/history-api.ts)) — the chunk body is the exact payload its digest was computed over, because the server re-hashes it.
- **Chunk sending** ([history-session.ts](../../apps/next/src/client/import/history-session.ts)) — `send` sends the chunks the server lacks one at a time; an admitted chunk resent after a lost answer inserts nothing. When every chunk arrived but the run never sealed (the last answer was lost mid-seal), a replay of the last chunk seals it.
- **`creating`** ([history-session.ts](../../apps/next/src/client/import/history-session.ts)) — a run creation whose answer may have been lost is kept in memory with its manifest digest, so Retry repeats it even when browser storage is blocked.
- **`historyConfirmKey`** ([history-session.ts](../../apps/next/src/client/import/history-session.ts)) — deterministic per row version (`h-<rowId>-v<version>`), so a lost answer is retried with the same key and the server replays it.
- **`save`** ([history-session.ts](../../apps/next/src/client/import/history-session.ts)) — confirms every ready row in server pages of 50. The owner presses once; the number of requests grows with the file, the number of decisions does not. It stops when a page brings no progress (every item refused). It will not start while an answer or Skip is in flight, because confirming ahead of it could save the record being excluded.
- **`failIfCurrent`** ([history-session.ts](../../apps/next/src/client/import/history-session.ts)) — a superseded run never reports its failure over the current one.
- **`stampLedger` and `followStamps`** ([history-session.ts](../../apps/next/src/client/import/history-session.ts)) — one ledger per run in this tab, so a save that failed half-way or ran before the last questions were answered still counts: the passport before the run's first confirm (read beside the first page; `null` claims no stamp) plus the route countries of every row created since. New stamps are decided as in the regular import: wait for the derived publication of the last confirm's acknowledgement (ready at once, or the bounded poll; anything else or a timeout is delayed), re-read the passport, and keep the countries this save touched that were not pressed before. An unreadable passport claims nothing; the passport itself shows what was pressed.
- **`HistoryImport`** ([history-import.tsx](../../apps/next/src/client/import/history-import.tsx)) — one summary of counts, one question per group, the records that still need an answer paged from the server, and one Save walked by the controller in server pages. Everything shown comes from the server run, so a refresh lands on the same decisions.
- **`ChoiceAnswer`** ([history-import.tsx](../../apps/next/src/client/import/history-import.tsx)) — an answer is sent at once, so only an explicit choice sends it. Leaving the field does not (Combobox settles a typed exact code on blur), so a click on Skip or another answer is never preceded by this one.
- **Focus after an answer** ([history-import.tsx](../../apps/next/src/client/import/history-import.tsx)) — focus goes to the item now in its place; when its list emptied, to the first item of another list, then Save, then the title. Never to a section heading, which unmounts with its last item.
- **History copy** ([history-copy.ts](../../apps/next/src/client/import/history-copy.ts)) — English and Russian together («вы»), calm and direct because it is capture and privacy copy. Server messages are never shown; causes come from `HistoryFailure` kinds.

### Security lane figure

- **Tray placement** ([lane-figure.ts](../../apps/next/src/client/import/lane/lane-figure.ts)) — a tray is drawn once at `MOUTH` and every other place is that one moved by a CSS transform, so the element survives a rebuild and its transition runs. Bounds come from every possible place (`REACH`), so the viewBox never depends on the model.
- **Twin trays** ([lane-figure.ts](../../apps/next/src/client/import/lane/lane-figure.ts)) — a tray past the tunnel stands behind it and one before it stands in front, yet an element that changes layers loses its transition. So each tray is drawn twice with one transform: one copy under the tunnel, and a twin over it that shows only in front of the entrance.
- **`SecurityLane`** ([security-lane.tsx](../../apps/next/src/client/import/lane/security-lane.tsx)) — keyed on `JSON.stringify(model)`, because the parent builds a new model on every render and the drawing should rebuild only when it says something new. A phone gets the small box once the media query can be read, the desktop one until then. A new box is a new drawing (the figure is keyed by box size), so trays never glide from one scale's places to the other's. Disconnected trays are pruned from the travelling set, because a tray removed mid-travel ends its transition where no listener hears it and the rollers would keep running.

### Welcome flow and onboarding

- **`WelcomeFlow`** ([welcome-flow.tsx](../../apps/next/src/client/welcome/welcome-flow.tsx)) — the parent owns the passport geometry. Step changes are published before the morph's new snapshot, and the phone's same-step bench reveal is scoped to the same machinery without starting a transition inside a step morph. Back past the name step lands on the entry URL; it is replaced with the name step (`welcomeUrl`), because the account already exists and the create step must never show again.
- **`morph`** ([morph.ts](../../apps/next/src/client/welcome/morph.ts)) — runs a card state change as a same-document view transition, so the card grows, the passport opens and the step content cross-slides instead of snapping. `html[data-welcome-morph]` names the morphing parts only while it runs, so the theme sweep's own view transition never sees them ([welcome.css](../../apps/next/src/client/welcome/welcome.css) holds the names under that attribute). Without the API, with the tab hidden or during a theme switch, the change applies at once. The attribute is cleared only when the morph's id is still the latest, because a newer morph owns it.
- **`dissolve`** ([dissolve.ts](../../apps/next/src/client/welcome/dissolve.ts)) — the card's exit into the Overview uses opacity, scale and blur over `--dur-moment` with `--ease-out`; reduced motion keeps only the crossfade. It resolves half way, so the caller starts the navigation while the fade finishes and the old document keeps painting it until the Overview's first paint, instead of a blank wait after an empty card. It resolves at once without WAAPI.
- **Flights step auto-advance** ([flights-step.tsx](../../apps/next/src/client/welcome/flights/flights-step.tsx)) — `observed` records that this mount saw the batch being read (or sent it); only then does `ready` move on by itself. A batch already ready on arrival (Back from review, a reload) waits for the member (17.13).
- **Flights step input** ([flights-step.tsx](../../apps/next/src/client/welcome/flights/flights-step.tsx)) — keyboard clipboard chips (Gboard, SwiftKey) insert text without a paste event, so the box needs its own submit path. A file drop is always claimed, because an unclaimed file would navigate the tab away from the step. The screenshot file input sets no `capture` attribute, so the phone's sheet offers both camera and library.
- **`readClipboard`** ([clipboard.ts](../../apps/next/src/client/welcome/flights/clipboard.ts)) — reads inside a click: an image item first, then text, then `readText()` for browsers without `read()`. One attempt only: a denial is reported and never retried. A refusal (`NotAllowedError`) is final; any other failure (an unsupported type, a missing API) falls back to `readText()`.
- **Name step** ([name-step.tsx](../../apps/next/src/client/welcome/name-step.tsx), [name-step.css](../../apps/next/src/client/welcome/name-step.css)) — a fixed random tail per mounted step keeps the `pilot-xxxx` fallback address from flickering while typing. An unreachable username check resolves as ok: the server is authoritative on save and must not be blocked by the check. On mobile the address editor is a full 48px input (board 16.13 drew 36px) with 16px text, which keeps iOS from zooming on focus.
- **`ReviewStep`** ([review-step.tsx](../../apps/next/src/client/welcome/review/review-step.tsx)) — keeps the latest copy of every draft in a ref store, so a save started right after an edit sees the version that edit returned. The saver is disposed in a microtask so React's effect replay (strict mode) can reactivate it first. A fresh batch with nothing unsure and something right is saved without a stop here; only the first settled state decides, once, and a member who later resolves the last unsure card presses Save themselves. A row the server refused for good is not retried as it stands: it goes back to unsure, with a fresh read on a conflict. Resolving an unsure card removes the control that had focus, so focus is handed to the next card.
- **Review card layout** ([review.css](../../apps/next/src/client/welcome/review/review.css)) — no hairlines between rows; space does the grouping (project-wide ban). The save bar bleeds to the panel edge with the frame's `--welcome-bleed`.

### Onboarding passport bench

- **`PassportPreview`** ([passport-preview.tsx](../../apps/next/src/client/welcome/passport/passport-preview.tsx)) — the server and the first render are the phone's. The bench loads for the desktop at once, and on a phone only once a batch is read or the reveal comes (`benchOnPhone`).
- **Bench live layer** ([bench-live.ts](../../apps/next/src/client/welcome/passport/bench-live.ts)) — one `requestAnimationFrame` loop writes attributes on refs inside the generated SVG, so React never re-renders per frame. `shown` measures printed text even while its page is hidden: a closed leaf is `display: none`, and hidden text measures 0, so the page is unhidden briefly. `clearEntry` also drops finished entry presses, because `snap()` replays every kept press and would ink the cleared stamp again. The bench keeps countries in arrival order and presses membership additions even when review inserts an earlier draft's countries before existing ones or reorders the list.
- **`bench-geom.ts`** ([bench-geom.ts](../../apps/next/src/client/welcome/passport/bench-geom.ts)) — Node runs this file directly with type stripping, so it uses explicit extensions and erasable TypeScript only.

### Ground travel API and drafts

Journey and boundary model: [ADR 0005](0005-ground-travel-journey-boundaries.md).

- **Operation keys** ([api.ts](../../apps/next/src/client/ground/api.ts)) — every ground-journey write carries its own operation key, so a retry replays instead of writing twice. `sendCommand` also drops `listMemo` again once the write settles, because a list read during the write may already have been remembered.
- **`listMemo`** ([api.ts](../../apps/next/src/client/ground/api.ts)) — holds the last list answers of this browser tab, so returning to the page shows them at once while a fresh read runs. It is written only from browser effects, never on the server, and any write drops it, because a stale copy could hide the change. `useGroundList` ([use-ground-data.ts](../../apps/next/src/client/ground/use-ground-data.ts)) starts a return visit from it (shown as refreshing, not as a skeleton); a full load has none, so hydration matches the server.
- **`readRailTicket`** ([api.ts](../../apps/next/src/client/ground/api.ts)) — one file per call; the server detects the type from its bytes and stores nothing. The OCR provider may take up to 90 s, so the client waits longer than its 30 s default, as flight import does.
- **Form drafts** ([draft.ts](../../apps/next/src/client/ground/form/draft.ts)) — unfinished ground-journey input lives under the capture prefix, so the identity reset (`clearCapturePreferences`) removes it. Keys carry the owner id and a schema version, so another account never reads a draft and an older shape is discarded instead of half-restored. A draft stores `journeyId`, the id a new journey is created under, so a retry after a reload never creates a second journey, and `baseVersion`, because the server's 409 decides whether an edit's starting version is still current. A save whose result is unknown is frozen with its operation key. Stored ticket previews keep only the editable preview fields, never the file or the reader's text, and are absent in drafts written before the reader existed.
- **`parsePending`** ([draft.ts](../../apps/next/src/client/ground/form/draft.ts)) — the frozen command is re-sent verbatim, so its identity is checked in full: a known form action, an operation key, the draft's own journey id, a version where the action needs one, and a route whose places the notice reads. Anything else is dropped rather than half-trusted.
- **`watchIdentityReset`** ([draft.ts](../../apps/next/src/client/ground/form/draft.ts)) — after an identity reset the stored draft belongs to nobody: the writer sets a reset flag so nothing queued or scheduled later brings it back. It stops writing for good and returns the unsubscribe for unmount.
- **`returnTo` and return context** ([journey-form.tsx](../../apps/next/src/client/ground/form/journey-form.tsx), [return-context.ts](../../apps/next/src/client/ground/form/return-context.ts)) — only the list's own filters are accepted from the URL, so a crafted link can never send the member to an arbitrary address (page-flow contract: allowlisted return context). Cancel and the saved journey navigate only to that allowlisted list address.
- **`EditJourney`** ([edit-journey.tsx](../../apps/next/src/client/ground/form/edit-journey.tsx)) — another owner's journey and a missing id read the same (404), so no data is revealed. A failed read is an error with Retry, never an empty form.
- **`JourneyForm`** ([journey-form.tsx](../../apps/next/src/client/ground/form/journey-form.tsx)) — built on the client only (`useMounted`), because unfinished input lives in `localStorage` and rendering it on the server would mismatch hydration. The `with-ocr` wrappers ([with-ocr.tsx](../../apps/next/src/client/ground/form/ocr/with-ocr.tsx)) exist because server pages cannot pass a function prop to a client component, so the wrapper owns the slot render.
- **`JourneyForm` save paths** ([journey-form.tsx](../../apps/next/src/client/ground/form/journey-form.tsx)) — `focusCountries` is a ref set synchronously, so two fast clicks cannot both start a re-read before the reducer shows it. The draft writer watches the identity reset, so a write queued for the owner who just left cannot land after it. When a save is pending the draft is flushed at once, not after the debounce: a write in flight is unconfirmed the moment the page may go away. Async save paths compare against `latest` (the form as it is now), not the form as it was when the request left. A late answer must not erase what was typed after the request left: keep the form and the draft, move the baseline to what was saved, and say the newer edits need their own save. On a version conflict the baseline version moves first, so even a refused apply leaves the next save aimed at the server's current version. If the saved journey was completed elsewhere while this edit is still a plan, the form becomes completed and demands the countries answer.
- **Save notice** ([journey-form.tsx](../../apps/next/src/client/ground/form/journey-form.tsx)) — one live alert, with the buttons outside it so a re-render never re-announces them.
- **Save state machine** ([save.ts](../../apps/next/src/client/ground/form/save.ts)) — a write that returns no usable answer is `unknown`, never `failed`: the frozen command keeps its operation key, so Check result reads the receipt and Retry original save replays the very same write. A new create id or key is never a way around it. In that phase the frozen request is shown, re-sent or checked as is; later edits never replace it. `commandFor` keeps the same operation key for the same payload across resubmits (double click, retry after an error); a changed payload is a different request and gets a new key, because the server rejects a reused key with a different payload.
- **Detail-sheet commands** ([journey-actions.ts](../../apps/next/src/client/ground/journey-actions.ts), [use-journey-actions.ts](../../apps/next/src/client/ground/use-journey-actions.ts)) — one command at a time, with a fresh operation key per attempt; a command whose answer was lost keeps its key until the owner resolves it (Check result / Try the same change again / dismiss), so a retry replays the original write (page-flow contract "Сохранение и восстановление"). A 409 never retries by itself: the latest version is loaded and the owner chooses again. State is kept per journey id, so one journey's notice or unresolved command never shows on, or blocks, another. If the session ended while an answer was in flight, the result is `unknown` (not failed) and nothing is applied, because whether it landed is unknown.

### Ground form model and rail OCR

- **Countries answer** ([model.ts](../../apps/next/src/client/ground/form/model.ts)) — a journey's status decides countries: plans carry none, completed ones always carry an answer. Crossed countries are owner-confirmed and never pre-filled. `noCountries` is the deliberate "None of these" answer, mutually exclusive with the list; an empty checklist alone is silence. `confirmedCountries` returns `[]` only for that deliberate answer and `null` for an unanswered form, so an empty list is never sent by default. `routeCountryCodes` are suggestions only, never a confirmation. A stored completed journey, even with an empty list, is a deliberate answer; completing a plan starts unanswered.
- **`durationManual`** ([model.ts](../../apps/next/src/client/ground/form/model.ts)) — holds only minutes the owner typed; empty means "let the schedule decide". `stateFromDto` copies a leg's duration only when `durationSource === 'manual'`, because echoing a schedule-derived value would turn it into a manual one on save.
- **`fromCity` and `toCity`** ([model.ts](../../apps/next/src/client/ground/form/model.ts)) — a city printed on a ticket, kept while the place is unset so the picker can search for it. Never a chosen place.
- **Command action** ([model.ts](../../apps/next/src/client/ground/form/model.ts)) — the one command a form save sends follows the stored status: a plan being completed uses `complete`, a completed journey `update` with its countries, any other stored journey `update` without them.
- **Rail OCR model** ([ocr/model.ts](../../apps/next/src/client/ground/form/ocr/model.ts)) — pure (no DOM, no network); nothing in it invents a year, a place or a country from a ticket. Printed cities are shown beside stations and never turned into a chosen place. `precheckFile` only refuses before any request; the server re-checks the real signature either way. Cancelled and other-passenger previews start unticked, so they are not added by default.
- **`legFromPreview`** ([ocr/model.ts](../../apps/next/src/client/ground/form/ocr/model.ts)) — with a `base` (Replace this leg) the old leg's id, places and typed duration stay and only the fields the preview states overwrite; without it the leg is new. Printed cities travel as hints for the place pickers while the leg has no place.
- **`repeatKey` and `findRepeats`** ([ocr/model.ts](../../apps/next/src/client/ground/form/ocr/model.ts)) — a possible repeat means the same train number, date and stations as a leg already in the form or an earlier preview. Without both stations nothing distinguishes two tickets, so nothing is called a repeat. Repeats are marked, never removed: one ticket twice and two similar tickets are the owner's call.
- **`OcrRow.attempt`** and **`settleRow`** ([ocr/model.ts](../../apps/next/src/client/ground/form/ocr/model.ts)) — `attempt` counts attempts, and `settleRow` applies an answer only if the row is still reading that exact attempt, so a late answer after Stop or Retry is recognised and dropped. The draft keeps only rows with previews not yet added and only their editable preview fields, never the file or the reader's text.
- **`useRailOcr`** ([use-rail-ocr.ts](../../apps/next/src/client/ground/form/ocr/use-rail-ocr.ts)) — runs the per-file requests two at a time in the order the files were chosen. Stop aborts what is running and starts nothing new. An answer applies only if its request was not aborted, its row is still on that attempt and the session is the one that sent it. Received rows are never rolled back.
- **`RailOcrPanel`** ([rail-ocr-panel.tsx](../../apps/next/src/client/ground/form/ocr/rail-ocr-panel.tsx)) — reads one file per request and every answer lands as editable previews. Nothing reaches the route except through "Add to route", "Replace route" or "Replace this leg". The partial ticket date is formatted in year 2000, a leap year, so 29 February prints; the year is never shown or used.
- **`ordered-rows`** ([ordered-rows.tsx](../../apps/next/src/client/ground/form/ordered-rows.tsx)) — `RowFields` stays open once a problem is revealed, so correcting an error does not hide the focused input. `OrderedRows` keeps a `latest` ref because the removal notice outlives the render and Undo must read the list as it is then, not as it was when the row was removed.
- **`SEGMENTS_OF`** ([metrics-preview.tsx](../../apps/next/src/client/ground/form/metrics-preview.tsx)) — after «из» the Russian count takes the genitive, so 21 reads «21 отрезка».

### Ground travel sheets and history gate

- **Ground wording** ([format.ts](../../apps/next/src/client/ground/format.ts)) — an unknown value is a word, never zero, and every distance is a straight-line approximation.
- **Ground states** ([states.tsx](../../apps/next/src/client/ground/states.tsx)) — a failed read is an Alert with Retry, never an empty state; "nothing here" and "nothing under this filter" are different screens.
- **`useGroundList`** ([use-ground-data.ts](../../apps/next/src/client/ground/use-ground-data.ts)) — fetches the list once per active/cancelled view; the transport filter is applied locally, so switching it never refetches. `useJourneyRead` reads one journey for the detail sheet. Answers that arrive after a session change, a newer request or an unmount are dropped.
- **Ground view history** ([use-ground-view.ts](../../apps/next/src/client/ground/use-ground-view.ts)) — follows the Journal's history rules (`journal/store.tsx`): filters `replaceState` and never move focus; opening a journey pushes ONE entry and switching replaces it; closing steps Back over the entry the sheet pushed (keeping filters changed meanwhile); a deep link, which has no entry of ours below it, closes by replacing the URL with the list.
- **`NEXT_HISTORY_KEYS`** ([use-ground-view.ts](../../apps/next/src/client/ground/use-ground-view.ts)) — `__NA`, `_N` and `__PRIVATE_NEXTJS_INTERNALS_TREE`: Next's patched history keeps its internals there, and copying them back (`ownHistoryState`) would skip its own `useSearchParams` sync.
- **History write throttling** ([use-ground-view.ts](../../apps/next/src/client/ground/use-ground-view.ts)) — browsers throttle history writes (Safari: 100 per 30 s). The write may throw by design; the view stays right and the next write catches the URL up.
- **Route sketch atlas** ([route-sketch.tsx](../../apps/next/src/client/ground/route-sketch.tsx)) — the pinned world outlines are drawn only for the copies that reach the frame (a date-line route needs two). Borders scale with the drawing, so a zoomed-in map (`scaleY > 3`) takes the fine-stroke `r2-fine` variant instead of a thick band.

## Consequences

- Changing any behaviour listed above means updating this ADR in the same change. A symbol that is renamed or removed has its entry renamed or removed here.
- The rules that replay a write under the same key (confirm items, history rows, manual-flight receipts, ground commands) are one contract: a change to any of them is checked against the others and against ADR 0001 §6 and ADR 0008.
- Privacy rules for boarding passes and documents (nothing but allowlisted flight fields leaves the device, no source bytes or decoded text in browser storage) are a boundary: widening one needs a new ADR, not an edit to this one.
